**Two things, and the first one corrects what `v0.1.1` said about itself.**

## The radio no longer becomes a new node by itself

`v0.1.1`'s notes said the first unit's radio came back from a half-written
install **with its key**. It did not. Its next `HELLO` on 6 November 2026 carried
a new key, meshmaster.dk logged `agent.companion_changed`, its repeater had to be
registered again, and its admin password became a random one nobody knows.

**The cause was in this firmware, and this release is where it stops.** Up to
`v0.1.1` the repeater's first act was the Adafruit core's `InternalFS.begin()`,
which **erases the whole file-system region and formats it when the volume will
not mount** — and the firmware then found no key file, drew a new key and saved
it, without a word. The volume had stopped mounting because one of its seven 4 KB
pages was torn: the core rewrites a whole 4096-byte page to change a 128-byte
LittleFS block, and the first page holds the superblock and the root directory, so
one reset inside that window takes the node's identity, its settings, its ACL and
its clock at once.

From `v0.1.2` a key is made **only where no node was** — a region that is blank
(a radio just provisioned), or a volume with neither a key file nor settings.
Anything else is a **lost identity**: no key is made, nothing is written, the mesh
is not started, and the radio says so until a person decides.

```
IDENTITY LOST: the file system at 0xED000 would not mount and is not blank. No key was made
and the mesh is not started. 'erase' then 'reboot' makes this radio a new node; the old key
cannot be recovered (docs/flashing.md 3a)
```

That line goes to the USB console every ten seconds, and there is no
`Repeater ID:` in front of it. On the link, a Walter sees the same news three
ways: `IDENTITY` is answered **`ERR_STATE`**, `HELLO`'s `caps` is **`0x21`** —
`CLI` and `ATTENTION`, and nothing else, because no clock, telemetry, mesh client
or observation ring is brought up — and an `EV_ATTENTION` of **reason 6, detail
1** wakes a sleeping Walter once. `CLI` knows two words, upstream's own: `erase`
and `reboot`; every other line is answered with the text above. The old key is
gone either way — nothing anywhere keeps a copy of a private key — but a node
that a mesh and MeshMaster both knew does not become a stranger without somebody
saying so, and whatever is left in the region stays readable until `erase` is
typed.

[**docs/flashing.md §3a**](https://github.com/twinoak/twinoak.meshcore.repeater-firmware/blob/v0.1.2/docs/flashing.md)
is the page: the recovery in four steps, `rak update status` on the Walter first,
what each flashing path may write and what it may not, how to tell whether the
key survived, and what a person re-applies if it did not.

## Link 1.2: a repeater can be read through its own Walter

**The repeater now answers its own Walter's status, neighbours, access-list and
owner-info requests with MeshCore's own bytes.** `LOCAL_REQUEST`
(`spec/LINK-PROTOCOL.md` §5.9, the capability bit `0x80`) is answered by the
node's own request handler — the same function that answers a mesh admin logged
in as one, called on the node itself with nothing on the air, nothing re-encoded
at either end and no job disturbed — and the response carries that answer's bytes
after its four tag bytes, which is exactly what a mesh exchange would have
delivered. So meshmaster.dk can read a repeater's status and its neighbour table
**through its own unit**, which until now it could not read at all: the link
carried that repeater's CLI lines and its telemetry and nothing that yields those
four answers, so a unit's own repeater stayed *stale* on the server for good.

Not one file of MeshCore is edited for it, as ever. Telemetry stays `LPP_GET`'s
and is refused here; discovery and trace are exchanges with *another* node and
have no local form, so they are not in 1.2. `caps` is now `0xff`, every bit the
protocol defines.
[docs/link.md](https://github.com/twinoak/twinoak.meshcore.repeater-firmware/blob/v0.1.2/docs/link.md)
§2i is the page, and `tools/linkcli.py local status` (or `neighbours`,
`access-list`, `owner-info`) is how a person reads it from a laptop.

## The Walter it goes with

**`v0.1.1`** — the Walter firmware's current release, published 7 November 2026.
It speaks **link 1.1**, so it does not ask for any of this: the two meet at 1.1,
a 1.1 `HELLO` is answered a 1.1 body, and the one thing that changes for it is a
`caps` word with a bit in it that the protocol tells it to ignore. **Nothing
breaks.**

It can flash this release. `requires.link_major: 1` is the only version a Walter
compares before it offers an image, and the descriptor it holds the flashed image
against afterwards compares the major too — no part of its update or its health
path looks at a link minor. And the first unit's radio now has a **golden image**
(`v0.1.1`, installed over SWD on 7 November), so this is the first release of this
firmware that can be offered to a radio over LTE with somewhere to roll back to.
The command that will ask a radio for these four answers (`rak local status`,
`rak local neighbours`) is that repository's pile 9, unreleased; until it is
there, the radio's half simply waits.

One thing a `v0.1.1` Walter cannot yet tell you: a radio in the lost mode reads to
it like **a repeater it has not identified yet**. `agent id` says *the radio has
no identity yet* and counts an answer with no key, and the heartbeat carries no
companion key — all true, but none of it says that the radio is refusing rather
than waiting for its first install. Telling the two apart from `ERR_STATE` is
that firmware's next pile.

## What it is

The same **MeshCore repeater** as `v0.1.0` and `v0.1.1`: upstream's
`simple_repeater` from the pin `repeater-v1.18.0` (`81dbae59`), compiled
unmodified and subclassed, with the link to the Walter, a clock for a board with
no RTC, the radio half of a MeshMaster exit node, and an image that says what it
is. **NoiseScope**, the spectrum and noise scanner, is in this release as before;
it speaks no link and keeps no identity, so neither of the two things above
changes it — its image carries `link 1.2` in its descriptor only because a
release's link version is one field for the whole release.

## What has been on a board, and what has not

**`v0.1.1` is on a board; this image is not.** On 7 November 2026 the first
unit's radio took `v0.1.1`'s `.bin` over SWD from its own Walter at `v0.1.1` — a
first install, 102 pages, read back whole, *proving*, *committing*, `done: … is
the golden image` — so the radio in the field runs `0.1.1+3d81536` today, and the
`.bin` over SWD, which `v0.1.0`'s notes called *met by no hardware at all*, has
been walked. The base `.hex` still has not. A telemetry job for
that repeater has also come down from meshmaster.dk and back through the link
(the Walter firmware's `tasks/phase-8/FOLLOWUPS.md`, the bench items of
7 November). The day before that, the same radio had taken a half-written
application over SWD and come back from `v0.1.0`'s published `.uf2` **as a new
node**, which is the event the first half of this release is a reply to.

**Everything `v0.1.2` adds is held by host tests and by the link loop, and by no
radio:** the identity rule and the lost mode against every state a volume and a
key file can be in, and `LOCAL_REQUEST` against all 106 checks of the
specification's 1.2 fixture, its nine rules in the session, and a laptop driving
`local …` through the real codec against a stand-in for upstream's handler. What
only a board can show is whether upstream's **real** handler answers those four
with the bytes it is expected to, and whether a torn file system is refused on the
chip the way it is refused in a test.
[docs/bench.md](https://github.com/twinoak/twinoak.meshcore.repeater-firmware/blob/v0.1.2/docs/bench.md)
§0 and §4 are the lines that would prove both.
