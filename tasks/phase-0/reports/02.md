# p0-02 — the-release

Pushing a tag `vX.Y.Z` on a commit CI has passed makes a GitHub Release that a
person, MeshMaster's catalogue and the Walter can all use: per image the raw
application binary for the SWD flasher, the DFU package and the UF2, plus
`manifest.json` in the canonical form, its Ed25519 signature and `SHA256SUMS`
(`spec/FIRMWARE-MANIFEST.md`, `spec/SYSTEM.md` S-8). *Run workflow* rehearses
the same three jobs and publishes nothing. `tools/verify.ps1` rehearses it
again on this machine on every commit, so the release path is exercised
without GitHub and without the key. Done in one session.

```
RAM:   [=         ]  13.2% (used 31096 bytes from 235520 bytes)
Flash: [=====     ]  47.1% (used 383752 bytes from 815104 bytes)
```

(unchanged by this task: nothing of ours is compiled into the image yet, and
the three defines it adds or respells are read by the tooling, not by code.)

## The shape of it

| | |
|---|---|
| `tools/pio/buildinfo.py` | a post-script, on every build: writes `$BUILD_DIR/buildinfo.json` (role, board, band, MCU, the version in the image, the MeshCore tag and pin, the environment) **and a byte copy of the linker script the link command used**, `ldscript.ld`. Nothing the build knows is typed into the release tooling. |
| `tools/release/build_release.py` | one build directory per image → `out/release/`: the raw `.bin` with its `load_address`, the `.zip`, the `.uf2`, `manifest.json` (validated with `manifestref.validate` before it is written) and `SHA256SUMS`. |
| `tools/release/sign_manifest.py` | `manifest.json.sig` from `$RELEASE_SIGNING_KEY`, never an argument and never printed. Refuses a release version with the specification's test key, refuses a missing key with the instructions, refuses a key that is not the one `keys/release.pub` publishes. |
| `tools/release/test_release.py` | 47 tests. |
| `tools/release/selfcheck.py` | those tests, then a dry run of the real thing: build, sign with the test key, verify. One command, because it needs `cryptography` and on this machine that means one container run rather than three. |
| `tools/release/requirements.txt` | `cryptography==50.0.2`, the one place it is pinned; `tools/verify.ps1` and both workflows install from it. |
| `.github/workflows/release.yml` | `ci-green` → `build` (one job per board environment, read from `platformio.ini`) → `publish`. |
| `keys/README.md`, `docs/release.md` | the key, and how a release is made and what to do when a tag is refused. |

`spec/tools/manifestref.py` is imported, not re-implemented: the canonical
form, `validate`, `file_entry`, `sign`, `verify`, `key_id`,
`find_descriptor` and `TEST_PRIVATE` all come from it, and
`manifestref.check(spec/fixtures/manifest)` is the first test to run so that
the fixtures everything else is held against are proven before they are used.

## Deviations from the spec or the task

- **`TWINOAK_BOARD` was `"rak4630_single"` and is now `"rak4630-single"`.** The
  specification spells a board `rak4630-single` (`spec/FIRMWARE-MANIFEST.md`
  §2, and the fixture's descriptor and file names), and that string is the
  manifest's `board`, the descriptor's `board` and part of every file name.
  Phase 0's task 01 defined it with an underscore, after the *environment*
  name. **`spec/` wins** (`tasks/README.md`), so the define is respelled and
  `TWINOAK_BAND='"868"'` is added beside it — the band was missing altogether
  and a manifest entry cannot be written without it. Nothing read either
  define before this task (task 01's report says so), the environment is
  still `repeater_rak4630_single`, and `platformio.ini` now says why the two
  spellings differ. Phase 3's task 01, which puts these strings into the
  image descriptor, inherits the corrected ones.
- **`ci-green` accepts a green `ci` run of either event for the commit, where
  the agent firmware's pins `--event push`.** `ci.yml` here does not run on a
  branch push (task 01's decision: one run per commit), so a *rehearsal* on a
  branch has only its pull request's run — with `--event push` the dry run
  this task's acceptance asks for could not pass at all before the merge. The
  job now takes any completed `ci` run of that commit whose conclusion is
  `success`, refuses when every run of that commit has completed without one,
  and waits otherwise. For a tag the effect is unchanged: a tag must be on
  `main`, and a commit of `main` has a push run.
- **`tools/verify.ps1`'s release step reads `out/build/<env>`, not
  `.pio/build/<env>`.** Found the hard way: the native step runs PlatformIO
  *in a container*, where a different Python and a different core compute a
  different project checksum, and PlatformIO then **deletes `.pio/build/`**
  before running — taking the board build's images and `buildinfo.json` with
  it. The build step already copied the images to `out/build/<env>` for the
  reviewer; it now copies `buildinfo.json` and `ldscript.ld` too and fails if
  one is missing, and the release step reads that directory. This also makes
  the local dry run the same shape as the workflow's, which reads a
  downloaded artifact and not a build tree. The note is in the script, beside
  the copy.
- **No `requires` in the manifest.** It is optional
  (`spec/FIRMWARE-MANIFEST.md` §2) and nothing here knows a minimum Walter
  version yet; the Walter firmware's own first release is where that number
  comes from. The shape test holds our image's keys against the fixture's
  minus that one field, so adding it later is a visible change.
- **The descriptor check is written and switched off**, as the task asks, and
  the workflow does *not* pass `--require-descriptor`. Without the flag the
  tool says `repeater.rak4630-single.868: no descriptor yet` per image; with
  it, `manifestref.find_descriptor` must find exactly one and it must agree
  with the manifest's role, board, band, version and link version. Phase 3's
  task 01 adds the flag to the `build_release.py` line of
  `.github/workflows/release.yml` in the same commit that places the
  descriptor. `docs/release.md` says so where a reader will look for it.

## Decisions taken without asking

- **The version comes from the image, and `--version` is a cross-check.**
  `build_release.py` reads the version out of `buildinfo.json` — what the
  build baked into the firmware — and refuses when a `--version` given on the
  command line disagrees: *"a manifest may not claim a version the image does
  not report"*. The workflow always passes `--version`, so the two agree or
  the release stops; the local dry run passes none and gets `0.0.0-dev`,
  which is what that build honestly reports. The alternative — typing the
  version into the manifest — is how a manifest comes to describe an image
  that is not there.
- **`app_region` is read from a *copy* of the linker script, taken at build
  time into the build directory.** The release is assembled on a machine that
  may not be the one that linked it: in CI the publish job downloads the
  build job's artifact and has no toolchain package, so the absolute path
  `env.GetActualLDScript()` returns would not resolve there. The copy is that
  file, byte for byte, so reading it is reading the script the build used.
  `buildinfo.json` also records the absolute path it came from, for the
  record.
- **The linker script's arithmetic is parsed, not evaluated.** `LENGTH =
  0xED000 - 0x26000` needs expressions, and a recursive-descent parser for
  integers (decimal, `0x`, ld's `K`/`M`/`G`), `+ - * /` and parentheses is
  thirty lines and runs nothing. `ORIGIN`/`org` and `LENGTH`/`len` are
  accepted; ld's one-letter aliases `o` and `l` are not, and a script that
  used them would fail loudly rather than quietly.
- **The raw binary is cut from the `.hex`, not from the `.elf`.** The Intel
  HEX is the linked image this build leaves and what every flasher for this
  board consumes, it is plain text, and its records make a gap and an
  out-of-region byte exact rather than inferred. Every record's checksum is
  checked and the end-of-file record must be there, so a truncated `.hex`
  cannot become a short image. The nRF52 build's own file uses extended
  *segment* records (type 2) rather than linear ones (type 4), which a test
  pins.
- **`link` comes from `spec/fixtures/link/link-v1.json`'s `link` field**
  (`1.0`). The manifest's `link` is the version the firmware speaks, and no
  firmware of ours speaks it yet (phase 1); the specification's own fixture is
  the smallest honest source. When phase 1 gives the firmware a constant, that
  is what a release should read, and `build_release.link_version` says so in
  one line.
- **`SHA256SUMS` covers the images and `manifest.json`, not
  `manifest.json.sig`.** Signing is a separate step and the `.sig` does not
  exist when the sums are written; and it needs no covering — the signature
  covers the manifest, and the manifest covers every other file by hash. The
  `sha256sum -c` step of the workflow passes with the `.sig` beside it
  unlisted.
- **A release version is `X.Y.Z` with optional `+build` metadata and no
  pre-release part**; anything else (`0.0.0-dev`, `0.0.0-dryrun+<sha7>`) is a
  rehearsal. That one regular expression is where `sign_manifest.py` decides
  whether the specification's test key may sign, and a test fixes both sides
  of it.
- **The public half is held against `keys/release.pub` by key id**, which
  `manifestref.sign` puts in the signature line — so `sign_manifest.py` needs
  no key arithmetic of its own and derives nothing. For the test-key path the
  public half comes from `spec/fixtures/manifest/index.json`'s
  `test_public_key`, again not derived.
- **A tag with no secret is refused twice**: once in `ci-green`, before
  anything is built, by testing only whether the secret is empty (its value is
  never printed, compared or written); and once for real in
  `sign_manifest.py`, which is the one the test covers.
- **The build matrix of `release.yml` is read from `platformio.ini`** by the
  `ci-green` job (`sed` over `[env:*]`, minus `native`), and the publish job
  derives its `--build-dir` list from the directories the artifacts came in.
  So adding a role or a board stays one section of `platformio.ini` and no
  second list anywhere — task 01's second decision, kept.
- **`cryptography==50.0.2`**, the newest release on the day, pinned in
  `tools/release/requirements.txt` and nowhere else. CI installs it into the
  runner's own Python beside PlatformIO (so the script takes its host path
  there), and this machine has none, so the release step runs in the same
  `python:3.11-slim` container the native step uses — nothing is installed
  into this machine's Python.
- **`out/release/` joins CI's artifact** (`out/build/`, `out/release/`,
  `out/verify/`), so the dry run every `ci` run makes is there to be
  inspected and not just believed.
- **`NOTES.md` is written to `out/`, not `out/release/`**, so that the release
  notes are not themselves an asset of the release.
- **The dry run's artifact is uploaded on the tag path too.** One step fewer
  to reason about, and the evidence of what was published is kept beside the
  release itself.

## New libraries (with the one-line justification)

- `cryptography == 50.0.2` (Python, `tools/release/requirements.txt`) — Ed25519
  as in RFC 8032 for the manifest's signature; it is what
  `spec/tools/manifestref.py` imports, so the choice is the specification's and
  only the version is ours. Nothing of it is on the board.

No new PlatformIO library, and no change to `[libs]` or to the MeshCore pin.

## Not verified here (and why)

- **The tag path's `gh release create` has never run, and cannot until the
  release key exists.** It is the same `publish` job as the dry run with one
  step more; what it would do is `gh release create vX.Y.Z` with the six
  files and `NOTES.md`. Two things are unproven by this session: that the
  upload itself works (a `GITHUB_TOKEN` with `contents: write`, which the
  agent firmware's identical step proves on another repository), and the
  signing step with a real key — stood in for by
  `test_the_real_path_signs_and_verifies`, which runs exactly that code path
  with a key in the environment and its public half in a file. **Thomas makes
  the key** (`keys/README.md`, `spec/SYSTEM.md` §10 item 1); until he does, a
  tag is refused in `ci-green` with the instructions, which is the safe
  state. The line is in `docs/bench.md` §0.
- **That the raw binary boots when written over SWD.** The `.bin` is the
  application bytes alone, to be written at `0x00026000` with nothing else
  erased. It was produced and checked against the build it came from — 383 752
  bytes, the flash figure to the byte, one contiguous span inside the
  application region — but no board took it, and no session can take one. The
  Walter's flasher and the bench own that; `docs/bench.md` §0 says what to do
  and what to look for.
- **The `.zip` and the `.uf2` were copied, not consumed.** They are the
  build's own files, renamed and hashed; task 01 left the same line about
  them.
- **The `--require-descriptor` path has never seen a real image**, because no
  real image has a descriptor yet. It is held by five tests against synthetic
  ones (none, one, two, a wrong board, a wrong version). Phase 3's task 01 is
  where it meets a linked image.
- **The weekly cache key changed** (`platformio.ini` *and*
  `tools/release/requirements.txt`), so `ci`'s first run on this branch was a
  cold one; its hit path is seen on the next.
- **A second board environment has never existed.** The manifest, the matrix
  and the `--build-dir` list are written for several images and tested with
  two synthetic ones (`test_two_environments_of_different_versions_are_refused`
  and the `upstream` check beside it), but only one environment has ever been
  built. Phase 3's task 01 adds the second.
