# p0-03 — the-upstream-watch

MeshCore moves and this firmware is built on a pin, so keeping up is now three
tiers, as in the agent firmware: a workflow that notices a new `repeater-v*`
tag and opens the bump as a pull request CI tests; one command that turns a
bump CI could not swallow into a task the driver runs; and
[`docs/upstream.md`](../../../docs/upstream.md), the page that says which is
which — and which, with the seven places a bump re-reads, is the substance of
the task. Nothing of what the firmware *is* changed: no source, no test, no
step of `tools/verify.ps1`.

```
RAM:   [=         ]  13.2% (used 31096 bytes from 235520 bytes)
Flash: [=====     ]  47.1% (used 383752 bytes from 815104 bytes)
```

(unchanged by this task, to the byte, from tasks 01 and 02.)

## The shape of it

| | |
|---|---|
| `tools/upstream-check.ps1` | is there a `repeater-vX.Y.Z` newer than `[meshcore].tag`? Reads and writes nothing; `-Tag` pretends the pin is an older one, `-GitHubOutput` for the workflow. The one question, askable by hand |
| `.github/workflows/upstream.yml` | Mondays at 06:29 UTC and on demand: that script, and the git and `gh` around it. A branch `upstream/<tag>` whose one commit moves `pin` and `tag` **and adds the row to the pin's history**, and a pull request *MeshCore \<tag\>* whose body is upstream's commits between the two pins. `pin_tag` rehearses the whole thing against an older tag |
| `tools/new-sync-task.ps1` | tier two in one command: `tasks/sync/NN-meshcore-<tag>.md` from the template, and the row the driver's table needs. It moves no pin — the workflow's branch already did |
| `tasks/sync/TEMPLATE.md` | this repository's standing instructions for a bump: the seven places, the rails, what is verified, and what stops the task |
| `tasks/sync/README.md`, `tasks/sync/reports/README.md` | the sync phase the driver already knows about (`-Phase sync`), with its table and where reports land |
| `docs/upstream.md` | the page: the three tiers, the seven places, what of MeshCore this firmware stands on, what a bump costs today, and the pin's history |

## Deviations from the spec or the task

- **The task takes two pull requests, for task 02's reason.** `gh workflow run
  upstream.yml --ref task/p0-03-the-upstream-watch` answers *HTTP 404:
  workflow upstream.yml not found on the default branch*, and the *Run
  workflow* button shows nothing either, so a rehearsal of *this task's own
  workflow* can only happen once that workflow is on `main`. The order is the
  one `reports/02.md` set: this pull request with everything and one checklist
  item openly unticked, merged on green; then the two dispatches; then a
  second pull request that changes nothing but this report. Nothing reaches
  `main` outside a pull request.
- **The task's list of places a bump re-reads is seven; there is an eighth,
  and it is the one that matters most today.**
  `test/test_version/test_version.cpp`'s
  `Version.ThisBuildSaysThePinOfPlatformioIni` asserts the whole version
  string — `repeater-v1.17.1 (d9296435)` included — against what
  `platformio.ini`'s defines produce, and `tools/release/test_release.py`
  names the old tag in a synthetic `buildinfo.json`. So **every** bump is red
  in CI before a line of upstream's has been looked at, which turns tier one
  (a green bump a person merges) into tier two (a session) for free. This task
  did not change it: it is task 01's file, and this task's first acceptance
  criterion says nothing `tools/verify.ps1` runs changed. What it did instead
  is say so three times where it cannot be missed —
  `docs/upstream.md` (*What a bump costs today*, with the one-line
  alternative: assert against the `TWINOAK_MESHCORE_*` macros instead of the
  literals), `tasks/sync/TEMPLATE.md` step 2 (so the first bump is cheap even
  as a session), and `tasks/phase-0/FOLLOWUPS.md` tagged `[reviewer]`, because
  whether tier one should be reachable at all is a decision about task 01's
  test and not mine to take.
- **`tasks/sync/` needed nothing of the driver.** The task is written as if
  the sync phase were new; `tasks/run-all.ps1` already maps `-Phase sync` to
  `tasks\sync` in both places it names a phase directory, and already refuses
  to delete an `upstream/<tag>` branch. The `README.md`, `TEMPLATE.md` and
  `reports/` this task adds are the files that were missing, and the driver's
  two reads were run against them rather than assumed (checklist item 3).

## Decisions taken without asking

- **The bump's own commit writes the pin's history.** The task asks the page to
  record the pin's history; a history only a person remembers to update is one
  that rots, and a *green* bump is merged with no session anywhere near it. So
  `upstream.yml` rewrites `pin`/`tag` in `docs/upstream.md`'s opening block
  with the same `sed` it uses on `platformio.ini` — the two lines are
  identical in form — and inserts the history row under a marker comment,
  failing loudly if that marker is not there exactly once. The prose around the
  block names no version for the same reason, and `platformio.ini`'s comment
  above `[meshcore]`, which used to restate the tag, now says only that these
  are the two lines a bump moves. Those three comment lines are the whole of
  this task's `platformio.ini` diff.
- **The tag family is `repeater-v*` and nothing else.** MeshCore tags a release
  per example family; our `[meshcore].tag` is a repeater tag and the firmware
  is built from `examples/simple_repeater`, so a `companion-v*` release is not
  this repository's business. `new-sync-task.ps1` refuses one by name.
- **Upstream's URL is read from `platformio.ini`, not carried a second time.**
  `[meshcore].url` is where this repository says where MeshCore is; both
  scripts default to it, and the workflow reads it with one `sed` and hands it
  to the step that clones for the commit list. The agent firmware has the URL
  in the workflow's `env` and in the script's default parameter — two more
  places to forget.
- **`-Tag` resolves the pretended tag's own commit.** The agent firmware's
  script reports the *real* pin as `previous_sha` under `-Tag`, which would
  make a by-hand rehearsal's commit range the empty one it is pretending not
  to be in. Here `-Tag repeater-v1.17.0` reports `727fc051`, that tag's
  commit, and says on its first line that `platformio.ini` still says
  `d9296435`. The workflow does not rely on it — its rehearsal really rewinds
  the pin on a branch — but a person asking the question by hand gets a
  truthful answer.
- **Monday 06:29 UTC**, off the hour and off the two MeshMaster watchers'
  minutes (06:17 in `meshmaster-agent-firmware`, 06:41 in `meshmaster.dk`), so
  that three repositories asking GitHub the same question do not share a
  minute. Nothing else in this repository runs on a schedule.
- **The bump branch is pushed without `--force`; only the throwaway rehearsal
  base is forced.** The step before it has already established that
  `upstream/<tag>` is not on `origin`, so a push that is not a fast-forward
  means something else is there and the job should stop rather than overwrite
  it. The agent firmware forces both.
- **One open bump at a time, found by the `meshcore` label** — the agent
  firmware's rule and its label name and colour, so a bump looks the same in
  both repositories. If `upstream/<tag>` is on `origin`, the workflow says
  which pull request the open bump is and does nothing.
- **The workflow is the `gh` around a script, not a script in a workflow.**
  `tools/upstream-check.ps1` is the only thing that decides anything, which is
  what let its two paths be exercised on this machine before the file was on
  `main` at all, and is how Thomas can ask the question without a runner.
- **A sync report lands on `upstream/<tag>`**, not on a `task/...` branch:
  the branch and its pull request already exist, so the session edits the body
  (`gh pr edit --body-file`) rather than opening a second one.
  `tasks/sync/reports/README.md` says so, because `tasks/RUNBOOK.md` §4 is
  written for the usual case.
- **The template's step 1 is the pinned checkout, not the pull request body.**
  `CLAUDE.md` and `tasks/README.md` both say to read the firmware you build
  against; a sync task is exactly the task most tempted to trust a
  transcription, so the `git -C .pio/libdeps/repeater_rak4630_single/MeshCore
  log` line is in the file with the two real pins substituted into it.
- **`spec/` fixtures are named in the template as *not* ours to change.** A
  bump whose compiler error would go away if a fixture moved is tier three
  (MeshMaster first) and a finding, and the template says so rather than
  leaving a session to discover `spec/README.md` under pressure.
- **The `.ps1` files are ASCII**, as this repository's other three are:
  Windows PowerShell 5.1 reads a BOM-less UTF-8 script as the ANSI codepage,
  and an em dash in a string is a parse error before it is anything else. The
  markdown they *write* is the repository's usual prose.
- **`docs/bench.md` gets one line under *0. Before the rig*** — the first
  Monday and the first real bump. Neither needs the rig, but task 02 put the
  release key there for the same reason: it is the list of what no session
  could check.

## Not verified here (and why)

- **The weekly schedule has not fired.** The two dispatches prove the job;
  what only a Monday can prove is that `cron: "29 6 * * 1"` is a minute GitHub
  actually runs this workflow at. `docs/bench.md` §0 has the line.
- **No real newer tag exists.** MeshCore's newest `repeater-v*` is
  `repeater-v1.17.1`, which is the pin, so the "something newer" path has only
  ever been walked by the rehearsal input — which is what that input is for.
  **A real bump has not happened, and the first one that does is the test of
  `tasks/sync/TEMPLATE.md`**: it will be red for the reason in the second
  deviation above before it is red for anything of upstream's.
- **`tools/new-sync-task.ps1` has never been run against a real red bump.** It
  was run against a synthetic tag and a throwaway commit, with `-Commit` so
  that nothing was resolved over the network, and against the three refusals.
  What is unproven is only the shape of a real failing job's log in the
  `{{LOG}}` block, which is a paste.
- **The *Approve and run* click.** The pull request a real bump opens is
  `github-actions[bot]`'s, and GitHub holds workflows on such a pull request
  rather than starting them. `docs/upstream.md` says so and gives the
  `gh api … /approve` line; what this session can say about it is in the
  rehearsal's own checklist item, and it is the agent firmware's finding
  before it is this repository's.
- **Nothing was flashed and no radio was heard** — this task touches no image.
  Phase 0's two earlier lines in `docs/bench.md` §0 still stand unchanged.
