# p0-01 — the-toolchain

`pio run` builds MeshCore's stock `simple_repeater` for the RAK4630 from the
pinned dependency — `repeater-v1.17.1`, `d9296435`, not one file of upstream's
edited — as the environment `repeater_rak4630_single`; `pio test -e native`
runs the first native test; `tools/verify.ps1` is what *verified* means from
here on, and CI runs it and nothing else. Done in one session.

## The three decisions every later task inherits

1. **How MeshCore is consumed on an nRF52.** As a PlatformIO library at one
   commit (`[meshcore]` in `platformio.ini`), with `-D MC_VARIANT=rak4631` and
   `-D BUILD_EXAMPLE=simple_repeater` telling upstream's `build_as_lib.py`
   which of its own sources to compile. Upstream's flag blocks are copied into
   our `platformio.ini` with their source named; what a consumer cannot reach
   is reached by two scripts under `tools/pio/` that read the pinned checkout
   and raise if a bump moves what they reach for. One file is vendored,
   `boards/rak4631.json`, and `boards/README.md` says why. The whole list of
   what a consumer does not get for free is below.
2. **How the board is named.** `<role>_<board>`: `repeater_rak4630_single`.
   `tools/verify.ps1` reads every `[env:*]` but `native` from `platformio.ini`
   and builds each; adding a role or a board is one section, no second list.
   The environment carries `TWINOAK_ROLE` and `TWINOAK_BOARD` as string
   defines for the descriptor phase 3 adds, beside `TWINOAK_MESHCORE_TAG` and
   `TWINOAK_MESHCORE_PIN`, which move with the pin and never by hand.
3. **What "verified" means.** `tools/verify.ps1`: spec against its manifest,
   the link fixture, every board environment's build (images copied to
   `out/build/<env>/`), the native tests — with this machine's `g++` when
   there is one, otherwise in the `python:3.11-slim` container of RUNBOOK §2.
   One log per step under `out/verify/`, one summary line per step, non-zero
   exit on any failure, `-Only <step>` for one of them. CI (`verify` job) is
   `pwsh tools/verify.ps1` with PlatformIO Core pinned to this machine's
   `6.2.0`; the only steps beside it are a size summary and the artifact.

## What a package consumer does not get on an nRF52, and how each was arranged

The agent firmware's bootstrap report (meshmaster.dk `tasks/phase-4.2/reports/65.md`)
found three things on ESP32; the nRF52 adds five.

| | What upstream has that the package does not give | Arranged by |
|---|---|---|
| 1 | **The flag blocks.** `[arduino_base]`, `[nrf52_base]`, `[sensor_base]` and `variants/rak4631/platformio.ini` use paths relative to MeshCore's root (`-I variants/rak4631`, `extra_scripts = create-uf2.py`, `post:variants/rak4631/fix_bsec_lib.py`) and cannot be included. | Copied into `platformio.ini` with the source section named, as the agent firmware does; a pin bump re-reads them. |
| 2 | **`lib/ed25519`**, a private library of upstream's project; `Identity.cpp` fails with `ed_25519.h: No such file` without it, and `lib_extra_dirs` cannot reach into a dependency. | `tools/pio/meshcore_private_libs.py` (the agent firmware's, unchanged in what it does) compiles it out of the pinned checkout; `-I ${meshcore.dir}/lib/ed25519` beside it. Raises if the pin moves the directory. |
| 3 | **Exact library versions.** `library.json` and `platformio.ini` ask with ranges; `helpers/sensors` is in `build_as_lib.py`'s filter unconditionally, so the fifteen sensor libraries are not optional. | `[libs]`, every one exact: the agent firmware's resolved list at the same pin, plus `CustomLFS` at upstream's own tag. RadioLib is the registry's `7.8.0` and not upstream's git commit, for the agent firmware's reason (two libraries for one `RadioLib.h`). And **our pins come first in `lib_deps`**, MeshCore after them: the other way round, PlatformIO resolved MeshCore's `^7.6.0` to a second, unused `RadioLib@7.8.1` directory beside ours (seen on the first build; one directory after the reorder, `pio pkg install` log). |
| 4 | **`boards/rak4631.json`.** PlatformIO reads `boards_dir` before it clones a dependency, so `board = rak4631` cannot name a file inside MeshCore. | Vendored byte for byte (SHA-256 `1ec1da4a…` equals `git show <pin>:boards/rak4631.json`'s); `boards/README.md`; `.gitattributes` keeps git from touching a line ending in it. The one file of upstream's in this repository. The Arduino variant it names (`WisCore_RAK4631_Board`) is the core's; MeshCore's own `variants/rak4631/variant.{h,cpp}` — the same pin map plus the LoRa pin defines its board object needs — is reached by `-I` and compiled into the MeshCore library by `MC_VARIANT`. |
| 5 | **The Adafruit nRF52 core fork** at the commit upstream pins (`meshcore-dev/Adafruit_nRF52_Arduino#d541301`). | Nothing special: `platform_packages` is a project-level setting, so the consumer pins the same URL and commit (`framework-arduinoadafruitnrf52@1.10701.0+sha.d5413016` in the build log). NoiseScope in the hardware repository pins the same commit. |
| 6 | **The UF2.** Upstream's `create-uf2.py` is a custom target reading `$PROJECT_DIR/bin/uf2conv/uf2conv.py`; a consumer's project has no `bin/`, and a script inside a dependency cannot be named in `extra_scripts`. | `tools/pio/meshcore_uf2.py`: a post-action on `firmware.hex` that runs `uf2conv.py` out of the pinned checkout with the same family id, on every build rather than a target to remember. Raises if the pin moves the converter. |
| 7 | **The DFU package.** Upstream's board definition says `"protocol": "nrfutil"`, and the nordicnrf52 platform builds `firmware.zip` with `tool-adafruit-nrfutil` by itself for such a board. | Free, because the vendored board definition carries the protocol; `tools/verify.ps1` checks the file is there. |
| 8 | **Two `variant.cpp`s.** `MC_VARIANT=rak4631` compiles MeshCore's `variants/rak4631/variant.cpp` into the MeshCore library while the framework compiles the core's `WisCore_RAK4631_Board/variant.cpp` into its own: `g_ADigitalPinMap` and `initVariant` twice, in two archives. | Nothing to do: the linker takes the first archive that resolves each symbol and never opens the other's object, and the two pin maps are identical (compared at the pin). Upstream's own build has the same pair. Noted so that a pin bump that changes one of them is read with this in mind. |
| 9 | **`-w`** in `[arduino_base]`, which would silence our `-Werror`. | Left out (`platformio.ini` says why); upstream's sources then print 270 warning lines on this toolchain (`-Wreorder` 186, `-Wformat=` 29, `-Wsign-compare` 24, `-Wunused-variable` 14, …; `out/build-first.log`), none from `src/`, which is strict. |
| 10 | **Two linker scripts of upstream's own** (`boards/nrf52840_s140_v6_extrafs.ld`, `…_v6.ld`), named root-relative by its companion environments. | Not needed: the repeater environment uses the core's `nrf52840_s140_v6.ld` from the board definition. An environment that wants upstream's (`EXTRAFS` with a larger file system) would have to vendor it; phase 0's task 02 reads the application region from the script the build used, whichever it is. |

## Deviations from the spec or the task

- **Two more things left out of upstream's RAK4631 flag block than the task
  listed**, each with a comment in `platformio.ini`: `ENV_INCLUDE_BME680_BSEC`
  with its `-UENV_INCLUDE_BME680` and `fix_bsec_lib.py` (Bosch's binary BSEC
  library needs upstream's root-relative post-script to link, and the unit has
  a BME280; the open Adafruit BME680 driver of `[sensor_base]` is compiled
  instead, as in the agent firmware), and `ENV_INCLUDE_RAK12035` (a WisBlock
  soil-moisture sensor; its driver still compiles because `helpers/sensors` is
  unconditional). The task's own list — `-w`, `MESH_PACKET_LOGGING`,
  `MESH_DEBUG`, the display class, the GPS — is left out as asked; leaving the
  GPS out also drops the SparkFun u-blox GNSS library the RAK GPS path pulls.
- **`ADMIN_PASSWORD` is not defined, and the image still has upstream's
  default.** `examples/simple_repeater/MyMesh.cpp:32` at the pin defaults it
  to `"password"` when the define is absent, so the stock image of this phase
  carries a default password (`spec/SYSTEM.md` S-13 says none ever on the
  air). It is upstream's example compiled unmodified, nothing is flashed, and
  phase 3's first-boot provisioning is where S-13 is met; `docs/bench.md`
  says so beside the image.
- **`src/version.{h,cpp}` is where the task put it; `docs/ARCHITECTURE.md`
  §1 puts the version string under `src/app/`.** The task's deliverable list
  is explicit, so the file is at `src/version.{h,cpp}` and `[env:native]`'s
  filter names it there; phase 1's task 01, which creates `src/app/`, can
  move it in the same commit that first calls it.
- **`tools/verify.ps1` was run under Windows PowerShell 5.1 here, not
  `pwsh`** — this machine has no `pwsh`. The script is written for both (no
  `&&`, no ternary, no `??`); CI is where `pwsh` runs it, and that run is in
  the checklist.
- **PlatformIO Core is `6.2.0`** here and therefore in CI; the agent
  firmware pinned `6.1.19`. The task says the version this machine runs.

## Decisions taken without asking

- **The nordicnrf52 platform is pinned** (`platformio/nordicnrf52@11.0.0`,
  the newest release on the day of the first build; upstream says
  `nordicnrf52` with no version). Every other dependency here is exact and
  the toolchain it resolves (`toolchain-gccarmnoneeabi@1.70201.0`,
  `tool-adafruit-nrfutil@1.503.0`) is part of the build.
- **The channel's CR and power are in the environment, the frequency, the
  bandwidth and the SF in `[nrf52_base]`** — where upstream's `[arduino_base]`
  has them. `LORA_CR=8` is added: upstream's RAK block does not set it and
  MeshCore's default is not the Danish channel's.
- **`TWINOAK_ROLE` and `TWINOAK_BOARD`** are defined as strings in the
  environment, beside the two `TWINOAK_MESHCORE_*` defines the version
  string needs. Nothing reads them yet; the descriptor (phase 3) and the
  manifest (task 02) will, and an environment that is `<role>_<board>` by
  name should say so to the compiler too.
- **The images are copied to `out/build/<env>/`** by the build step, and the
  step fails if one of the four is missing, so "the build output includes an
  image" is held by the script and not by the eye. CI's artifact is
  `out/build/` plus `out/verify/`.
- **`-Only` takes a step name** (`spec`, `link`, `build`, `native`) and
  nothing finer; `build` builds every environment.
- **Python is the one PlatformIO runs on**, read from `pio system info`'s
  `Python Executable` line, with `python3`/`python` on PATH as the fallback.
  On this machine that is `~/.platformio/penv/Scripts/python.exe`
  (3.11.7); in CI, the `setup-python` 3.11 that `pip install platformio` went
  into. `pio` itself is found the way `tasks/run-all.ps1`'s preflight finds
  it when it is not on PATH.
- **The container run pins the same PlatformIO version as the host's**
  (`pip install platformio==<pio --version>`), so the native step is the same
  step in both places; `DEBIAN_FRONTEND=noninteractive` and the pip
  root-user notice are silenced because they are noise in a log.
- **The CI job is named `verify`**, which is the status check the branch
  protection requires; the artifact is `firmware-<sha>`.
- **`docs/bench.md` is started** with the section order of
  `spec/SYSTEM.md` §7 and the headings phase 1's tasks name, and this task's
  two lines under "Before the rig".
- **No `docs/upstream.md` yet** — task 03 writes it; the comments in
  `platformio.ini` and `tools/pio/*.py` already point at it as the place a
  bump re-reads.

## New libraries (with the one-line justification)

All of them MeshCore's own dependencies at the pin, exact rather than ranged
because a firmware build has to be reproducible:

- `jgromes/RadioLib @ 7.8.0` — the SX1262 driver; the registry release in
  MeshCore's `^7.6.0` range rather than its git commit, for the reason in `[libs]`.
- `rweather/Crypto @ 0.4.0` — Ed25519 and SHA-256 for identities and packets.
- `adafruit/RTClib @ 2.1.4`, `melopero/Melopero RV3028 @ 1.2.0` — MeshCore's clock helpers, compiled whether a board has an RTC or not.
- `electroniccats/CayenneLPP @ 1.6.1` — the telemetry encoding of its sensor helpers.
- `adafruit/Adafruit BusIO @ 1.17.4`, `bblanchon/ArduinoJson @ 7.4.3` — transitive, declared because upstream asks for them with `*`.
- `oltaco/CustomLFS` at tag `0.2.3` — `[nrf52_base]`'s file system (`EXTRAFS=1`); upstream's own pin, a tag, already exact.
- fifteen sensor libraries (`Adafruit AHTX0/BME280/BMP280/BMP085/BME680/SHTC3/INA219/INA260/INA3221/MLX90614/_VL53L0X`, `robtillaart/INA226`, `Sensirion I2C SHT4x`, `Arduino_LPS22HB`, `MicroNMEA`) — `build_as_lib.py` compiles `helpers/sensors` into every build, so they are not optional.
- `google/googletest @ 1.17.0` — the native tests; the framework MeshCore's own `test/` uses.

Seven more directories land in `.pio/libdeps/` by those libraries' own
manifests (`Adafruit GFX`, `SSD1306`, `SH110X`, `NeoPixel`, `Unified Sensor`,
`Sensirion Core`, `Unity`); none is named in `lib_deps` and none appears in
the dependency graph of the build. The agent firmware has the same seven.

Platform packages, pinned in `platformio.ini`: `platformio/nordicnrf52@11.0.0`
and `framework-arduinoadafruitnrf52` at `meshcore-dev/Adafruit_nRF52_Arduino#d541301`.

## Not verified here (and why)

- **Nothing was flashed and no radio was heard.** The image is upstream's
  stock repeater with our channel; the first thing worth flashing is phase
  1's. If it is flashed anyway, `docs/bench.md` "0. Before the rig" says what
  to expect.
- **The UF2 on a bootloader drive and the DFU `.zip` through
  `adafruit-nrfutil dfu serial`** were produced, not consumed: both are made
  by the tools upstream and the platform use for the same board, and the UF2
  reports the application start `0x26000`, but no board took them.
- **Branch protection on `main` needed no human**: `gh api -X PUT
  …/branches/main/protection` was accepted and reads back as asked — a pull
  request required with 0 approvals, `enforce_admins` false, no force pushes,
  no deletions, the `verify` check required with `strict: false` (a merge
  does not need the branch rebased first), as the agent firmware has it. What
  is not verified is only that GitHub enforces it on the next direct push,
  which the driver's notes commit will show.
- **The container path of `tools/verify.ps1` ran only on this machine; the
  host-compiler path only in CI.** Each ran where it applies; the same
  PlatformIO version and the same test ran in both, and both are in the logs.
- **The weekly cache in CI** (`actions/cache` keyed on `platformio.ini`) was
  exercised once, cold; its hit path is seen on the next run.
