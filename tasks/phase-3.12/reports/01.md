# p3.12-01 — humidity-and-pressure

Channel 5 of this unit's telemetry now carries the enclosure's **humidity and pressure beside its
temperature**, in a mesh reply and in `LPP_GET` alike. The sentence that kept them off the air for
a year — *CayenneLPP 1.6.1 cannot encode humidity or pressure* — was wrong, and it is corrected
where it stands, with a test that links the library so that no claim about it has to be believed
again.

**The library, first (deliverable 1).** The gate `tasks/phase-1/reports/06.md` read is a `switch`
whose cases fall through to one `return true`, and every case sits behind
`#ifndef CAYENNE_DISABLE_<type>`:

```c++
#ifndef CAYENNE_DISABLE_RELATIVE_HUMIDITY
    case LPP_RELATIVE_HUMIDITY:
#endif
...
#ifndef CAYENNE_DISABLE_BAROMETRIC_PRESSUE
    case LPP_BAROMETRIC_PRESSURE:
#endif
```

(`.pio/libdeps/repeater_rak4630_single/CayenneLPP/src/CayenneLPP.cpp:53-140`, version 1.6.1.) The
list in report 06 is the cases that can be seen without reading the `#ifdef` lines; the gate in
fact names **every** type the header names, and `grep -rn CAYENNE_DISABLE platformio.ini src/
.pio/libdeps/*/MeshCore/` finds nothing. Built for the host and run:

```
isType: hum=1 pre=1 pow=1
hum ret=3
pre ret=7
size=7 bytes=0568a205732794
error=0
sizes: hum=1 pre=2 mults: hum=2 pre=10 signed: hum=0 pre=0
```

(`out/p3.12-01/probe.cpp`; the same bytes are now `test/test_cayennelpp`'s first case.) So neither
type is refused, nothing had to be written by hand around the library, and `addPower` would have
worked too — it stays out by choice (deliverable 5).

**What the wire carries now.** `ourFields()` pushes the humidity after channel 5's temperature and
the pressure after that, each only while its validity bit is set, each the number `ENV_GET` reports
converted into the unit its type takes — percent for type 104, hectopascal for type 115, which is
the unit upstream's own `query_bme280` hands the library (`readPressure() / 100`,
`EnvironmentSensorManager.cpp:286`, `query_bme280`, at the pin `81dbae59`). The seven new bytes, from the real link
loop:

```
LPP_GET perm_mask 0x05 (base, environment)
  97 byte(s): 01740190 02740711 02750078 03740190 0375ffcc 0474018e 04750055 0567ffdd
              0568a2 05732794 066400002edf … 0e6400000e0f 016700d4
  channel 5  enclosure  temperature           -3.500 C
  channel 5  enclosure  humidity              81.000 %
  channel 5  enclosure  pressure            1013.200 hPa
```

(`out/p3.12-01/linkloop.log`; the hex is one string in the log, split here to show the fields.)
Both new types are **unsigned** and both truncate, so `81.25 %RH` reads back as `81.0 %` and
`101 325 Pa` as `1013.2 hPa`: at or below what `ENV_GET` says, by less than one step, never above
it. `ENV_GET` is still where the full precision is, and `docs/link.md` §2d now says so.

### Deliverable 3, what it costs

**Bytes.** The Cayenne-LPP goes from **90 to 97** — three for the one-byte humidity, four for the
two-byte pressure — against a `kMeshLppCap` of 180, with 83 bytes free. The frame around it is
MeshCore's, computed with its own arithmetic and not a formula from memory
(`out/p3.12-01/airtime.py`, which reproduces p3.10-02's own two rows exactly, which is what says
the script is right): `MyMesh.cpp`'s `4 + tlen`, `Utils::encrypt`'s zero-pad to
`CIPHER_BLOCK_SIZE` 16, `encryptThenMAC`'s `CIPHER_MAC_SIZE` 2, `Mesh::createDatagram`'s two
one-byte hashes, then `Packet::writeTo`'s header and path-length bytes:

| | LPP | reply data | encrypted payload | **on air, zero hops** |
|---|---:|---:|---:|---:|
| v0.1.2 | 36 | 40 | 52 | **54 bytes** |
| v0.1.3 / v0.1.4 | 90 | 94 | 100 | **102 bytes** |
| this | 97 | 101 | 116 | **118 bytes** |

**Seven bytes of LPP cost sixteen on air, and the reason is the cipher.** 94 bytes of reply data
fit in six 16-byte blocks; 101 need seven. So the padding is **11 bytes where it was 2**: 90 bytes
of LPP sat two below a block boundary and 97 is five past it. Each byte of returned path adds one
more byte to the frame.

**Airtime at SF8, 62.5 kHz, CR 4/8** — the Danish channel (`[band_868]`) — with
`SX126x::calculateTimeOnAir` (RadioLib 7.8.0, on disk), the **32-symbol preamble** MeshCore sets
for SF ≤ 8 (`RadioLibWrappers.h:56`, `preambleLengthForSF`), explicit header, CRC on and
`ldrOptimize` 0. Symbol time 4096 µs, `bitCount = 8·len + 12`, `nSymbol×4 = 177 + 32·ceil(bitCount/32)`:

| | frame | coded blocks | **airtime** |
|---|---:|---:|---:|
| v0.1.2 | 54 bytes | 14 | **640.0 ms** |
| v0.1.3 / v0.1.4 | 102 bytes | 26 | **1033.2 ms** |
| this | 118 bytes | 30 | **1164.3 ms** |

**+131 ms, +12.7 % on v0.1.4** (and +82 % on v0.1.2). Well under the cap either way: 118 bytes
on air against `MAX_PACKET_PAYLOAD` 184, and `createDatagram`'s own guard passes with room —
`101 + CIPHER_MAC_SIZE + CIPHER_BLOCK_SIZE-1` is 118, against 184. At the band's 10 % duty cycle a
1164 ms reply buys 10.5 s of silence after it instead of 9.3; telemetry is asked for hourly, so
the cost against the
window goes from 0.0287 % of the hour to **0.0323 %**. This stays the most expensive single packet
this firmware sends, and the 83 free bytes of the LPP buffer are now worth less than they look:
the next eleven bytes are free and the twelfth pays for a whole cipher block.

## Deviations from the spec or the task

- **CayenneLPP is now a dependency of `[env:native]`, and two settings are what that costs.** The
  task asks for a host test that uses the library; the library had never been compiled for the host
  here, and p3.10-02 recorded that as the reason its mirror was asserted and not linked. It
  compiles cleanly — but two things had to be said in `platformio.ini`'s `[env:native]`, both
  commented there and neither reaching a board environment:
  - `lib_compat_mode = off`, because the library's `library.json` declares frameworks `arduino`
    and `espidf` and PlatformIO's `soft` default would skip it for `platform = native`. Its own
    sources are framework-free on the `#ifndef ARDUINO` path, which is the path this environment
    compiles;
  - `-include cstdint`, because `CayenneLPPPolyline.cpp` — the non-Arduino polyline codec, which
    nothing here calls but `CayenneLPP`'s constructor must link — includes only `<utility>` and
    `<vector>` and then uses `uint8_t`. As its own translation unit it needs the header its own
    header assumes somebody else included. **Not an edit to the library**, and harmless to every
    other native translation unit.
- **Report 06's wrong section is left standing, with a dated note above it.** The task asks for
  that and `tasks/README.md`'s *leave the evidence* is why: a report is what was thought at the
  time. The note says what was misread — the `#ifndef CAYENNE_DISABLE_*` lines between the cases —
  and where the truth now lives. Two further sentences of that report say the same thing in other
  sections (its *Not verified here* and its *Deviations*); they are its own text and are left as
  they are, because the dated note at the head of the section the task names covers the claim and
  the page that a person actually reads — `docs/bench.md` — is corrected in place.
- **`test/test_power`'s "a type nothing here knows" case had to change its example.** It used
  type 104 and said CayenneLPP refuses it. It now uses `LPP_POWER` (128) and says the true thing:
  the library encodes it, the **mirror's table** does not have a row for it, and that is deliberate
  (deliverable 5) — so a field of a type nobody added to `kTypes` is dropped rather than
  mis-encoded.
- **One expectation of that same test was wrong about the new shape and is now right.** At a cap of
  three bytes the reply used to encode nothing; it now encodes the one-byte humidity, because that
  is the only field of the list that fits in three bytes and the library's overflow check is per
  field and does not stop the walk. The test says so, and `test_cayennelpp` holds the same ten caps
  against the library.
- **`docs/bench.md` §5's `p1-06` env line said the opposite of the truth, so it is corrected and
  not only added to.** A new `p3.12-01` line (**5.3a**) carries the mesh half — a phone and
  meshmaster.dk — and the page is 121 lines where it was 120, which `README.md` now says.
  `tools/bench/walk.py` gained the matching `PageLine` because `bench walk 5` enumerates every
  bullet of its section (`test_walk`'s
  `test_every_bullet_of_a_walked_section_is_a_line_of_its_walk`), and the line is *needs a person*:
  no session can read a phone.

## Decisions taken without asking

- **Hectopascal and not pascal, because that is what the type means.** `LPP_BAROMETRIC_PRESSURE`'s
  multiplier is 10 and its unit is 0.1 hPa, so the float handed to it has to be hectopascal.
  `ENV_GET` keeps pascal, where the protocol put it. Upstream's own BME280 does the same division
  (`readPressure() / 100`), which is the thing to copy rather than invent.
- **The order inside channel 5 is `ENV_GET`'s order**: temperature, humidity, pressure. Nothing
  requires an order inside a channel, and the one the box link already uses is the one a reader of
  both will expect.
- **`EnvReadings` gained `humidityValid()` and `pressureValid()`** beside the `temperatureValid()`
  it already had, rather than `ourFields()` testing the bits by hand. Three quantities, three
  accessors; the bit constants are still the single source and `LinkPower.h` still
  `static_assert`s them against the link's own.
- **`kMaxLppFields` is 20 and not more.** It was 18 and is exactly the longest list again, and
  `test_power` asserts `telemetryFields(...) == kMaxLppFields` rather than `<=` — p3.10-02's own
  choice, kept, so that a twenty-first field added without raising the bound is a red test and not
  a channel silently missing from the wire.
- **`test_cayennelpp` transcribes `BoardPower.cpp`'s `switch`.** The one place the library is
  really driven lives in a file that needs a board, so the test has its own copy of those six
  cases. The copy is eight lines, it is commented as a copy, and a type added to `kTypes` and to
  one switch but not the other shows up as a dropped field in
  `WritesWhatTheLibraryWritesFieldByField` rather than as silence.
- **`LPP_POWER` stays out**, as the task asks, and the mirror's table is the thing that keeps it
  out. Said plainly in `Telemetry.cpp`'s comment and in `docs/link.md` so that the next reader does
  not think it is another oversight.

## New libraries (with the one-line justification)

None. `electroniccats/CayenneLPP @ 1.6.1` is already a pinned dependency of every board build
(`[libs].core`); this task adds the **same exact version** to `[env:native]`'s `lib_deps` so that a
host test can hold the mirror against the real thing, which is cheaper than another transcription
of it.

## Not verified here (and why)

No session opens a port, and no session can hear a radio. Both lines are in `docs/bench.md` §5 in
the order the rig is brought up; the first is `p1-06`'s, corrected by this task, and the second is
new as **5.3a**. Neither is a `bench walk` step: the walk of §5 is the two threshold lines, and
these two need a thermometer, a phone and a browser.

- **`linkcli.py env` against a thermometer, and all three readings on LPP channel 5**
  (`docs/bench.md` §5, `p1-06`). The page said the humidity and the pressure *deliberately* were
  not on channel 5. They are now; the line says so and still needs a BME280 on the bus and
  something trustworthy to compare the three numbers with.
- **The enclosure's three readings as a mesh reader gets them** (`docs/bench.md` §5, **5.3a**, new).
  `linkcli.py lpp` must print `channel 5` three times, each **floored** to its type's step — a
  tenth of a degree, half a per cent, a tenth of a hectopascal — so `81.25 %RH` on the link reads
  `81.0 %` in the LPP and `101 325 Pa` reads `1013.2 hPa`; a number *above* `env`'s, or more than
  one step below it, is a finding. Then the same from a phone's telemetry view of the repeater, and
  then on meshmaster.dk's page for the unit, where channel 5 is one chart today and must become
  three. The reply is 97 bytes of Cayenne-LPP where v0.1.4 sent 90, which is 118 bytes on air and
  1164 ms at SF8: long enough to be worth a glance on a busy channel and far inside the duty cycle.
  **No phone has ever read this node's telemetry**, which is the older half of the same line.
- **The airtime above is arithmetic and not a measurement**, as p3.10-02's was: it is RadioLib's
  own `calculateTimeOnAir` with this band's five numbers and MeshCore's preamble, run on this
  machine. A scope or a second radio timing the reply is the bench's.
