# p3.12-02 — The release says what is left

On 13 November the button published v0.1.4 and told Thomas it had failed. Nothing had: `main`
asks for the `verify` check, so the job cannot merge the pull request that files the notes, and
the step ended `exit 1` over it. The pull request's body then said *No check runs on this pull
request*, which is not what happens either — GitHub **does** start a `ci` run for it and holds it
for a maintainer's approval, and an hour later that held run was listed as failed, which is the
second red run of the evening.

So: a release that published is a green run that names the one pull request left to merge, that
pull request says what is true about its check, and both sentences come out of one tested place.

### How the step ends, in one place

`tools/release/notes_pr.py`: pushed or not, opened or not, merged or not, and what the run knows
(the tag, the branch, the pull request) in; the exit code and the one line that is both the top of
the run's summary and the job's annotation, out. The step has one `exit` of its own — the commit
that the move has just made failing to commit at all, which is a fault and not something waiting
for a person — and otherwise asks that module.

Four ways out, each tested: not pushed (red), opened but not pushed… that is not a state; pushed
but not opened (red), pushed and opened and not merged (**green**, the ordinary end of a release
today), merged (green). The Walter firmware's `release.yml` is the model for ending green — its
`waiting()` ends green for the push and the open failures as well, and the task asks for those two
to stay red here, because nothing is waiting for a person when there is no pull request.

## Deviations from the spec or the task

- **The same untrue sentence was in two more places, and is corrected where it stands.**
  `docs/release.md` said *GitHub starts no workflow from an event raised with the job's own token*
  twice, and `gate.py`'s docstring (with the class comment of `TheCiRunThatStandsForACommit`) said
  it of a push and a pull request both. A push raised with that token does start nothing; a pull
  request raised with it starts a run that is held for approval. The three places now say that,
  and `gate.py`'s walk is unchanged — it is the fallback for a commit that has no run, which is
  still a commit it can meet.
- Nothing else. `spec/` has no word about the release workflow; `spec/FIRMWARE-MANIFEST.md` is
  about what a release carries, which this task does not touch.

## Decisions taken without asking

- **The decision lives in a new module, `tools/release/notes_pr.py`, and it writes the body too.**
  The alternative was a function in `release_notes.py`, which is about the lines a task leaves;
  the pull request those lines are filed in, what it says and how the step ends are one small
  subject, read together, and `release.yml` now calls that one file twice (`body`, `outcome`).
- **The three merge attempts stay.** All three are refused while `main` asks for `verify` (20
  seconds of sleeps on each release), and they are what finishes the job by itself on the day
  Thomas changes that rule. The follow-up where he decides is phase 3.12's.
- **The one line is also the job's annotation** (`::notice::` green, `::error::` red), so the run's
  own list says what the summary says.
- **The body does not say why GitHub holds the run.** That it is held for a maintainer's approval
  is what was seen; the rule behind it is GitHub's and could change under us, and the two ways to
  finish do not depend on it.
- **Nothing to commit after the move is red**, with no summary line of its own: the move has just
  written `VERSION` and `release-notes/`, so an empty commit means the tooling is wrong rather
  than that something is waiting for a person.
