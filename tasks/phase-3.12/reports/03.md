# p3.12-03 — CI where a public repository may run

Every job of every workflow here runs on a GitHub-hosted runner, and
`tools/ci/check-runners.ps1` refuses a self-hosted one anywhere in
`.github/workflows/`.

This repository became public on 13 November 2026, between 16:05 and 16:52 UTC.
The organisation's one runner group is *All repositories, **excluding** public
repositories*, so from that hour no job of `ci` or `upstream` was given a
runner: runs queued, the required `verify` check never reported, and nothing
could be merged — including task 01 of this pile, which is finished and waits as
[#51](https://github.com/twinoak/twinoak.meshcore.repeater-firmware/pull/51).
The group's setting is right and stays right. What was wrong is where the
workflows asked to run.

The rule is the exit-node firmware's, which has been public longer and took it
in its task p1.8-29: **every job on a GitHub-hosted runner**, one rule and no
file that is special, for two reasons that both come of the same fact.

- **Running here costs nothing.** [Actions on standard GitHub-hosted runners are
  free in a public repository](https://docs.github.com/en/actions/concepts/billing-and-usage).
  The minutes that got out of hand in October 2026 — the premise of
  `tasks/phase-3.6/01-built-at-home.md` — are the *private* repositories', and
  theirs is the CI that rightly runs at home.
- **On a public repository a self-hosted runner runs a stranger's code.** Anyone
  may fork and open a pull request, a pull request can change a workflow file,
  and it would then run on the Unraid host with its docker socket, its LAN and
  its Tailscale. GitHub's own words: self-hosted runners
  [*"should almost never be used for public repositories"*](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions#hardening-for-self-hosted-runners).

| Workflow | Job | Before | Now |
|---|---|---|---|
| `ci.yml` | `verify` | `[self-hosted, unraid]` | `ubuntu-latest` |
| `upstream.yml` | `bump` | `[self-hosted, unraid]` | `ubuntu-latest` |
| `release.yml` | `ci-green`, `build`, `publish` | `ubuntu-latest`, *what ships stays away* | `ubuntu-latest`, *a public repository* |

The job is still called `verify`, so `main`'s required check is the one it
reports. Nothing under `src/`, `lib/`, `test/` or `spec/` is touched: the diff is
three workflow files, one script in `tools/`, the README, `docs/release.md`,
`docs/upstream.md`, `keys/README.md` and this report.

### What `ci.yml` keeps of the months it ran at home, and what it loses

Deliverable 3, said plainly.

| Step | Verdict | Why |
|---|---|---|
| *Nothing of the last job is left in the workspace* (`.pio/`, `out/`) | **removed** | It existed because a self-hosted runner keeps its workspace from one job to the next and the branch that ran there last was somebody else's task. A hosted runner is a machine that did not exist a minute ago; there is no other branch's build output to find, and a step that can only ever pass is not a guard |
| *installing* `g++ git curl tar` with `apt-get` when they are missing | **removed** | `actions/runner-images` carries all of them. The `apt-get` path was for the thinner Unraid image, and on a hosted runner it is dead code that would also silently paper over an image change |
| *checking* that `g++ git curl tar bash pwsh` are there | **kept** | `g++` decides where the work happens: `tools/verify.ps1` runs the native tests and the link loop with the host compiler when there is one and in a `python:3.11-slim` container when there is not — seven minutes against one in this run. If GitHub's image ever drops it, this step fails by name instead of the run going slow and quiet |
| the runner written into the step summary | **kept** | Which machine ran it is the one thing about a hosted run worth recording, and it is how this report's table was filled |
| `if: runner.environment == 'github-hosted'` on *Cache PlatformIO* | **removed (the cache stays)** | Every job is hosted now, so the condition is always true. The cache is what makes a hosted run of this job five minutes rather than a cold one |
| `$RUNNER_TEMP` in `upstream.yml` instead of a fixed `/tmp` path | **kept** | The one real find of p3.6-01 and right on either kind of runner: it is per-job and emptied when the job starts, which is exactly what `/tmp` was being trusted for |
| `permissions`, the concurrency group, one run per commit, the artifact | **kept, untouched** | Nothing to do with where a job runs |

## Decisions taken without asking

- **The rule is "every job runs on a GitHub-hosted runner", not "no job carries
  the `self-hosted` label".** The deliverable asks for the second; the first is
  that refusal plus one more, and the extra one matters. GitHub adds
  `self-hosted` to a self-hosted runner's labels of its own accord, but a
  workflow may *address* that runner by any of its labels — `runs-on: unraid`
  reaches the Unraid containers with no `self-hosted` written anywhere, and the
  old rule would have accepted it in `release.yml`. So the check is: exactly one
  label, beginning `ubuntu-`, `windows-`, `macos-` or `macOS-`. A `self-hosted`
  label gets the named sentence; anything else that is not a hosted label is
  told that if it is a self-hosted runner under its own label the rule is the
  same. This is the exit node's decision, taken for the same reason.
- **Three more refusals, none of them asked for, each the rule being worth
  having:** a `runs-on` that is an expression (`${{ vars.RUNNER }}` — where a
  job runs is not something to decide at run time, and this guard cannot see
  what it evaluates to), a job with no `runs-on` at all, and a workflow file the
  reader found no job in (a rule that could not be applied has not been passed).
  The one admitted exception is a job whose work is a reusable workflow (`uses:`
  at the job level), which by YAML's rules has no `runs-on` of its own; it was
  already allowed and is now a self-test case, so the day that changes a test
  says so.
- **`$ships` is gone.** One rule, every file, and `release.yml` identified by
  nothing. The self-test keeps *"release.yml at home, which is no different"* and
  *"upstream.yml at home, which is no different either"*, so the day somebody
  reintroduces an exception, a test says what changed.
- **The planted failure is `-Dir` over copies, not a scratch commit pushed to
  CI.** p3.6-01 and the exit node's p1.8-29 both pushed a scratch commit and
  reverted it, because in both cases the question was whether the *step* was
  wired up at all. Here it already is — it has been `ci.yml`'s early step since
  p3.6-01, and this run's log shows it refusing nothing by name — so a scratch
  commit would prove only what `-Dir` proves, at the cost of two more runs and a
  red one on a pull request the whole pile is waiting behind. The criterion asks
  for a *test*, and the fifteen cases run in CI on every commit, which is the
  stronger of the two.
- **The self-test prints `refused:` rather than `::error::`.** An `::error::`
  line is a workflow command, so GitHub turns each one into a *failure
  annotation* against the file and line it names — and the planted files are
  called `ci.yml`, `release.yml` and `upstream.yml` like the real ones. Without
  this, every green run would carry a dozen annotations pointing at lines of this
  repository that are not wrong at all. The exit node found that on its run
  `41191528050`; `Invoke-Check` takes `$Annotate` for it, and a real refusal
  still annotates, which is the point of it.
- **`-SelfTest` runs the real check afterwards rather than instead.** One
  command in `ci.yml`, one exit code, and the rule is proved and then applied in
  that order. `pwsh -File tools/ci/check-runners.ps1` alone is still the plain
  check.
- **The guard is not added to `tools/verify.ps1`.** It has been a step of
  `ci.yml` since p3.6-01 and stays one: `verify.ps1`'s five steps are the
  definition of *verified* for the firmware, this is a rule about the workflow
  files, and it must run before PlatformIO is installed and before anything is
  built. The cost is that a local `tools/verify.ps1` would not catch a planted
  label — so the README names the one command that does, and this session ran it
  before pushing.
- **`ubuntu-latest`, not a pinned image.** GitHub migrates it to Ubuntu 26 from
  19 October 2026 and says so in a notice on every run. The day a build breaks
  on it, `ubuntu-24.04` is the pin and the guard's `ubuntu-` prefix takes it
  unchanged.
- **The README's *Where CI runs* was rewritten rather than edited**, with both
  halves of the reason, the two GitHub links, the table of three workflows, the
  rail and its one command, and the named way back:
  `tasks/phase-3.6/01-built-at-home.md` and its commit `4cb2200`. p3.6-01's
  other argument — a shared runner keeps its toolchains, so what *ships* should
  be built where each job begins new — is true, is not lost, and is in that
  section and in `release.yml`'s own header.
- **The six runs that never got a runner were left as they are.** Four are
  already cancelled or failed; `43589236461` (`main`) and `43586655182` (#51)
  were still queued and were cancelled here, because they can never be
  dispatched and they sit at the top of the Actions tab pretending otherwise.
  Nothing else about them was touched.
