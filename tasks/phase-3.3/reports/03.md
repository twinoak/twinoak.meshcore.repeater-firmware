# p3.3-03 — The bench walks itself

`docs/bench.md`'s four checkable sections are walks now: `bench walk 1`, `8`,
`9` and `10` run the page's own bullets, in the page's order, as steps that each
print the line they check, what they sent, what they saw and *ok*, *differs*,
*needs a person* or *skipped*; the result is a Markdown file under `out/bench/`
with every `→ ______` of the walked lines filled in. The walks are held to the
page in both directions by a test — every line of a walk is a bullet that is in
`docs/bench.md` exactly once, and every bullet of §1, §8, §9 and §10 is a line
of its walk — so a page that moves is red before anybody reads it. `--tick`
ticks what came back *ok* as `[x] … (bench, <date>, <commit>)` and writes what
came back *differs* into the follow-ups of the task that wrote the line; a
*differs* is never fixed here. **No RAK4630 was on this machine during this
session** — no `bench.local.json`, and no COM port at all — so nothing was
walked on a board: the walks are complete and each one runs end to end against
02's fake serial layer in `tools/bench/test_walk.py` (43 cases, in
`tools/verify.ps1`'s release step beside 02's 79), and every line of the four
sections is still *Not verified here*, in the list below, with what each one
needs.

## Deviations from the spec or the task

- **§9's restore is the page's bullet, run last of all the steps.** The page
  puts *Flash the repeater back* before *The watchdog is live* and before *The
  fast sweep*; nothing after it would have a scanner to talk to. The task's own
  deliverable text has the same order (“…the baseline … **then** flash the
  repeater back”), so the walk runs the page's bullets in the page's order
  within the scanner's half, then the fast sweep, then the restore — and the
  result file's table shows that step last, named as the page's bullet 9.5.
- **`get dutycycle` is read in §1, where the page has it in §10.** The task's
  §1 list asks for it “on a unit that has had its first boot since 01”; the
  page's §1 bullet does not mention it. It is a step of §1's first bullet with
  a note saying so, and the page was not restructured — §10 reads it too, which
  is where the page has it.
- **Three lines of §1 are p3.3-02's and only one of them is a walk's.** 1.7
  (*The round trip through `tools/bench/`*) is exactly what `bench walk 8` does
  — `status`, `flash`, a console line, `restore` — so §1 marks it *skipped*
  with that reason rather than claiming it twice. 1.6 (the application's and
  the bootloader's USB serial numbers being one) needs a double-tap reset and a
  power cycle: *needs a person*, with the application's half read and filled in.
  1.8 (what the tool refuses on a real board) needs `rf: antenna` in the
  person's own `bench.local.json`: *needs a person*, and the walk notes that
  `bench console "password x"` was refused with nothing opened while it was
  there.
- **§10's provisioning is the console's or the link's, never both** (the task:
  “through `linkcli.py provision` (if the dongle is there) or the console”).
  The page has them as two bullets; whichever did not run is *skipped* with the
  reason, so both bullets are accounted for and the unit is provisioned once.
- **Five changes inside 02's files**, each because the walk needs it and none
  of them changing what a command does:
  - `Bench.flash_locked` and `Bench.restore_locked` are the bodies of `flash`
    and `restore` with the lock already held — the lock is one per board per
    command and deliberately not re-entrant, and a walk is one command — and
    the “a repeater found on an RF port that is not the dummy load is never
    replaced” guard moved from `cmd_flash` into `flash_locked`, so it holds for
    the walk too (`SectionNine.test_the_baseline_needs_the_dummy_load` is that
    refusal, exit 2, nothing flashed);
  - `ScannerConsole.collect_raw` returns the lines as they arrived beside the
    parsed batch, so the baseline kept on disk is the device's own bytes and
    not a re-serialisation of them;
  - `console.redact` leaves a line whose value is already `****` alone, so a
    transcript can say *which* line was sent; anything with a value in it is
    replaced as before (eight cases in `test_walk.ThePieces`);
  - `runs._parse_linkcli` is now `runs.parse_linkcli` (the walk's `hello` step
    reads the same output with the same parser);
  - `fakes.FakeBoard`'s banner is armed by a **boot** and not by a host letting
    go of the port. It has to be: after an `erase` the `First boot:` lines
    belong to the boot after it, and a port opened only to send `reboot` must
    not be given them. 02's 79 cases pass unchanged with that fix.
- **`FakeRepeaterFirmware` and `FakeScannerFirmware` answer much more than they
  did**: upstream's two `sensor list` pages built the way upstream pages them
  (a line per setting while fewer than 134 bytes have been written, then the
  whole reply cut to its 159-character window, which is what loses the digit of
  `... next:5`), the settings a `get` reads back, a first boot after an `erase`,
  and the scanner's `sweep`, `hist`, `dwell`, `cad` and `scope` lines with the
  fields of `docs/noisescope.md` §5's own examples plus the `stat` heartbeat
  every ten seconds. A fake that answered less would have made the walks
  untestable rather than the walks wrong.

## Decisions taken without asking

1. **`--tick` is a flag, not the default.** The task asks a session with a
   board to tick what it confirmed; a person running a walk to look at a board
   should not have a committed page edited underneath them. Without it the walk
   ends with the line *to tick 1.1 in docs/bench.md: the same walk with
   `--tick`*; with it, the bullets that came back *ok* are ticked
   `(bench, <date>, <commit>)` and the *differs* are appended to
   `tasks/phase-<P>/FOLLOWUPS.md` of the task that wrote the line, under a
   heading naming the walk and the date. Ticking twice changes nothing the
   second time.
2. **A *differs* is exit 1 and a follow-up, never a fix** (the task's *Out of
   scope*). Exit 1 is this tool's “the board did not do what was asked”, which
   is what a page the board disagrees with is.
3. **What a step expects is read, not remembered.** `get radio` and
   `get dutycycle` come from `[band_868]` of `platformio.ini` — the one place
   01 put the band's ceiling — so the walk cannot drift from the build. `ver` is
   held to the MeshCore tag that the unit's own `fw.version` names, not to the
   page's quoted `v1.17.1 (Build: 14 Aug 2026)`: a bump moves both together, and
   the quoted text becoming stale is a **note**, not a finding. Role, board,
   band and version come from the image's descriptor through
   `manifestref.find_descriptor`, which is what the page's own
   `manifestref.py descriptor` runs.
4. **Each line of a walk carries a unique substring of its bullet** (the
   anchor), and the page is held against the walks both ways: every anchor is a
   `- [ ]` bullet of `docs/bench.md` that occurs exactly once and names its
   task, and the number of bullets in each walked section equals the number of
   lines in its walk. An anchor that is no longer unique or no longer there
   ticks **nothing** rather than the wrong thing.
5. **§10 refuses while a run is open**, and only `identity: disposable` lets it
   run at all. The erase takes the identity with it, and a run recorded before
   it could never be restored and checked again; the message says
   `bench restore` first.
6. **§1 reads the banner the way `bench record` does** — one `reboot`,
   upstream's own, when the board has been up and the `Repeater ID:` line is
   long gone (02's *Decisions* 4; the clock keeper's file is written on the way
   down). It is the only reset any walk performs, and the result file says so
   in its notes.
7. **§10's admin password is generated, sent once and written down nowhere.**
   `secrets.token_urlsafe(18)`, sent as a `password` line (which 02's console
   refuses outright unless the bench is disposable), recorded as
   `password ****`, and replaced by `****` anywhere else it could surface. The
   unit is then a bench unit whose admin password nobody has — which is what the
   task asks for and what §10's own warning (*do this last, or on a spare
   module*) means. `test_the_password_reaches_nothing` is the proof.
8. **The minute and the baseline are flags with defaults** (`--collect 60`,
   `--baseline 20`). `scope 150 960 2048` is a stream and not a measurement that
   ends by itself, so something has to say how long to keep it; `stat`'s *one
   every ten seconds* is checked inside the minute's capture rather than with a
   second wait of its own.
9. **The baseline's picture is `waterfall_plot.py --file … --save …` as a
   subprocess**, so that the NDJSON is the evidence and the picture is a
   convenience. This machine has no `matplotlib` (it is in
   `tools/noisescope/requirements.txt` and not installed), so the step keeps the
   capture, says the plotter exited non-zero and prints the exact command to
   draw it later.
10. **The result file is `out/bench/walk-<section>-<date>-<time>-<commit7>.md`**
    — the time as well as the date, because two walks of a section on one day
    would otherwise overwrite each other. A scanner frame is summarised in it
    (`"avg": "[281 values]"`, a base64 `lv` cut at 24 characters) rather than
    dumped: a result file a reviewer can read is worth more than 281 numbers.
11. **The walk opens the run for §8 and §9 and closes it with the restore.**
    §1 reads consoles only and §10 flashes nothing, so neither opens one — a
    walk that changed nothing leaves `bench status` saying *none open*.

## New libraries (with the one-line justification)

None. `tools/bench/walk.py` and `tools/bench/test_walk.py` are the standard
library only (`configparser` reads `[band_868]`, `secrets` makes the bench
unit's password), which is what lets the release step run them in CI's
container unchanged.

## Not verified here (and why)

No RAK4630 was on this machine during this session: no `bench.local.json`, no
COM port, no `239A` device. **No walk has ever met a board**, so everything
below is `docs/bench.md`'s own lines, plus what the walks themselves owe a
first run.

**The walks, on a board** — `bench walk 1`, then `8`, then `9`, then `10` (that
order; §10 last or on a spare module), with the dummy load on the antenna port
and `bench.local.json` filled in. What a first run would settle, and what
nothing here could:

- **The waits.** 30 s for a `sweep` line (the page says a pass is about 7 s),
  10 s for the first `hist` lines, 20 s for the first `dwell` window, 15 s for a
  `cad`, 10 s for three `scope` frames, and `--collect 60` read through pyserial
  rather than through a fake. Each is a guess until a board answers.
- **Upstream's exact words**, where the page quotes them and the walk holds the
  board to them: `can't find custom var` for `sensor set fw.version x` (our own
  `Settings.cpp` and `test_firstboot` rest on that wording), `RAK 4631` for
  `board`, `File system erase: OK`, ` default scope is now dk`, and whatever
  `region default` answers on its own — the walk only requires that one to be
  non-empty, because nothing quotes it.
- **That `get public.key` is the `Repeater ID:` of the banner**
  (`docs/provisioning.md` §5 says it is; §10's last step compares them).
- **The `scope` ack's field names.** The walk parses `n= step= rbw= seg= cov=
  interval= sweep=` out of the ack's `msg`, which is `src/roles/scanner/main.cpp:282`
  — read there, not transcribed — but no radio has ever produced that line.
- **Whether §1's one `reboot` is needed at all**, or the banner is caught the
  first time (02 left the same question open).

**Still a person's, whatever the walks do** — the walks print these as *needs a
person* with what each needs, and the page's §0b table says the same:

- **§1**: the adverts and the repeating (the roof antenna, a second radio, a
  phone); a phone's login and the passwords of the first boot; `INFO.VARIANT`
  off the bootloader's drive, which this tool never mounts; I2C at 100 kHz on a
  scope probe at P0.14; the two USB serial numbers (a double-tap reset and a
  power cycle); and what the tool refuses with `rf: antenna` in the config.
- **§8**: the Walter's half, which is `twinoak.meshcore.walter-firmware`'s own
  tests against the same fixtures.
- **§9**: `pwr` against the repeater's `power` on the production connector

  tinySA Ultra as a generator (the one line that may lower
  `kScopeSegmentMhz`); the site through the cavity filter; and ten minutes of

- **§10**: the power cut timed to the first second of a boot, three or four
  times; and a phone logging in as admin — which for a unit this walk
  provisioned means setting a password of your own first, because the one it

- **And the fast sweep on this part at all**, if `info`'s `rom` is not
  `SX1261 V2D 2D02`: `scope` refuses, nothing is uploaded, and the walk says so
  and skips the two `scope` lines (the first line of *The fast sweep* is what
