# p3.3-02 — A bench a session may use

`tools/bench/` is the one way a session touches a board, and the rails are in
the tool: the rig is a USB serial number in a git-ignored `bench.local.json`
and nothing is ever picked by any other rule; `bench flash` takes the DFU
package the build or the release made and refuses everything else — a
bootloader or a SoftDevice in the package, no descriptor or two, another
board, an image that does not fit the application region, a transmitting role
with the RF port off the dummy load, UF2, HEX, BIN — **before any port is
opened**; one lock per board for the whole of a command; a console that never
sends a password and never prints one; a run record taken before the first
flash and a `restore` that puts the role back and checks the `Repeater ID`.
Every guard is a host test against a fake serial layer that records every
open, run by `tools/verify.ps1`'s release step beside the release tooling's
tests. **The board was not on this machine** during this session — no COM
port enumerated at all, no device with Adafruit's vendor id — so the board
half of the acceptance list is the first thing `docs/bench.md` §1 now asks
for, and the tool is complete without it.

## Deviations from the spec or the task

- **The serial-number claim is half read and half to be confirmed.** The task
  asks to confirm on the board that the bootloader's port and the application's
  share the chip's id. The application's half is read off the core on disk:
  `TinyUSB_Port_GetSerialNumber` builds the string from `NRF_FICR->DEVICEID[1]`
  and `[0]` (`libraries/Adafruit_TinyUSB_Arduino/src/arduino/ports/nrf/
  Adafruit_TinyUSB_nrf.cpp:96-100` at the core's pin `d541301`). The
  bootloader's half **cannot be read here**: the Adafruit bootloader is not in
  the platform package as source (only `.hex` files for Adafruit's own boards,
  none for the RAK), and no board was present. What the tool does if they
  differ: `bench.local.json` takes an optional `bootloader_serial`, the
  bootloader's port is waited for under that name (default: the same serial),
  and if no such port appears within 15 s of the touch the tool stops with the
  double-tap message and nothing written. `docs/bench.md` §1's first new line
  is the confirmation.
- **The 1200-baud touch is the tool's, not nrfutil's `--touch`.** nrfutil's
  own touch reopens the *same* port name afterwards, and on Windows the
  bootloader's CDC port (`239A:0029`) is not always the same COM number as the
  application's (`239A:8029`). PlatformIO's own upload does what this tool
  does — `TouchSerialPort` then `WaitForNewSerialPort`
  (`platforms/nordicnrf52/builder/main.py`, `BeforeUpload`;
  `boards/rak4631.json`'s `use_1200bps_touch` and `wait_for_upload_port`) —
  and then runs nrfutil with `-b 115200 --singlebank` and no `--touch`, which
  is the argv this tool builds. The pinned copy is **PlatformIO's bundled
  one**: `tool-adafruit-nrfutil` 1.503.0 (adafruit-nrfutil 0.5.3.post16),
  pinned through `platformio/nordicnrf52@11.0.0` in `platformio.ini`, run as a
  subprocess with its own bundled pyserial; no pip pin was added.
- **`app_region` comes from a linker script beside the image, or the core's.**
  A DFU package carries no linker script and no load address (the bootloader
  writes the application where its settings say, `0x26000` on this board), so
  the region is read with `build_release.read_app_region` from the
  `ldscript.ld` that `tools/pio/buildinfo.py` leaves beside `firmware.zip` in
  a build directory, else from the core's `nrf52840_s140_v6.ld` that
  `boards/rak4631.json` names; an unreadable region is a refusal, and "fits"
  is the application's size against the region's. Never a constant.
- **`Repeater ID:` is a boot banner and not a command**, and it is the one
  thing the record and the restore check. Upstream's console has no line that
  prints the public key (`get prv.key` prints the *private* one, and this tool
  refuses it), and `Adafruit_USBD_CDC::write` drops bytes while no host holds
  the port, so a banner printed one second after boot can be missed. The tool
  reopens the port as soon as it enumerates, and when the banner was still
  missed sends upstream's own `reboot` once (the clock file is written on the
  way down) and catches it the second time. With a dongle in the config,
  `identity` and `hello` over the link are used instead and no reboot happens.
- **Three exit codes beside *no bench*.** The task says *no bench* is one
  documented code and "nothing else is an error"; the tool still has to tell
  a refusal (2), a held lock (4) and a board that did not do what was asked (1)
  apart from done (0), because task 03's walks need to. `bench --help`,
  `tools/bench/config.py` and `docs/bench.md` §0a document all five, and 3 is
  the only one the runbook names by meaning.
- **`tools/verify.ps1` ran as five `-Only` calls**, not one: a single call
  would exceed the runbook's nine minutes. Same script, same steps, same logs.

## Decisions taken without asking

1. **A repeater found on a board whose RF port is not the dummy load is never
   replaced.** The task allows a scanner image on any RF port; but a run that
   starts that way could not be put back (the repeater may only be flashed on
   the dummy load), and "the board is left as it was found" is the promise
   the tool exists for. So `bench flash` refuses — after recording, before
   touching — with the reason; a scanner over a scanner on an antenna is still
   allowed, and `restore` itself goes through the same image guards (a dummy
   load swapped for an antenna mid-run is refused with the reason, and the run
   stays open).
2. **The console refuses more than the two password lines.** `set prv.key`
   and `get prv.key` (the node's private key: never set from a laptop, never
   printed), `erase` unless the identity is disposable (it takes the identity
   with it), `reboot 1`, `2`, `3` and the scanner's `dfu` (bootloaders this
   tool does not use), and `region load` (it leaves upstream's interpreter
   waiting for a blank line the console cannot send; `docs/bench.md` §4). And
   the redaction covers the echo of the typed `password …` / `set
   guest.password …` line, not only the `password now:` reply — same secret,
   two places in the bytes.
3. **The lock's staleness is "process gone, or pid reused".** The file holds
   the pid *and* the process's own start time; a live pid whose start time is
   more than two seconds off the recorded one is a reuse and stale. Created
   with `O_EXCL`; the takeover is remove-then-create, and a loser of that
   microsecond race is refused, which is the safe side. On Windows liveness is
   `OpenProcess`/`GetExitCodeProcess` through `ctypes`, because
   `os.kill(pid, 0)` there *terminates* the process (the Python documentation
   says so).
4. **A run is one record per board**, begun by the first `flash` (or by
   `bench record [--image <zip>]`, for task 03 to begin a walk explicitly),
   given its image with `--found`/`--image` (held to the same guards), closed
   by a successful `restore`, left open by a failed one. The record is a file
   under the tool's data directory (`%LOCALAPPDATA%\twinoak\bench` on Windows,
   `$XDG_DATA_HOME/twinoak-bench` elsewhere, `TWINOAK_BENCH_HOME` overrides),
   beside the lock and the flash log.
5. **A `bench.local.json` that does not describe a bench is *no bench*, with
   the reason** — not JSON, an `rf` nobody named, no `serial` — rather than an
   error: there is no bench to use either way, and the message says what to
   fix.
6. **The repeater is probed first, with a CR-terminated line.** The scanner
   takes CR or LF as a line end; upstream's console takes only CR and would
   keep an LF-terminated probe in its buffer to corrupt the next line. So
   `record` asks `sensor get fw.version` with a CR, and only when no `  -> `
   comes back does it try the scanner's `info`.
7. **Four small commands beyond the task's three**: `status` (the config and
   what is present; opens nothing), `check <zip>` (the guards alone, for a
   person and for task 03's §8), `record` (above) and `console --scanner
   --collect <seconds>` (a minute of NDJSON, parsed and counted, for §9's
   "every line is JSON" line). Each is a few lines over the same layers.
8. **The flash log is written twice**: under the data directory, where it
   outlives a checkout, and under `out/bench/`, where a reviewer looks.
9. **The restore's version note is a note, not a refusal**: when the run was
   given an image whose descriptor version differs from what the board said,
   the tool says so and flashes the given image — the person who gave it knew
   what was on the board.

## New libraries (with the one-line justification)

None. The real port layer imports pyserial lazily, as `tools/linkcli.py`
already does (PlatformIO's own Python has it, and adafruit-nrfutil bundles its
own); the tests and `--help` need the standard library only, which is what
lets the release step run them in CI's container unchanged.

## Not verified here (and why)

No RAK4630 was on this machine during the session: no COM port, no `239A`
device. Everything below is `docs/bench.md` §1's three new `p3.3-02` lines,
in the order to walk them, and task 03 walks them if the board is there.

- **That the bootloader's USB serial number is the application's.** Read off
  the core for the application (above); the bootloader's source is not on
  disk. `python -m serial.tools.list_ports -v` in both modes; a difference goes
  in `bench.local.json` as `bootloader_serial`.
- **The round trip through the tool, with the dummy load**: `status`, `flash`
  of the repeater image (the record, the touch, the bootloader's port
  appearing, nrfutil's `Device programmed.`, the application back and
  `sensor get fw.version` agreeing with the descriptor), `console "ver"`,
  `restore` ending in `restored: … Repeater ID … matches`. Two timeouts are
  guesses until then — 15 s for the bootloader's port after the touch, 40 s
  for the application after the flash — and so is whether the banner is caught
  the first time or after the one `reboot`.
- **The refusals on a real board** — a repeater image with `rf: antenna`, a
  scanner image over a repeater on an antenna, `password x` with `identity:
  keep` — and that nothing on the board changed afterwards. The tests prove
  nothing was opened; a board proves nothing was written.
- **Recovery of a board whose application never enumerates**: the tool says
  *double-tap reset* and stops (the task's own *Not verified here*). The
  bootloader is untouched by anything this tool does, so that is all it
  takes; a person's hand.
