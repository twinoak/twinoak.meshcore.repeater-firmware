# p3.3-01 — The band's ceiling

A fresh unit was starting at **five times** the duty cycle its band allows:
869.618 MHz is in the 869.400–869.650 MHz sub-band, where the limit is 10 % of
each hour, and upstream starts a repeater at `airtime_factor` 1.0 — a 50 %
budget. The limit is now a property of the band, in `[band_868]` beside the
frequency and the power, and the first-boot profile's second line is
**generated from it**: `set dutycycle 10`, with the number in the text coming
from `platformio.ini` and nowhere else.

The three small gaps the reviews found are closed with it: `tools/linkloop/`
runs in `tools/verify.ps1`'s native step (shown failing on a stale include and
then restored), the upstream watch's pull-request body says *eight places* and
names the eighth, and `test_settings`' paging cases build their version strings
from the real format and assert the bound they rest on — which turns out to
have **no headroom at all** on a release image.

## Deviations from the spec or the task

- **The edition of ERC 70-03 is cited from CEPT's document database, not from
  the document.** The task asks for the edition read. CEPT's own PDF
  (`docdb.cept.org/download/4512`, *Edition of June 2024*, the newest the
  database lists) **would not fetch from this session** — a TLS certificate it
  could not verify — so the edition, the row (**h1.7**) and the pair *500 mW
  e.r.p., ≤ 10 % duty cycle or LBT+AFA* come from that database's listing and
  from the phase-3 review, and the 10 % is also what the Danish standard uses.
  This is written where it is cited: `docs/ARCHITECTURE.md` §7 carries a
  blockquote saying exactly what was and was not read, and asks a reviewer with
  the PDF open to confirm the edition and the row. The number itself is in one
  place, so confirming it changes one line.
- **`[band_868].duty_cycle` is carried by a define of ours, not by a `LORA_*`
  one.** The five radio defaults are upstream's defines; upstream has no define
  for the duty cycle at all (it is a preference, `airtime_factor`), so the new
  one is `TWINOAK_BAND_DUTY_CYCLE`, and the only thing that reads it is
  `Profile.cpp`. The **scanner** environment does not get it: that role never
  transmits, so the "a band must say what it allows" assertion is made against
  the *table* in `BandCheck.cpp` (which every board environment compiles) and
  the define-against-table assertion lives in `Profile.cpp`, where the line is
  built.
- **`README.md` said *seven places* too.** The follow-up names
  `.github/workflows/upstream.yml`; the repository's front page had the same
  word in the sentence that links `docs/upstream.md`. Both now say eight, and
  the workflow body names the eighth and points at the table.
  `tasks/phase-0/03-the-upstream-watch.md` still says seven — a task file
  already landed, which this task does not rewrite.
- **`tools/linkloop/check.sh` reads `platformio.ini`.** `Profile.cpp` now needs
  `TWINOAK_BAND` and `TWINOAK_BAND_DUTY_CYCLE`, and `check.sh` compiles it
  outside PlatformIO. Writing `10` there would have been a second place to
  forget, so the script extracts both from the same two sections the build uses
  (`[img_repeater_rak4630_single].band` and `[band_<that>].duty_cycle`) with
  `awk`, and refuses to build if either is missing. It is the habit
  `tools/verify.ps1` already has for the environment list.
- **`test_settings`' bound has no headroom, and that is a finding.** The
  arithmetic of `sensor list`'s first page holds while the version string is
  **70 characters or fewer**; the string is 41 characters of frame plus the
  release version plus the MeshCore tag, so the bound is
  `len(version) + len(tag) ≤ 29` — and `0.1.0+abc1234` with `repeater-v1.17.1`
  is exactly 29. A `0.10.0` release, or a tag `repeater-v1.17.10`, moves
  `clock.state` to the second page. That is now a test with a sentence instead
  of a surprise, and `docs/bench.md` §5's paging line says the same number.
  A **dry run**'s version (`0.0.0-dryrun+<sha7>`, 20 characters) is already
  over it — 77 characters, four keys on the first page. A dry-run image is not
  a release (`spec/FIRMWARE-MANIFEST.md` §3) and is never on a unit, so it is
  recorded in the test rather than asserted away.

## Decisions taken without asking

1. **The client's ceiling stays at 6 sends a minute.** The task left the choice
   open. Three reasons, all on `docs/ARCHITECTURE.md` §7 and in
   `SendCeiling.h`: (a) the two limits count different things — the ceiling
   counts *sends*, the budget counts *airtime of every packet the radio
   transmits* — and only the second can hold a regulation, which from the first
   boot on it does at the band's own value; a lower ceiling would make the band
   no safer. (b) 6 is three times the server's default rate of 2 a minute and
   that margin is the whole point: three a minute is one and a half times it,
   which a *correct* paced agent can touch — a login, its request and a retry
   inside one minute — and `ERR_BUSY` would stop meaning "the Walter is
   broken". (c) What a lower ceiling would buy is latency for a packet waiting
   to be forwarded, and §7's other answer already bounds that at one send's own
   airtime. So the constant is untouched and its comment now says this.
2. **The band's row keeps one duty cycle for the whole allocation.** The row is
   863–870 MHz and the number is the 869.400–869.650 MHz sub-band's, which is
   the narrower: every image of this band is built for 869.618 MHz and nothing
   else (`[band_868].freq`, held against the row by `BandCheck.cpp`). `Bands.h`
   says so, and says that a band whose images were spread across sub-bands with
   different limits would need a row per sub-band.
3. **The profile's line is a stringified define, not a string built at run
   time.** It makes the line a compile-time constant in `.rodata` as the other
   line is, keeps `runProfile` unchanged, and lets the `static_assert` tie the
   number to the band. The cost is two macros at the top of `Profile.cpp`.
4. **`linkloop`'s miniature of upstream's `set` answers `dutycycle` the way the
   pin does** — `airtime_factor = (100/dc) - 1`, then `OK - <n>.<n>%`, and
   `ERROR: dutycycle must be 1-100` outside 1–100 — rather than the bare `OK`
   it used to give. The profile's second line is judged by the reply rule, so
   the one host-side thing that can exercise that rule should produce the real
   reply. `check.sh` now asserts `firstboot.state` → `done` after the shipped
   table has run through it, and that `set dutycycle 0` is refused.
5. **`linkloop` is a second summary row, not a second container run of
   PlatformIO.** It needs `g++` and `python3` and no PlatformIO, so its
   container run installs nothing (`check.sh` apt-gets `g++` itself when there
   is none) and costs about ninety seconds. Two rows rather than one command
   because a red `linkloop` and a red `pio test` are different findings.
6. **`docs/bench.md` §10's existing lines are amended, not added to.** The
   walk is the same walk; `get dutycycle` → `> 10.0%` is the **first** thing to
   read on a fresh boot now, and the "never seen" case gained
   `get dutycycle` → `> 50.0%` beside `path.hash.mode` → `0`. The lines are
   tagged `p3-03, p3.3-01` so a reviewer can see whose they are. Task 03 of
   this phase walks them.
7. **A unit provisioned before this keeps 50 %, and the pages say so in a
   box.** The profile runs only on a boot that finds no settings, so an older
   unit is not corrected behind anybody's back (that rule is p3-03's and is not
   touched). `docs/provisioning.md` §2 has the one line to send
   (`set dutycycle 10`), §3 has it as a session with its replies, and the
   fourth bullet after that session says `get dutycycle` is the line to read on
   a unit you did not flash.

## Not verified here (and why)

- **A board answering `get dutycycle` after a first boot.** No session can
  flash a board. `docs/bench.md` §10's first two lines are the walk — a fresh
  boot answering `> 10.0%`, and the same after a reboot with no `First boot:`
  line — and task 03 of this phase walks §10 when the bench is there and the
  module's identity may go. What *was* proved without a board: the line is in
  the table, it is the band's own number, upstream's pinned `set dutycycle`
  branch accepts `10` and answers `OK - 10.0%`, the reply rule accepts that
  reply, and the whole shipped table runs to `done` through a miniature of that
  branch in `tools/linkloop/`.
- **That `10 %` is the right number for 869.618 MHz under the edition in
  force.** Read above under *Deviations*: a reviewer with CEPT's PDF open
  should confirm the edition and the row h1.7. One line of `platformio.ini`
  changes it if it is wrong, and every other place is built from that line.
- **What 10 % feels like on a real mesh.** The arithmetic says a run-away
  Walter is delayed rather than refused, and that a server's exchange uses a
  fifth of the budget. A busy site's forwarding load is the other four fifths,
  and only a repeater on a roof can say whether that is enough.
  `docs/bench.md` §6's mesh-client lines are where that would first show.
