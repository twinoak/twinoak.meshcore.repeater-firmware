# p3.13-02 — floods as the advert goes

The board's half of link 1.3. A flood the link says is scoped now leaves through **upstream's own
`MyMesh::sendFloodScoped` with upstream's own `default_scope`** — the road this node's flooded
advert has always taken — and `FLOOD_SCOPE` answers the default region's name out of **upstream's
own `region_map`**. No key is derived here, no transport code is computed here, and nothing of
upstream's behaviour changed. With the interface in place the image answers `HELLO` with
`caps 0x1ff`, `FLOOD_SCOPE` `0x100` among them.

Nothing changes on the air until a Walter of link 1.3 is on the unit: the session decides, and a
session of 1.2 is what it was, to the byte and to the packet (this phase's `FOLLOWUPS.md`, first
item).

## What this answers when the name and the key disagree

Deliverable 4 asks what upstream does when a default region's keys cannot be loaded, and whether a
name without a key or a key without that name can exist. Read in upstream's code at the pin, not
on a board. **Both can**, and this firmware reports each honestly rather than papering over it.

`onDefaultRegionChanged` (`MyMesh.cpp:1158-1164`) is the only thing that updates `default_scope`
after `begin()`:

```cpp
void MyMesh::onDefaultRegionChanged(const RegionEntry* r) {
  if (r) {
    region_map.getTransportKeysFor(*r, &default_scope, 1);
  } else {
    memset(default_scope.key, 0, sizeof(default_scope.key));
  }
}
```

It does not read what `getTransportKeysFor` returns, and for a **private `$` region**
`getTransportKeysFor` is `_store->loadKeysFor(id, dest, 1)` (`src/helpers/RegionMap.cpp`), which
answers 0 and **writes nothing into `dest`** when the id is not in the key cache — and the cache
is all `TransportKeyStore` has at this pin, its hardware keystore being three `// TODO`s
(`src/helpers/TransportKeyStore.cpp`). So:

| | `FLOOD_SCOPE`'s `scope` | a flood's `scoped` | what is on the air |
|---|---|---|---|
| **a name with no key** — `region default $priv`, keys not in the cache, no scope before it | `$priv` | 0 | no transport code, as before 1.3 |
| **a name with the wrong key** — the same, but some other region was the default first | `$priv` | 1 | the **previous** region's code |
| **a key with no name** — after a `region load` | empty | 1 | the last region's code |
| the ordinary case — `region default dk` | `dk` | 1 | `dk`'s code |

The third row is the one worth knowing and it is not hypothetical: `startRegionsLoad` builds the
new map in `temp_map`, whose `default_id` is 0 and is never set (`RegionMap::resetFrom` resets
`num_regions` and `next_id` and nothing else), and the blank line that ends a load does
`region_map = temp_map` **without calling `onDefaultRegionChanged`** (`MyMesh.cpp:1199-1203`). So
a `region load` leaves the node with no default region and the old key still in force. A
`region default <name>` afterwards sets both again.

This firmware changes none of that. `scope` is read from the map and `scoped` is read from the
key, at the moment each is asked, because those are the two different things section 6.5 asks for
— "the default scope's name as `region default` prints it" and "what was on the air". Making them
agree would mean either deriving a key here, which 6.5 forbids in as many words, or lying about
one of them. `docs/link.md` §2j now says this in a person's words, so a Walter operator who sees
a name and a `scoped` that do not match has somewhere to read. This phase's `FOLLOWUPS.md` third
item already carries the upstream half.

One note for a reader of the table: **`DEFAULT_FLOOD_SCOPE_NAME` is not defined in this build**
(nor in upstream's own `[rak4631]` or root `platformio.ini` at the pin), so `begin()`'s
auto-create branch is compiled out and a fresh unit has no default region at all until
`docs/provisioning.md` §2's `region default dk` gives it one. That is the firmware this task
ships: a unit nobody provisioned floods exactly as it did before, and the release note says so.

## Decisions taken without asking

- **Where the two private names live, and therefore where the send is.** The task says to keep
  `default_scope` and `region_map` in one file. The scope has to be *read at the send*, so the
  send had to move into that file too: `src/roles/repeater/link/FloodScope.cpp` holds both the
  `FloodScopeAccess` implementation and a free function `floodInDefaultScope(MyMesh&,
  mesh::Packet*)`, and `TwinOakMesh::dispatch` calls that instead of naming either member. The
  alternative — handing the scope out of that file to `dispatch` — would have put `TransportKey`
  and a copy of the scope in a second place, which is what deliverable 1 forbids.
- **`floodInDefaultScope` takes no path-hash size.** It passes
  `twinoak::meshclient::kFloodPathHashSize` itself, so that the rail can read the constant on the
  call's own line, the way it already reads it on `sendFlood`'s. A parameter would have moved the
  thing S-12 is about one call further away.
- **`scopeName()` returns a view into upstream's own `RegionEntry`**, not a copy into a buffer of
  ours. `FloodScopeAccess` documents the view as valid until the next request and the session
  encodes the answer inside the request's own handler, so no buffer is needed — and a buffer would
  have been a second copy of a name that is already in RAM.
- **The name is read with `strnlen`, not `strlen`, and clamped.** `RegionMap::load` reads the 31
  bytes of a name straight out of `/regions2` with no promise of a terminator, so a truncated file
  could otherwise walk off the end of the struct. The clamp is belt-and-braces beside a
  `static_assert` that `sizeof(RegionEntry::name) - 1 <= kScopeNameMax`, which is the part that
  makes a pin that widened the field a build error rather than a refused answer.
- **The leading `#` is stripped and nothing else is.** §6.5 says "as `region default` prints it,
  without a leading `#`"; upstream prints `def->name` whole, and `RegionMap`'s own `skip_hash` is
  the precedent for the hash being decoration. A `$` stays, because it is part of a private
  region's name and `region default` prints it.
- **The one-file rail covers all four private members, not only this task's two.** It is one list
  in one test and the extra two cost a line each; splitting it would have left link 1.2's pair
  with no rail at all for no gain. The same reasoning put `FloodScope.cpp` on rule 6's list of
  files that may not name a file-system API: what it is handed is ciphertext and not a password,
  but it is on the send path and the fence is cheaper than the argument.
- **`release-notes/standing.md` was not edited.** *The Walter it goes with* says this release
  needs no newer Walter, and that is still true: the session's version decides whether a flood is
  scoped, and a 1.2 session is byte for byte what it was. A release that needs a 1.3 Walter is a
  later one.
- **The upstream request was amended where it lives rather than rewritten.**
  `tasks/phase-3.9/reports/02.md` now carries a dated paragraph under the draft letter saying the
  same `protected:` moved up a line would cover all four members, and naming the narrower seams
  that would fit the flood scope if upstream prefers one. The letter itself is untouched: it is
  the record of what that task wrote.

## Not verified here (and why)

A session cannot hear a radio, and **the whole of what this task does that a person can see is on
the air**: whether a transport code is on a packet, and whether a repeater that holds `#dk`
forwards it. No session opened a port — this phase's README says none may, the task's deliverable 7
says these lines are "not run by this session", and §4 of `docs/bench.md` is not one of the six
walk sections (`bench walk 1, 3, 5, 8, 9, 10`), so there was nothing to `--tick` either.
`bench.local.json` is present on this machine; it was not used.

The lines are in **`docs/bench.md`, *The flood scope, the radio's half (link 1.3)***, in the order
the rig is brought up, and they need a repeater within earshot that holds `#dk` with flood allowed
and prints what it forwards:

- **The image advertises the bit**: `linkcli.py hello` says `caps 0x1ff` with `FLOOD_SCOPE` in the
  list, where the image before it said `0xff`. *Why not here:* `caps` on a board is built from the
  pointers `BoardLink.cpp` fills in, and no host build runs that file.
- **The name comes from the node's own region map**: `region default dk` + `region save`, then
  `flood-scope` answers `mode 1` and `scope dk`, and still does after a reboot;
  `region default <null>` makes it empty.
- **A flooded login carries the code and is forwarded**: `scoped 1` on this side, a **transport
  code** on the listening repeater's log, and the packet forwarded.
- **The one send without it is a plain flood**: `flood-scope --once-without` and the login in
  **one invocation**, `scoped 0`, no transport code on the listener, and the send after it scoped
  again.
- **A unit with no default scope floods as it always did**: `scoped 0` and a packet byte for byte
  like `v0.1.5`'s. This is the line that proves the new road costs nothing where there is no
  region.
- **From the Walter, once its pile 14 is on the unit**: `rak scope` says the name this radio
  answered, and a job floods the scope first and then once without it (meshmaster.dk's D-47).
  That is the Walter's bench and not this one's.

Everything §6.5 says that *can* be seen without a board was already walked by task 01 and still
is: `test/test_link_session`'s `TheFloodScope.*` drives the real session and the real mesh client
against a fake port, and `tools/linkloop/check.sh` drives `tools/linkcli.py` through a pipe into
the firmware's own session, with `--no-scope` for the node that holds none.

  `error: could not convert template argument '&MyMesh::default_scope' from 'TransportKey
  MyMesh::*' to … 'RegionEntry MyMesh::*'`, and a second error at the use site,
  `invalid initialization of reference of type 'const TransportKey&' from expression of type

re-read the names. The file was restored from `out/p3.13-02/FloodScope.cpp.bak` and the green run
above is the restored one.
