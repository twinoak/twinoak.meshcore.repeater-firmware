# p3.13-01 — the link speaks of scope

Link 1.3 on this side of `MeshPort`: the codec, the session's own version, `FLOOD_SCOPE`, the
route a flood is given, and the `scoped` byte at the end of a send's answer. Written against the
tests' fake. **No board implements the new interface**, so the image this task builds answers
`HELLO` with `caps 0xff` — no `0x100` — refuses `FLOOD_SCOPE`, and floods exactly as `v0.1.5`
does. Nothing changes on the air until pile 3.13's task 02 and the Walter's pile 14.

## Deviations from the spec or the task

- **`linkcli.py` now says `HELLO` before its first other request.** The task's deliverable 7 asks
  that the bench tools "read the new byte and can ask `FLOOD_SCOPE`". Neither is possible
  otherwise: §5.1 makes the session's version per boot and 1.0 until a `HELLO`, so a tool that
  never greets gets `ERR_STATE` from `FLOOD_SCOPE` and a send answer with no `scoped` byte. The
  tool now opens its session with one quiet `HELLO` — exactly what §5.1 says the first request of
  a session is — and `cmd_hello`'s own request is that greeting rather than a second one. The
  visible cost is one extra frame per invocation, which `-v` shows. `docs/link.md` §2 says so,
  and says the consequence a person has to know: **one invocation is one session**, so
  `flood-scope --once-without` and the send it is for must be the same invocation.
- **`EV_BOOT`'s test is now held against a fixture case again.** `tasks/phase-3.9/reports/02.md`
  recorded that 1.2 added no `EV_BOOT` case, so `test/test_link_session` had to build the
  expected payload out of the newest `HELLO` response. 1.3 *does* carry one — *boot event, 1.3:
  the bit in its caps* — so the test is back to a frame comparison. That deviation is closed.
- **`FLOOD_SCOPE` is not in the generic fixture sweep.**
  `TheFixtures.EveryRequestThisTaskAnswersGivesTheFixturesResponseFrame` feeds one request to a
  fresh session, and a fresh session is 1.0,
  where §6.5 is `ERR_STATE`. The fixture's three `FLOOD_SCOPE` requests are driven in order
  through one session of 1.3 instead
  (`TheFloodScope.TheFixturesCasesInOrderThroughOneSessionOfOnePointThree`), which is what
  their sequence is about; one of them, *flood scope: back to the
  scope*, carries no answer case at all, so its answer is read out of the frame the session
  built. The sweep's count for `link-v1.3.json` is therefore 20 — 1.2's nineteen and 1.3's fourth
  `HELLO`.
- **No disagreement between `spec/` and the task file was found.** Everything the task asks for is
  in §6.5, §6.2 and §5.1, and the numbers are `spec/tools/linkref.py`'s.

## Decisions taken without asking

- **Where the mode lives, and who works out whether a flood is scoped.** §6.5 fixes the rule and
  not the shape. The session owns both the session's version (`session_minor_`) and the mode
  (`flood_mode_`), and computes `floodScopedNow()` = *the interface is there* **and** *the session
  is 1.3 or later* **and** *the mode is 1*; it pushes that one boolean to the client before every
  send through a new `MeshClientAccess::setFloodScoped`. The alternative — the mode in the client
  — would have let a build with no `FloodScopeAccess` scope a flood, which §6.5 forbids
  ("a RAK without it … its floods carry no transport code"). The client stays a thing that knows
  nothing of `HELLO`.
- **The 120-second job end is reported to the session, once.** Every other reset point of §6.5 is
  a request the session executes; the self-ended job is the client's. `MeshClientAccess` gains
  `takeSilentJobEnd()`, which the session asks once a pass, above every early return of `poll()`
  so that a busy pass cannot lose it. The edge is explicit rather than inferred from `jobBegun()`,
  because a mode of 2 is legal with no job at all.
- **The order of `FLOOD_SCOPE`'s refusals** is the task's own list: no interface →
  `ERR_UNSUPPORTED`, a session older than 1.3 → `ERR_STATE`, no mode byte → `ERR_MALFORMED`, a
  mode outside 0–2 → `ERR_RANGE`. So a session of 1.2 sending a mode of 3 is told `ERR_STATE` —
  the thing it has to fix first. This is the one place in the session where a state check comes
  before the decoder, and it is commented there.
- **A `JOB_BEGIN` the codec refuses does not put the mode back.** §6.5 says "so do `JOB_BEGIN` and
  `JOB_END`"; a malformed `JOB_BEGIN` changes nothing at all, the job in progress included
  (phase 2's task 01), so it changes the mode neither. A **send** that is refused does put it
  back, because §6.5 says so in as many words.
- **`scoped` is `what the port did AND this route was a flood`.** The client ands the port's
  answer with `flooded` before it fills the byte, so a port that answered yes to a direct send
  could not make the byte a 1. §6.2 fixes 0 for a direct send unconditionally.
- **`SendResponse` carries a `session_minor` that is not on the wire.** It is how the encoder
  knows whether to write the byte, mirroring what `HelloBody::proto_minor` does for 1.1's `band`,
  and the session is the one place that fills it in. Default 0, so a caller that forgets writes
  the 1.2 bytes rather than the 1.3 ones.
- **`MeshPort`'s three sends return a `PacketSent` instead of a `bool`.** The port has to say back
  whether a transport code went on the packet (deliverable 5), and one shape for all three reads
  better than an out-parameter on two of them. `sendTrace` answers it too and always false.
- **`linkloop` grew a `--no-scope` flag** so that §6.5's *empty name* and *a flood asked scoped
  that went out without one* are walked behind the pipe, with no board.

## Not verified here (and why)

A session cannot open a board's port for a repeater image, and this task's lines are not one of
`docs/bench.md`'s existing walks, so none was run. Both lines are in `docs/bench.md` under *The
flood scope, the link's half (link 1.3)*, in the order the rig is brought up.

- **`linkcli.py --port <port> hello` says `protocol 1.3` and `caps 0xff`** — 1.3 spoken, and
  `FLOOD_SCOPE` **not** in the list — and `linkcli.py --port <port> flood-scope` then answers
  `ERR_UNSUPPORTED`, one status byte and nothing else. That pair is the whole of what this task
  ships to a board: a newer link, and no new behaviour on the air. *Why not here:* `caps` on a
  board is built from the pointers `BoardLink.cpp` fills in, and no host build runs that file.
- **A flooded send is answered `scoped 0`, and the packet is the one it always was.** With a job
  begun and no path, `discover --no-wait` → `send 1 (sent as a flood)` and `scoped 0`: the byte
  is there because the session is 1.3, and it says 0 because nothing was scoped. A second radio
  within earshot sees the flood `v0.1.5` sent — two-byte path hashes and **no transport code**.
  *Why not here:* a session cannot hear a radio. This is the line that would catch a board
  scoping a flood a task early.

Everything else §6.5 says was walked without a board: `test/test_link_session` drives the real
session and the real mesh client against a fake port for all of it, and `tools/linkloop/check.sh`
drives `tools/linkcli.py` through a pipe into the firmware's own session — `flood-scope`, the one
send without the scope, a flooded send answered `scoped 1`, a direct send answered 0, and a node
with no default scope answering an empty name and a `scoped` of 0.

## What this costs in flash

The repeater image went from **422 196** to **422 788** bytes — **+592**. Phase 3.13's
`FOLLOWUPS.md` asks for this number: the unit's Walter holds its lease on an apply for 15 minutes
and `v0.1.5` flashed for 14 min 51 s, so an image that grows is flash time the lease has not got.
592 bytes is about 0.14 % of the image; at `v0.1.5`'s rate that is on the order of a second. It is
still an image to apply **after** meshmaster.dk's task 227 or the Walter's pile 14 task 04, as
that follow-up says.
