## The plugin, read

`src/roles/scanner/vendor/sx126x_spectrum/spectrum.asm` (157 lines, whole) and
`SX126xSpectrumScanner.h`'s `setSweep()` (~L130–162) and `latencyFor()` (~L78). Both are
vendored, not ours.

### 1. What one point costs the plugin, against one RSSI update

Per point the plugin's `.update` loop executes **25 instructions** (`spectrum.asm`, `.update` to
the `jzc .update` that closes it), of which one is `calls retune` — **9 more** (four pairs of
`move` into `0x6B`…`0x6E`, and `rets`) — and one is `calls wait_update`, whose cheapest path is
**6** (`move r2,[P_WAIT]`, then `move r3,(i0)`, `cmp`, `jne`, `move [LAST],r3`, `rets`). So **about
40 instructions a point** on top of the waiting itself.

In time: the fork's own figure is *a poll taking ~0.6 µs plus `delay` × 0.125 µs* (`setSweep`'s
comment), and a poll that finds no change is 7 instructions, so **an instruction is about 86 ns**
on this core — ~12 MHz. *That step is an inference from the fork's number and not something the
source says.* On it, 40 instructions is **about 3.4 µs**, and against one RSSI update
(1.6 ms ÷ RBW in kHz):

| RBW | one update | the plugin's own work a point | what that is of an update |
|---|---|---|---|
| 4.8 kHz | 333 µs | ~3.4 µs | ~1 % |
| 58.6 kHz | 27.3 µs | ~3.4 µs | ~13 % |
| **467 kHz** | **3.43 µs** | **~3.4 µs** | **~100 %** |

**At 467 kHz the bookkeeping of one point costs about a whole update period.** The sweep cannot
then be what its comment describes — *retunes right after every RSSI update* — because the retune
for the next point lands as the next update is already arriving. Whether a point there costs one
update or two is a thing `sps` says outright, and deliverable 6 asks for `sps` of every line:
`scopeSweepMs()` predicts (points + 8 × segments) × 1.6/rbw ms, so a sweep that takes twice its
prediction at 467 kHz and not at 58.6 is this.

### 2. `setSweep` at 467 kHz: `delay` 0 and a `wait` of 17

`setSweep` computes `update_us = 1600/rbw`, `delay = (update_us/8 - 0.6)/0.125` clamped to
0…255, and `wait = 3 × update_us / (0.6 + 0.125 × delay)` clamped to 4…255:

| RBW | `update_us` | `delay` computed | `D` sent | `W` sent | `L` (`latencyFor`) |
|---|---|---|---|---|---|
| 4.8 kHz | 333.3 | 328.5 | 255 | 30 | 2 |
| 58.6 kHz | 27.30 | 22.50 | 22 | 24 | 3 |
| 467 kHz | 3.426 | **−1.37** | **0** | **17** | 4 |

At 467 kHz the arithmetic wants a *negative* delay — the poll is already slower than an eighth of
an update — so `D` is 0 and the poll loop runs flat out. `W` is 17, so what the poll loop then
does is: read `REG_RSSI_INST`, compare with `LAST`, and if it has not changed go round again with
no delay at all, **at most 17 times** — about 10 µs, or three update periods — and then fall out
of the loop and **take the reading as it stands** (`wait_update`'s `.next`/`jzc .read` falls
through to `.new`, which stores `r3` into `LAST` and returns it). So a timeout is not an error and
is not reported; it is indistinguishable, from the loop's side, from an update.

### 3. What `wait_update` does when a reading does not change, and what that does to the latency

The answer above, and its consequence: **the latency is counted in `wait_update` returns and not
in RSSI updates.** `[SKIP]` is set to `L` and decremented once per pass of `.update`
(`move r2,[SKIP]` / `dec` / `move [SKIP],r2`), and the first reading stored is the (L+1)-th
*return*. On a level that does not change — which is exactly what a **steady** carrier gives —
some of those returns are timeouts after ~3 update periods rather than updates, so the reading
filed under a point may belong to a frequency the receiver left several updates ago, and the
pacing of the whole sweep after it is wrong by however many timeouts there were. The pacing is
therefore **signal-dependent**, which is the one thing in these 167 words that can behave
differently in a frame that holds a carrier and in a frame that does not — and the blocks of
23 November appear only in the frames that hold one. This is `tasks/phase-3.16/FOLLOWUPS.md`'s
third item, read out of the source rather than guessed at; it is still not measured.

### 4. What the chip is told at a retune, and what the arm leaves the receiver doing

**The retune is four register writes and nothing else** (`retune`, the last subroutine of
`spectrum.asm`): `CUR` into `0x6B`, `0x6C`, `0x6D`, `0x6E`, most significant byte first, and
**the write of `0x6E` commits the frequency** (the file's own header says so, *checked on hardware
against SetRfFrequency*). There is no `SetRfFrequency` opcode, no `Calibrate`, no
`CalibrateImage`, no read of the chip's status, and **no wait for a PLL lock** anywhere in the
program. Whatever the synthesizer does between two frequencies, the plugin neither knows nor waits
for it.

**Before the first point the receiver is in continuous receive at the segment's centre.**
`setSweep` does `standby()`, `setRxBandwidth(rbw)`, `setFrequency(start_mhz + step_mhz × points/2)`
— *the centre* — then `setRfSwitchState(MODE_RX)` and `receiveContinuously()`
(`RX_TIMEOUT_INF`). Our own `armScopeSegment()` has already set that same centre, with RadioLib's
calibration skipped, so `setSweep`'s own `setFrequency` is a move of zero and calibrates nothing
(`src/roles/scanner/Sweep.h`, `ScopeArmRadio::setFrequency`; `Sweep.cpp`). Then `sweep()` writes
`0x9B`, and the plugin reads the RSSI register into `LAST`, calls `wait_update` once *to sync to
the update grid*, `retune`s to **point 0**, and calls `wait_update` **twice more** — the two extra
updates its header allows for the jump, which it describes as *a jump of several MHz settles 1–2
updates slower than a step*. **Point 0 is half a segment away from where the receiver was
sitting**: 14.9 MHz for a 64-point segment at 467 kHz, and up to 16 MHz for any segment this
firmware plans. Two updates is 6.9 µs there.

### 5. Which of these could make what was seen, and which measurement would tell

The loop is **uniform from point to point**: the same 25 instructions, the same single retune, the
same `[SKIP]` arithmetic. **Nothing in the program has a period of twelve points, of 5.6 MHz or of
41 µs** — there is no counter in it that comes round at any such number. Exactly two things in it
are *not* uniform, and this is what each could and could not do:

| What | Could put a block at a segment's **first point**? | Could repeat every so many MHz / points / µs? |
|---|---|---|
| **The arm leaves the receiver at the segment's centre**, and point 0 is half a segment away with two extra updates for it (§4) | **Yes, and it is the only thing in the plugin that can.** A half-segment jump given the allowance for *several MHz* is the one point of a sweep measured through something that has not settled | No. It happens once a segment, so it can repeat *per segment* and not inside one |
| **`wait_update` times out on a level that does not change** (§3), so the pacing and the latency count depend on the signal | Only by accident | **Perhaps** — it is the one signal-dependent thing here, and a mis-count that accumulates would show at some number of points or microseconds. But nothing fixes that number at twelve, and the plugin does not count anything that would |
| **The chip's synthesizer changing band, with no lock wait anywhere in the plugin** (§4) | Yes, if a band edge falls at a segment's start | **This is the guess** — and it is the only candidate that is naturally a number of **MHz**. *Marked as a guess:* the SX1261/2 datasheet was **not read in this session** (below, *Deviations*), so no band edge is cited and no spacing is claimed from it |

So: **the comb is the chip's and not the program's** — read from the source, which is as far as a
session can take it. Which measurement of deliverable 6 tells which:

- **the same 180 MHz begun 7 MHz lower**, and the spans of 60, 31 and 20 MHz: whether a block is
  at a frequency or at a place in a segment. If the blocks move with the segments, the frequency —
  and the synthesizer with it — is out, and the cause is in the sweep's own structure;
- **the step halved, and 234.3, 117.3 and 58.6 kHz**: whether the interval is MHz (the
  synthesizer), points (the loop) or microseconds (the clock). `echoes.py` says all three and the
  run's last line names the one that holds — which is the whole reason the list has four shapes of
  the same span in it;
- **`sps` of every line**: §1's question, whether a point at 467 kHz costs one update or two;
- **the carrier's own peak**, which `echoes.py` reports as an offset in points: whether
  `latencyFor()`'s 2, 3 or 4 is right for that bandwidth. A peak a point or two off where the
  generator is says the latency is not;
- **`boost off`**: whether the receiver's gain control is in it at all.

## Decisions taken without asking

1. **The floor is read across the frequency axis, not across time** — each segment's own tenth
   percentile. With a steady carrier on the bench every frame holds it, so there is no quiet frame
   to subtract; and the floor jumps where a segment does, so it cannot be one number for a
   capture. **Not the median**: blocks twelve points apart that fade over ten cover most of a
   segment, and a median then sits *inside* them. `--floor` says it outright for a segment its
   echoes fill and `--floor-quantile` moves it.
2. **A point's level is the median over the frames that hold the carrier**, and a frame holds the
   carrier when the strongest of its carrier point and the two either side reads at least `--lit`.
   The two either side because the plugin files a reading under the point it retuned to `L`
   updates ago and a carrier can land a point along — which is also why the carrier's offset in
   points is reported rather than assumed to be zero.
3. **A run of points never crosses a segment boundary.** Its distance is measured from a
   segment's first point, so a run lying in two segments has two distances and is two runs.
4. **Inside one `scope` the three units are one number, and the tool says so instead of picking
   one.** A distance of k points *is* k × step MHz and k × 1.6/rbw ms; the tolerance is half a
   point in each, so the worst miss is the same fraction of the interval in all three. What tells
   them apart is two scopes of **different step and different bandwidth**, and that is what the
   capture-level verdict reads and what `hunt.py`'s list is built to give. The task's deliverable
   1 asks for *in which of the three units they repeat best*; the honest answer for one scope is
   *none of them*, and the tool's own docstring, the summary line and two tests say it.
5. **What is not an interval**: fewer than three points (a block is five to fifteen points long,
   so a closer spacing is below what anybody could read, and below the tool's resolution), and a
   set of multiples that is sparse — at least half of the multiples from the first to the last
   have to be there. Without the second rule the nine unrelated spurs of the dummy-load baseline
   came out as *every one and a half points*, on the tenth, fourteenth, seventeenth, thirtieth,
   thirty-third, forty-first and fifty-second multiple of it. It is **not** a cap on the multiple
   itself: a segment of 220 points really does hold thirty-seven blocks six points apart.
   `test_peaks_that_do_not_repeat_are_not_called_an_interval` is that baseline's nine distances.
6. **`hunt.py` sends `stop` after every `scope` it captured**, and its default list ends with
   `boost on` — so the board is left with the scanner running, boosted gain on and no stream, and
   `bench restore` is neither needed nor run (the pile's README: this task flashes the scanner and
   nothing else).
7. **A capture `hunt.py` writes carries the `ack` as JSON at its top and then the board's own
   bytes.** The plan a board *took* belongs with the frames, and the ack arrives before the
   collecting starts, so there is no way to keep it verbatim; `tools/noisescope/captures/README.md`
   says this is the one re-serialised line in a capture.
8. **The C++ half of the plan table compares to seven significant digits and not sixteen.** This
   build's ArduinoJson reads a number into a `float` (`ARDUINOJSON_USE_DOUBLE` is not defined for
   `[env:native]`), so 863.014 comes back as 863.013977 and a `rbw_khz` of 234.3 comes back as
   234.30000305 — which `narrowestRbwKhz()` answers with the *next* filter up, making the plan
   another plan. So the test snaps a bandwidth the table names to the filter it names before
   handing it to `planScope()`, and its tolerance is a few of `float`'s own steps. The file itself
   is exact and the Python half reads it at full precision, so nothing of the table goes
   unchecked. `platformio.ini` was **not** changed for this: a build flag for every native test is
   more than this task should move.
9. **`echoes.py` is standard library only** and does not import `waterfall_plot.py`. Its tests run
   in `tools/verify.ps1`'s release step, which has numpy and matplotlib nowhere; the level
   arithmetic is `scope_levels_to_dbm()`'s, written out again with a comment saying so.
