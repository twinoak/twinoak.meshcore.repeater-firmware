## How the settle is made, and why not the other way

The task offered *a sweep of one point whose reading is thrown away*. **It cannot work**, and the
reason is in the vendored `setSweep()` (`SX126xSpectrumScanner.h` ~L130–162, read at the pin): it
is the only way to load the sweep that counts, and it does `standby()`, `setRxBandwidth()`,
`setFrequency(start + step × points / 2)` — **the segment's centre** — and only then
`receiveContinuously()`. So anything done *before* `setSweep()` is undone by it, and a throwaway
sweep placed before it leaves the receiver nowhere useful; a throwaway sweep placed *after* it
would overwrite the parameters it just loaded, and `_params` is private to a file we do not edit.

The one move left is the move the plugin itself makes at every one of its points: the frequency
written with the receiver already in continuous receive and nothing calibrated — `spectrum.asm`'s
`retune`, four writes to `REG_FREQ` `[0x6B..0x6E]`, *checked on hardware against SetRfFrequency*
by the fork's own author. `ScopeArmRadio::setFrequency()` is that write through RadioLib
(`SX1262::setFrequency(float, true)` → `setFrequencyRaw` → `SetRfFrequency`, 7.8.0,
`SX1262.cpp:178-189`: with `skipCalibration` nothing is calibrated and no mode is changed). So:
arm as always, then the first point, then stand there, then sweep — and the plugin's own retune
into point 0 is a move of zero, with its two extra updates spent on a synthesizer that has
already settled.

**What is not proved and only a board can say:** that the SX1262 honours `SetRfFrequency` while
it is in continuous receive. The plugin does the equivalent register write there all sweep long,
which is the strongest argument available without the datasheet (task 01 had no copy of it and
neither had this session). If the chip ignores it, the settle is a delay that changes nothing —
the sweep is still correct, the `sps` still drops by the settle, and deliverable 6's table shows
it at once as *no change at any settle*. Nothing about it can corrupt a reading: the frequency
the plugin files each point under is the plugin's own.

## Deviations from the spec or the task

1. **`kMaxTokens` went from 8 to 9, and one test's *name* with it.** Nine words is now the longest
   command there is. `Commands.RepeatedSeparatorsAreOneAndNineWordsAreEight` reads the cap through
   the symbol and its body already sends ten words, so it passes untouched — but its name had
   become false, so it is now `…AndTenWordsAreNine`. No assertion changed.
   `docs/noisescope.md` §5's *At most eight words are read* is now nine.
2. **`FakeArmRadio` gained a `settle()` override** that records the call. Nothing in the file asks
   for a settle except the three tests that are about one, so every expectation already in it is
   what it was. `ScopeArmRadio::settle()` is **not** pure — it defaults to standing for no time —
   precisely so that a fake written before this task is still a `ScopeArmRadio`.
3. **`Scope.ThePlanTableIsPlanScopes` reads two more fields** (`seg_mhz` and `settle_us` of a
   request, `seg_mhz` of a plan), because the shared table gained them; and
   `ThePlanTable.test_the_table_has_the_spans_this_pile_is_about` now says *the row of the wide
   span with no width asked for*, because there are three rows of that span. Both are the table
   growing, not a check loosening.
4. **`docs/noisescope.md` §5's `ack` example said `sweep=86ms` and that is wrong.** 250 points at
   39.0 kHz is `(250 + 8) × 1.6 / 39.0` = 11 ms; 86 ms is that plan at 4.8 kHz. The new host test
   holds the real bytes, and the page now reads `sweep=11ms`. Found by writing the test, not by
   changing the code: `main` would have answered 11 ms too.
5. **A segment inside a calibrated range is skipped only for a plan cut narrower than
   `kScopeSegmentMhz`.** The task asks that thirty-three segments not pay thirty-three
   calibrations; it also asks (criterion 1) that a `scope` with six numbers or fewer arm *exactly*
   as on `main`. Those two meet in one place: `scope 863 870 2048` is nine segments inside
   1.6 MHz, so a plain 32 MHz calibration window would cover all nine and that plan would make
   **one** calibration where `main` makes nine — faster, invisible in the `ack`, and still a
   change to what a board does when nobody asked for one. So `scopeCalibrationRange()` returns
   the segment's own range when `plan.seg_mhz >= kScopeSegmentMhz` and the 32 MHz window
   otherwise, and the test asserts both halves. Whoever makes a narrower width the default
   inherits the faster arm with it.
6. **No calibration's own duration is in the plan's time.** `kScopeSegmentUpdates` (eight RSSI
   updates a segment) is the arm's allowance the plan has always carried, and the settle is added
   to it — but a real `calibrateImageRejection()` takes milliseconds, not microseconds, and
   putting that in `sweep_ms` would change the `ack` of every `scope` ever typed. It is the
   reason deliverable 4 exists, and what it costs is `sps` on a board: deliverable 6 asks for
   `sps` of every line, which is where a calibration's price is actually visible.
7. **Nothing bounds `segments × settle_us`.** A legal pair can plan a sweep of 41 s (2048
   segments of 20 ms), which the `ack`'s `sweep` says outright before the first frame. It is not
   a safety matter — one segment is one pass of `loop()`, so the watchdog is fed between them and
   the longest blocking stretch is one settle plus one plugin call, under 1.02 s — and the task
   asks for two bounds, not three. A reader of the `ack` can see it; a later task can refuse it if
   the tables want a default.
8. **The SX1261/2 datasheet was not read** (as in task 01: no copy, no web access). Every claim
   about the synthesizer stays a guess and none is given a number; `SetRfFrequency` in receive
   rests on the plugin's own behaviour and is flagged above as the thing a board must confirm.
9. **No bullet was added to `docs/bench.md` §9.** `tools/bench/walk.py` holds that section's
   bullets and its walk one for one
   (`test_walk.test_every_bullet_of_a_walked_section_is_a_line_of_its_walk`), so a new bullet is a
   new walk step — and this session has no board to write one against, exactly as in task 01's
   deviation 4. The image-check bullet now names `p3.16-02`, carries this task's one command and
   its three blanks, and says that it measured nothing.

## Decisions taken without asking

1. **The two numbers come after the aggregate**, so `scope <f0> <f1> points rbw interval agg
   seg_mhz settle_us`. The task's deliverable 1 writes them in that order and it is the only
   order that leaves every line typed before this task reading the same.
2. **The width is taken to a tenth of a MHz by `floor(x × 10 + 0.5) / 10`.** The task says *a
   tenth of a MHz is taken*; rounding to the nearest tenth (rather than truncating) is what a
   person typing 5.64 means. One consequence worth knowing: a value whose tenth sits exactly on a
   half, like 5.65, is not representable as a double and lands on 5.6 — the test says so with
   5.64 and 5.67 rather than pretending otherwise.
3. **A width below one step is refused rather than clamped**, and *one step* is the plan's own
   step, not `kScopeMinStepKhz`: a segment narrower than the step it is made of would be a
   segment of one point asked for in a way that hides the fact. A width of one step *is* legal and
   gives a point a segment (386 of them for the wide span), which is in the test.
4. **The `ack` names both numbers whenever either is not the default**, so the line has one shape
   rather than four. `32 0` typed out is the default and gets the line `main` gives.
5. **A one-segment plan stands on its first point before every sweep.** `serviceScope()` only
   re-arms when `armed != segment`, which for one segment is once ever — so the settle would have
   been paid on the first sweep and never again, while the receiver comes to every later sweep
   from the **last** point of the one before it, a whole span away. That is exactly the case of
   23 November's second capture (13 MHz, one segment, a block at its first point in every frame),
   so the settle has to be there every time. `settleScopeSegment()` is its own function for that
   reason, and the arm ends with it.
6. **A failed retune in the settle is `kScopeArmSettle` and not `kScopeArmSetFrequency`**, so the
   `err` says which of the two frequency moves of an arm returned the code. `docs/noisescope.md`
   §5's list of `call` words has `settle` in it now.
7. **The calibration is remembered as the range that was *asked for*, and a segment is inside it
   when every frequency the segment measures is.** The window is from the segment's own first
   point up, never past the plan's last point and never narrower than the segment — so no point is
   ever swept through an image the chip was not calibrated for, which is the only property that
   matters. A reload invalidates the memory, because the reset does.
8. **`scopeAckMessage()` and `kScopeRefusal` moved into `Sweep.cpp`.** `main.cpp` is in no host
   test (no board environment's `main` is), so the `ack`'s bytes could not have been held to
   anything where they were. Moving them is what makes deliverable 2's *a test holds both*
   possible; the format string is the one `main.cpp` had, character for character.
9. **Three rows added to `scope_plans.json`, not eight.** The firmware's own test checks all four
   widths over both spans arithmetically
   (`Scope.ASegmentWidthCutsThePlanAndEveryPointIsStillMeasuredExactlyOnce`); the shared table
   exists to hold the tool's copy of the arithmetic to the firmware's, and three rows — 17, 33 and
   3 segments — exercise the new parameter in both halves without adding 169 segment records to a
   file a person reads.
10. **`echoes.py` takes the width from the `ack` and 32 MHz when there is none.** A frame carries
    `f0`, `step`, `n` and `rbw` and no width, so a capture of a narrow-width line read without its
    ack is laid out in the wrong segments and every distance is wrong.
    `test_the_same_capture_read_without_its_ack_is_read_wrong_and_that_is_the_reason` is that
    failure, written down on purpose; `hunt.py` already writes the ack at the top of every capture.
11. **The settle is carried through the tool but changes no distance**, because it is time spent
    before a segment's first reading and every echo is measured from that reading.
    `test_a_settle_changes_no_distance_inside_a_segment` says so for 0, 500 and 20 000 µs.
12. **The list's combination lines are the pair the README's reading points at** — 5.6 MHz and
    500 µs — with one value either side of each taken from the widths and settles the list already
    tries. A static list cannot know the best pair before the table exists; the list says so, and
    the best pair is two more `scope` lines when the table is read.

## What the default would become if Thomas takes the numbers

Nothing in this branch decides it, and nothing in this branch has measured it. What the two
captures of 23 November point at, as the numbers a later task would put in `src/roles/scanner/`:

- **`kScopeSegmentMhz` 5.6 instead of 32.** Twelve points of the wide span, and the interval the
  blocks were read to repeat at. The wide span becomes 33 segments instead of 6: 33 arms instead
  of 6, **7** image calibrations instead of 6, and `(386 + 264) × 1.6 / 467` = 2.23 ms of RSSI
  time instead of 1.12 ms — so under half the sweeps a second before the arms are counted, and the
  arms are what the bench has to price.
- **a settle of 500 µs**, which is 146 RSSI updates at 467 kHz where the plugin allows two. On
  33 segments that is 16.5 ms a sweep — **eight times the sweep itself** — so if the block at the
  first point goes at 100 or 200 µs, that is the number to take and not this one. This is the
  single most useful thing in deliverable 6's table.
- the two together on the wide span: `sweep` goes from 2 ms to **19 ms**, about ten sweeps a
  second instead of a hundred at the plugin's best. Whether that is worth it depends entirely on
  whether the blocks go, which no session can say.

`tasks/phase-3.16/FOLLOWUPS.md`'s first item is that decision, and it is still open.
