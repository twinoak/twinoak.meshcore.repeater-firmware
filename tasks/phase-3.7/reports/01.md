# p3.7-01 — The first release

Thomas, 5 November: the first unit's repeater came up on the mesh, its Walter did
not, and *we're missing the firmware as releases on GitHub, together with a small
guide and release notes.* Nothing had ever been tagged here.

**The key is there.** `gh secret list` → `RELEASE_SIGNING_KEY  2026-10-20T13:46:39Z`
(the name and the date only, never a value), and `keys/release.pub` holds the
public half Thomas committed on 20 October (`82e2534`). `keys/release.pub` read
with `sign_manifest.read_public_key` now returns key id **`73efdd383a957596`**,
which is the id the task names. So the first check passed and no
`logs/STOPPED-01.md` was written.

**And the task was right about why a tag would have failed.** The committed file
is one line in the Walter firmware's trust-table form —
`ed25519 73efdd383a957596 dad705e5…f1fe` — and `read_public_key` wanted the 64
hexadecimal characters alone, so the tag path would have stopped in `publish`,
*after* both builds, with *does not hold 64 hexadecimal characters on its first
line of content*. Reproduced on `main` before anything was changed:

```
$ python -c "<main's sign_manifest.py>.read_public_key('keys/release.pub')"
SigningError: keys/release.pub does not hold 64 hexadecimal characters on its first line of content
```

`git show main:tools/release/sign_manifest.py` imported beside the real file, so
that is `main`'s code on `main`'s data and not a reconstruction of it.

Nothing caught it because **no check on any commit read that file**: the dry run
signs with the specification's test key, which never touches it, and the tests
used a stand-in `.pub` under a temporary directory. That gap is closed below, and
it is the shape of the finding rather than the one line: a tag reads two files no
dry run does, and now a commit reads both.

## What changed

### `keys/release.pub` as the signer reads it

- **`tools/release/sign_manifest.py`** — a new `public_key_of_line(line, path)`
  under `read_public_key`, which takes
  - `ed25519 <key id> <64 hex>`, the trust table's line, and
  - the bare `<64 hex>`, which is what `manifestref.py keygen` prints,

  and **recomputes the key id from the key** with `manifestref.key_id`: a line
  whose named id is not the key's own is refused, because both halves of that
  line are a person's and a hand-edited one would have the signer compare a
  signature against one key while a reader of the file believed another. The
  message names **both ids** — a key id is in the clear in every signature — and
  never the key. Everything else the reader did is unchanged: `#` comments and
  blank lines above the key, the *is not there* and *holds no key* messages with
  `HOW_TO_MAKE_THE_KEY` under them.
- **`tools/release/selfcheck.py`** — a new first part,
  `the_files_only_a_tag_reads()`, and `--only keys`: the **real**
  `keys/release.pub` through `read_public_key` — the reader the tag path uses —
  and every `release-notes/vX.Y.Z.md` through `release_notes.hand_written`. It is
  the first thing `tools/verify.ps1`'s `release` step runs and the first thing CI
  runs, so a malformed public half or a notes file named `v0.1.md` fails on a
  commit. Its two lines on this commit:

  ```
  == the two files only a tag reads: keys/release.pub, and the release notes
  keys/release.pub: a 32-byte Ed25519 public key, key id 73efdd383a957596 (the form keys/README.md describes)
  release-notes/v0.1.0.md: 3117 characters, 54 line(s) in front of the generated part
  ```
- **`keys/README.md`** — *`release.pub`* now describes the one form both
  repositories write a key in, says the id is recomputed, and has a *The key that
  is here* block: `ed25519 73efdd383a957596 …`, 20 October 2026, `82e2534`. The
  sentence *It is not here yet. Until it is, a tag is refused* is gone, because it
  has been wrong since 20 October.
- **`tools/release/test_release.py`** — a class `ThePublishedPublicHalf`
  (eight tests; the two existing `.pub` tests moved into it) and one more in
  `TheSignature`:

  | test | what it holds |
  |---|---|
  | `test_the_key_alone_is_a_key` | the bare 64 hex |
  | `test_the_trust_tables_line_is_a_key` | `ed25519 <key id> <64 hex>` |
  | `test_an_upper_case_key_id_is_the_same_key_id` | the id is compared case-insensitively |
  | `test_a_key_id_that_is_not_the_keys_own_is_refused` | **a wrong id**, and that the message names both ids and not the key |
  | `test_a_public_key_file_that_is_not_a_key_is_refused` | five malformed lines: three fields that are not a signature line, two fields, `ssh-ed25519`, 63 characters, a non-hexadecimal character |
  | `test_a_missing_file_and_an_empty_one_both_say_how_to_make_the_key` | both say `manifestref.py keygen` |
  | `test_the_committed_file_is_the_key_thomas_made` | the **real** `keys/release.pub` reads as `73efdd383a957596` |
  | `test_the_public_key_file_takes_comments` | `#` lines and blank lines above it |
  | `TheSignature.test_the_real_path_takes_the_trust_tables_line_for_the_public_half` | the whole tag path — key from the environment, public half from a `.pub` in the trust table's form — signs and verifies |

### The release notes a person reads

- **`tools/release/release_notes.py`** (new, 124 lines, standard library only) —
  the hand-written top of a release body, `release-notes/v<X.Y.Z>.md`. `tag_of`
  names the file from the release's own version, so `0.1.0+abc1234` and
  `0.0.0-dryrun+abc1234` both reduce to the `X.Y.Z` the tag is; `hand_written`
  returns the text with a blank line and a `---` under it (the blank line matters:
  a `---` directly under a paragraph is a Markdown setext heading, which a test
  holds); `no_hand_written` is the one line a rehearsal prints instead.

- **`tools/release/test_release.py`** — a class `TheHandWrittenNotes` (eight

## Deviations from the spec or the task

- **The task says *`tools/verify.ps1` gains a check*; the check lives in
  `tools/release/selfcheck.py`, which is the script `tools/verify.ps1`'s `release`
  step runs.** Putting it in the PowerShell would have meant a sixth step, a sixth
  name in the `-Only` set, and a Python one-liner in a `.ps1` where every other
  check of the release path is a function in a module with tests. It is the first
  thing that step runs, before the tooling's tests, so a malformed file is the
  first line of the log rather than something after a minute of tests; `-Only
  release` and `--only keys` both reach it. The effect the task asks for holds:
  `tools/verify.ps1` fails on a commit whose `keys/release.pub` the tag path would
  refuse.
- **It reads `release-notes/` too, not only the key.** Both files are *files only
  a tag reads*, for the same reason — no dry run touches either — so closing the
  gap for one and not the other would have left the second half of this task able
  to fail at a tag.
- **README's *State* lost one sentence that was not this task's.** *Nothing above
  has been on a bench* has been false since 22 October (p3.4-02 walked the first
  board; 26 of `docs/bench.md`'s lines are ticked), and this task's release notes
  had to say what a board has shown, so the two now say the same thing. *Phases 0
  to 3 have landed* became *The piles through 3.6 have landed* for the same reason.
- **`keys/README.md` lost *It is not here yet*.** The task asks only that the file
  describe the one form; leaving a paragraph saying the key does not exist beside a
  block naming the key that signed `v0.1.0` would have been worse than the edit.
- **The generated notes' last section was rewritten.** It said *`docs/release.md`
  in this repository is the long version*, and the long version of flashing is now
  `docs/flashing.md`. Deliverable 1 asks for the guide to be found, and a release
  body is where a person with a unit on a desk starts.

## Decisions taken without asking

- **The notes file is refused in `ci-green`, by the same module that assembles the
  body.** The task says *a tag without that file is refused, as a tag without a key
  is*; a tag without a key is refused in `ci-green`, before the builds, so this is
  too. One module (`release_notes.py`) does both the refusing and the assembling,
  so the two cannot drift; the workflow carries no second copy of the rule.
- **A rehearsal is not refused, and says so in one line.** Its version is
  `0.0.0-dryrun+<sha7>`, and writing a `release-notes/v0.0.0.md` to satisfy it
  would have been a fake file in the repository. Instead the body of a dry run
  begins *No hand-written top. `release-notes/v0.0.0.md` is not in the repository,
  which is what a rehearsal of version `0.0.0-dryrun+<sha7>` expects* — so the
  mechanism is visibly exercised on every dispatch, and the tests cover the
  refusing half.
- **The hand-written notes say the Walter release is *none yet*.** The task asks
  which Walter release this goes with, and there is none: the Walter firmware's
  first release is its own phase 7, unrun, and the one Walter that exists runs a
  development build. Rather than leave the question out, the notes answer it and
  say what follows — the box link these images speak is 1.0, every image entry
  carries `requires.link_major: 1`, a Walter is only offered an image of a major it
  speaks, so the RAK is flashed by cable today and a Walter release will be able to
  carry the next one over LTE.
- **The notes say, in the release itself, that this image has not been on a
  board.** *What has been on a board, and what has not* opens *Honestly: **not this
  image***, and names the two files that have met no hardware at all (the base
  `.hex` and the `.bin` over SWD). A first release that claimed more than it has is
  the thing a person would find out the hard way.
- **The release body's links are absolute, at the tag.** A relative
  `docs/flashing.md` does not resolve in a GitHub Release body; `blob/v0.1.0/…` is
  good for as long as the tag is, and a rehearsal's point at the commit it
  rehearsed.
- **`docs/bench.md`'s p0-02 key line is ticked.** It is not a bench line at all —
  it is *the release key, which only Thomas can make* — and it was made on
  20 October and has now signed `v0.1.0`. Leaving an unticked box saying *until it
  exists a tag is refused* beside a published release would have been the only
  wrong reading of that page. Nothing else was ticked; the walks were not run (see
  below).
- **The reader compares key ids case-insensitively** (`fields[1].lower()`), because
  `manifestref.key_id` returns lowercase and a person writing the line by hand
  from a signature is not going to be held to the case of sixteen characters.
- **`docs/flashing.md` says `v0.1.0` nowhere.** It is written as `vX.Y.Z`
  throughout, so the page does not go stale at `v0.2.0`; the release's own body
  names the version.

## One thing found after the tag, and fixed

**`release_notes.py` wrote the notes in the console's encoding.** Diffing the
rehearsed body against the published one showed every em dash of the hand-written
part mangled *in the local artifact* — `sys.stdout.write(text)` on Windows
encodes to cp1252, so an em dash goes out as the single byte `0x97` into a file
GitHub would then read as UTF-8. Reproduced against the code as `v0.1.0` shipped
it, on this host:

```
as v0.1.0 shipped it: b'An em dash \x97 '
  utf-8 decodable: no - 'utf-8' codec can't decode byte 0x97 in position 11
```

**The published release is not affected** — `publish` runs on `ubuntu-latest`,
whose stdout is UTF-8, and the body above is correct UTF-8 as GitHub holds it —
so the tag stands. The fix is in this report's own pull request: the script writes
`text.encode("utf-8")` to `sys.stdout.buffer` when there is one (a stdout a test
has replaced has none), with a test that runs the script **as a process**, because
that is the only way the encoding of its stdout is the real one. It would have
bitten the first person who assembled a body by hand on this machine, or any
future step of the release that did.

`release` step of `tools/verify.ps1`: 269.
