# p3-03 — the-first-boot-profile

A board fresh from the flasher is already a well-behaved member of the Danish
mesh — the right channel from the build, a random admin password nobody knows,
and a **table of console command lines** that runs exactly once — and there is
one written page for making it *this* unit, at the USB port or over the link
([`docs/provisioning.md`](../../../docs/provisioning.md)). Done in one session.

```

Flash: [=====     ]  50.8% (used 413860 bytes from 815104 bytes)  p3-02: 412452 (+1408)
```

(`out/verify/build-repeater_rak4630_single.log`. The scanner is byte for byte

### The profile as shipped

```
# flooded adverts carry two-byte path hashes (spec/SYSTEM.md S-12, meshmaster.dk D-33)
set path.hash.mode 1
```

One line, because the task's rule is "a line only where a document in `spec/` or
the hardware repository gives the value" and that is the one such value. Upstream
floods this node's own adverts at `path_hash_mode + 1` bytes
(`MyMesh::sendSelfAdvertisement`, `examples/simple_repeater/MyMesh.cpp:1035` at
the pin `d9296435`; the periodic flood advert at `:1297`), so upstream's default
of 0 is one byte — and meshmaster.dk's D-33 names this key for repeaters in so
many words ("the best-practice profile's `path.hash.mode` *at least 1* for
repeaters"). The mesh client's own floods already pass 2 in code
(`meshclient::kFloodPathHashSize`); this is the half of S-12 that upstream
decides from a preference, and it was the only half still at upstream's default.

### Why once is exact

The decision is the **same one boolean** p1-01 used for the password, in the same
place: `hasSavedPrefs()` before `the_mesh.begin()` runs upstream's `loadPrefs`.
What is new is that the two things it decides are now atomic together.

Upstream saves after **every** `set`, and `CommonCLI::savePrefs(FILESYSTEM*)`
(`CommonCLI.cpp:143`) does `fs->remove("/prefs.json")` and then writes it again.
So a first boot that saved line by line has a window in which `/prefs.json`
exists and the work is half done — and the next boot, finding the file, would run
no profile at all and never finish it. `TwinOakMesh::savePrefs()` — a public
virtual of `CommonCLICallbacks`, defined inline in `MyMesh.h:195` — is overridden
to **hold** saves for the length of `twinoak::firstBoot()` and perform exactly
one at the end. So:

- power cut **before** that write: no file, and the next boot does the whole
  thing again (`firstboot.state` → `done` on that boot);
- power cut **during** it: `remove` then `open` then write, so what is on flash
  is either no file or a complete one — the same window upstream already has for
  every `set`, and a missing file means "do it again";
- power cut **after** it: the unit is done, and the next boot says `never`.

There is no moment at which the file exists and the work is half finished, and no
second marker anywhere that could disagree with the file. At every other moment
of the firmware's life `savePrefs()` is upstream's and nothing else.

Beside `set`, three things the Danish standard asks for are not `set` keys at
all and are in `docs/provisioning.md` §2 instead: `region default dk` +
`region save` (the default scope), `password <new>` (the admin password), and
the position, which is `set lat`/`set lon` but per site.

Two of upstream's own defaults are worth reading twice, because a fresh unit's
behaviour follows from them and neither is this firmware's choice:

- **`advert.interval` does not stay at two minutes.** `CommonCLI::savePrefs()`
  zeroes `advert_interval` whenever it is below sixty minutes, "now that device
  has been manually configured" — and the profile's one line is a manual
  configuration as far as upstream is concerned. So a provisioned unit sends no
  two-minute local adverts; the boot advert and the 47-hour flood advert are what
  announce it. That is also what the Danish standard asks for
  (`advert.interval 0`), reached by upstream's own rule rather than by a line of
  ours. Upstream does not call `updateAdvertTimer()` on that path, so the timer
  already scheduled in `begin()` fires once at about two minutes and stops; ours
  does not call it either, because the smallest decision is upstream's behaviour.
- **`guest.password` empty is not "no guest".** `MyMesh::handleLoginReq`
  (`MyMesh.cpp:90-110`) handles a blank password by looking the sender up in the
  ACL and, when it is not there, falling through to `strcmp(data,
  _prefs.guest_password)` — which an empty one matches. So out of the box a
  stranger's blank login **succeeds at guest permission**. That is upstream's
  design and not a defect; `docs/provisioning.md` §1 and §2 say so, and setting a
  guest password is therefore a decision a person takes rather than a default.

## Deviations from the spec or the task

**The console's reply buffer had to grow, and that is a bug fix the tenth setting
forced.** Upstream's console gives its interpreter `char reply[160]` on the
stack, and upstream's own `sensor list` can write past it: it adds a line while
it has written fewer than 134 bytes and then appends `... next:<i>`. p1-05
measured that, gave the **box link** a 64-byte guard behind the same window, and
left the console as upstream has it — because with five keys the longest listing
was 148 bytes. With nine it reached 162 on a release image (p1-06 recorded it);
with ten, upstream's header becomes `10 vars` instead of `9 vars` and an
**ordinary** fresh node reaches **160** characters, whose NUL would have gone one
byte past the buffer. `src/roles/repeater/main.cpp` now gives the console the
same window and the same guard as the session, zeroes both before each line and
prints the window's own 159 characters — which is what the link already sends.
The cost is one character of output: the digit of `... next:5` on the first page.
The hint that there is more is still there, `sensor list 5` prints all five
remaining keys on one page, and `sensor get <key>` is unaffected.
`test/test_settings` measures both cases (160 and, on a release version string,
163) by running upstream's own loop over our table.

**Flash is +1408 bytes and RAM +256.** The linker map
(`out/build/repeater_rak4630_single/firmware.map`) accounts for it:

| | bytes |
|---|---|
| `Profile.cpp.o`: `runFirstBootProfile` 376, `runProfile` 276, `replyAccepted` 100, `noteState` 64, `stateText` 8, the table and its count 12, string literals 119 | **955** flash |
| `g_state[32]`, `.data` — the state's buffer, and the only thing this task keeps at run time | **32** flash + **32** RAM |
| `FirstBoot.cpp.o` grew from about 170 bytes to about 430: `firstBoot()` 172, the `MeshCli` adapter and its vtable 76, the rest unchanged | **+260** flash |
| the console's reply buffer, moved from `loop()`'s stack into `.bss` and 64 bytes longer | **224** RAM |
| the rest — `TwinOakMesh::savePrefs`/`holdPrefsSaves`/`releasePrefsSaves` and the vtable slot, the tenth settings key, and `setup()`'s two new console lines with their literals | **161** flash |

RAM's 256 is exactly 224 + 32 and nothing else: the profile keeps no state on the
board beyond the word `done`.

**`tools/linkloop/` did not build at all before this task, and that is a finding
about p3-01.** Its `linkloop.cpp` still included `"app/Settings.h"`,
`"clock/ClockKeeper.h"`, `"link/session/Session.h"` and fourteen more at their
pre-split paths; p3-01 moved every file of `src/` into `common/` and
`roles/repeater/` and src-rooted the includes **inside** `src/`, but
`tools/linkloop/` is outside it and was missed. `bash tools/linkloop/check.sh`
failed at the compiler. The seventeen includes are fixed here, `check.sh`
compiles `Profile.cpp` with the rest, and the whole script passes (exit 0). It is
not in `tools/verify.ps1` — it needs a host compiler — which is why nothing
caught it; whether it should be is a follow-up for the reviewer and not a change
this task makes.

**`docs/bench.md`'s new section is §10, not §9.** The task says "9. First boot
and provisioning"; §9 is NoiseScope, written by p3-02 after this task file. The
alternative was to renumber, and seven lines of §1, §4 and §5 name sections by
number. First boot is appended rather than put where the rig would reach it,
with a warning at its head that the first line erases the node's identity — so
it is the section to walk last or on a spare module.

**The profile's command interface is `twinoak::link::CliAccess`**, the interface
the box link already defines (`src/common/link/session/Interfaces.h`), rather
than a second one of the same shape. It is the same concept — one command line
in, one reply out, with upstream's own 160-byte window — and reusing it means the
board hands the profile the same kind of object it hands the session, and a test
writes one fake rather than two. The cost is that `firstboot/Profile.h` includes
a header of `common/link/`; nothing of the link is linked by it on the board, and
`[env:native]` already compiles that directory.

## Decisions taken without asking

1. **One line in the table, and the rest in the report.** The task's rule is
   explicit — "add a line only where a document in `spec/` or the hardware
   repository gives the value" — and only S-12 does. meshguide.dk's
   `lib/checks.js` is the network's own standard and I have put every one of its
   recommendations in the table above beside upstream's default, but it is
   neither `spec/` nor the hardware repository, and most of what it recommends is
   **per site anyway**: the three delays come from how many neighbours a unit
   hears, which a unit that has never been switched on cannot know. Filling the
   table from it is the reviewer's, in one pass, with the arithmetic already
   done.
2. **The state is per boot and in RAM.** The question `firstboot.state` answers
   is "what did *this* boot do", so a unit provisioned last month says `never`.
   Persisting it would need a file of our own with nothing to say that
   `/prefs.json` does not already say, and would be a second marker that could
   disagree with the one the once-ness rests on.
3. **A refused line does not stop the run.** The lines are independent settings:
   a unit with four of five is better than a unit with one of five, and the one
   that was refused is on the console and in `firstboot.state`. (`provision`
   behaves the *other* way, and says why: a person's file is a sequence they
   wrote.)
4. **The profile borrows the console's two buffers.** `command[160]` and
   `reply[224]` are file-scope statics in `main.cpp` and are idle while `setup()`
   runs, so the profile is given them rather than putting 384 bytes on a stack
   that p1-05's own comment calls 2 KB — and there is one place that says how
   much room upstream's interpreter has.
5. **`firstboot.state` is appended as the tenth key**, as `Settings.cpp`'s own
   rule says every later task's key must be, so that nothing `docs/link.md`,
   `docs/bench.md` or a report already numbered moved. The cost is the character
   above.
6. **The profile's table carries a reason per line, as a C++ field** (`why`),
   held to a non-empty string by a test, and `docs/provisioning.md` prints the
   same table with the reasons as `#` comments — which is the format
   `linkcli.py provision` reads. So "the file format is the profile's own" is
   literal: the shipped table written out *is* a provisioning file.
7. **A provisioning file is read before anything is sent.** An over-long line, a
   control character, a `region load` or one of the four commands that never
   answer is refused with the file and the line number and the link is never
   opened. A half-sent file is the thing the tool exists to avoid.
8. **`provision` prints four stars, never the real length**, and prints no reply
   at all for a password line — because upstream's refusals can echo the whole
   line (`unknown config: guest.passwordX hello`), not only its success.
9. **The three replies that are not `OK`.** `provision` knows two exceptions,
   each read off upstream's own branch: a `password` line is taken when the reply
   begins `password now:`, and a `region` line is taken when the reply does not
   begin `Err`. Without them a complete provisioning file could not be a single
   file, and the alternative — telling a person to send those lines by hand — is a
   procedure with a hole in it.
10. **`--first-boot` on `tools/linkloop/`**, with a miniature of upstream's
    `set`, `region` and `password` branches behind it. `provision` needed
    something that answers a `set` the way upstream does; the alternative was to
    test the tool against nothing.
11. **The console prints the first refused line, not the reply.** The command is
    ours and carries no password (a test); the reply may.

## Not verified here (and why)

`docs/bench.md` §10, "First boot and provisioning", seven lines. In short, and
each of them needs the board the session does not have:

- **A first boot is a first boot.** `erase`, reset: a new `Repeater ID:`, both
  `First boot:` lines, `sensor get firstboot.state` → `done`,
  `get path.hash.mode` → `1`, `get radio` → `869.618,62.5,8,8`,
  `get guest.password` → empty. Every one of those is a string this session read
  out of upstream's source; none of them has been printed by a board.
- **It runs once, and a reboot proves it.** No `First boot:` line the second
  time, `firstboot.state` → `never`, and `path.hash.mode` still `1`.
- **A power cut in the middle leaves no half-provisioned node.** `erase`, reset,
  and pull the power during the first second, three or four times: either both
  `First boot:` lines appear again (the write never happened) or they do not and
  `get path.hash.mode` says `1` (it did). **No `First boot:` line together with
  `path.hash.mode` → `0` is the failure this is looking for.** The arrangement
  is argued above and tested against a fake; only a real flash and a real power
  cut can show it.
- **A provisioning session at the USB port**, `docs/provisioning.md` §3 line for
  line, and one over the link with `linkcli.py provision` — including a
  deliberately broken line in the middle, to watch the run stop and nothing
  after it be sent. The tool's half of this is exercised against the firmware's
