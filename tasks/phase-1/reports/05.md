# p1-05 — local-management

The box beside this one can now manage it without the radio. `CLI` runs a line through
**upstream's own interpreter** with a sender timestamp of 0 — a command typed on the console,
console privileges and all — and answers with what it wrote; our five settings are a portable
table on upstream's `sensor` CLI, so the USB console and a **mesh admin** reach them by the same
road; `src/link/attention/` is §8 as one small portable machine (the wake bytes, the 300 ms gap,
ten sends a second apart, the queue, the hourly limit per reason); and `SLEEP_NOTICE` is the
belief that the Walter is asleep, which holds back every event but `EV_BOOT` and `EV_ATTENTION`.
`HELLO`'s `caps` is `0x61` now — `CLI`, `ATTENTION`, `TIME_PERSIST` — from three non-null
pointers and nothing else. Not one file of upstream's is touched. Done in one session.

## Every console command that never returns, and what the link does

From the source at the pin (`d9296435`), `src/helpers/CommonCLI.cpp:182`'s `handleCommand`, there
are exactly **three call sites and four command words**, and no other path out of the interpreter
fails to return (`grep -n "reboot()\|powerOff()\|NVIC_SystemReset\|while (1)"` over `CommonCLI.cpp`
and `MyMesh.cpp` finds these three and nothing else):

| Line | Command (matched with `memcmp`, so any line that *starts* with it) | What happens | What the link does |
|---|---|---|---|
| `:183`–`:184` | `poweroff`, `shutdown` | `_board->powerOff()` — `NRF52Board`'s SYSTEMOFF | No response is built and none is owed. The handler does not try to out-run it: our `TwinOakBoard::powerOff()` writes the clock's file first (p1-04), and then the node is off until the kill line or a power cycle. |
| `:185`–`:186` | `reboot` | `_board->reboot()` — `NVIC_SystemReset` | The same, and the link comes back with `EV_BOOT` a second later, a new `boot_id` and `reset_reason` 4. The clock's file was written on the way down, so the restored clock is a few seconds on and not an hour. |
| `:187`–`:190` | `clkreboot` | sets upstream's clock to its 2024 default, then `_board->reboot()` | The same restart — and the clock keeper restores the *saved* time on the boot that follows, so `clkreboot` does not put this node behind itself (p1-04's decision; it is the one command whose documented effect this firmware deliberately defeats). |

So the rule in the code is: **the response to those lines is not owed**. The handler calls
`runCommand` and never comes back; nothing is queued, no timer is armed, and the Walter's own
rule (§5.7: "treats silence after such a line as the expected outcome") is what makes it correct.
`tools/linkcli.py cli "reboot"` prints *(no answer, which is what `reboot` means: the node
restarted)* rather than calling the link down, and `tools/linkloop/`'s fake console really does
exit the process for those four words so that path is exercised with no board.

Two more lines are worth knowing about, neither of which fails to return:

- **`erase`** reformats the file system (`CommonCLI.cpp:269`, `sender_timestamp == 0` only — so
  this link can do it and a mesh admin cannot) and *does* answer. It destroys the identity, the
  preferences and the clock's file; the node keeps running with none of them until it restarts.
- **`region load`** (`:320` → `MyMesh::startRegionsLoad`) puts the interpreter into a mode where
  every following line is a region definition until a **blank** one ends it
  (`MyMesh.cpp:1197`–`:1206`, `StrHelper::isBlank`). A blank line is not a legal `CLI` request, so
  that mode cannot be left over this link in the obvious way — but `isBlank` treats a line of
  spaces as blank (`TxtDataHelpers.cpp:22`), so `cli " "` is the way out, and a `reboot` is the
  other. It is on the bench list and in `docs/link.md` §2b as the one line not to send from here.

## Who may run `sensor set` over the mesh

**An admin, and nobody else** — and it is upstream's own permission check that says so, not ours.
From the source at the pin:

- `MyMesh::onPeerDataRecv` (`examples/simple_repeater/MyMesh.cpp:702`) runs a text message
  through the interpreter only inside
  `else if (type == PAYLOAD_TYPE_TXT_MSG && len > 5 && client->isAdmin())`, and `isAdmin()` is
  `(permissions & PERM_ACL_ROLE_MASK) == PERM_ACL_ADMIN` (`src/helpers/ClientACL.h:33`, `:11`).
  A client becomes admin in one of two ways: a login with the admin password
  (`MyMesh::handleLoginReq`, `MyMesh.cpp:102`–`:103`, `perms = PERM_ACL_ADMIN`), or an explicit
  `setperm <pubkey> <perms>` from a console or another admin (`MyMesh.cpp:1240`). A guest
  password gives `PERM_ACL_GUEST` and no CLI at all.
- `sensor set` carries **no** `sender_timestamp == 0` condition
  (`src/helpers/CommonCLI.cpp:289`), unlike `erase` (`:269`), `log` (`:434`), the three
  `stats-*` (`:437`, `:439`, `:441`), `set freq` (`:713`) and `get prv.key` (`:832`). So an admin
  over the mesh may run it, which is exactly what `walter.wake` is for.
- And a nonzero timestamp is not something a sender can avoid: `onPeerDataRecv` only executes a
  message whose `sender_timestamp >= client->last_timestamp`, and treats
  `sender_timestamp == client->last_timestamp` as a **retry** that is answered without running
  the command (`MyMesh.cpp:710`–`:735`). A fresh client's `last_timestamp` is 0, so a message
  carrying timestamp 0 is read as a retry and never executed; after any real message, 0 is
  refused as a replay. The console-only commands are therefore genuinely console-only, which is
  the assumption §5.7 rests on when it says this link gets more than the mesh does.

`docs/ARCHITECTURE.md` §4 and `docs/link.md` §2b say the same in a sentence each.

## The reply window, and the one command that can write past it

Upstream's console loop gives its interpreter `char reply[160]` (`src/main.cpp`, which is
upstream's `main.cpp` unchanged in this respect), and **three of its own branches assume that
number as a literal**: `snprintf(reply, 160, ...)` and `_region_map->exportTo(reply, 160)`
(`CommonCLI.cpp`, the region branch), `StrHelper::strncpy(&reply[14], _prefs->password, 160-15)`
(the `password` branch) and `get owner.info`'s hand-written loop at `reply - start < 159`. So the
window this handler passes is `kCliReplyMax` = **160**, not 161: a reply is at most 159 characters
and its NUL, here exactly as on USB, and it fits the protocol's 0-to-160-byte field with a byte to
spare.

Behind that window the session keeps **64 guard bytes**, zeroed before every line and read after
it. The one upstream command that can write past 160 is **`sensor list`**: it adds a
`<name>=<value>\n` line while it has written fewer than 134 bytes and then appends
`... next:<i>`, so the worst case is 133 + the longest line + 11 — which with our longest value
(`fw.version`, a 78-byte line) is 222 bytes, 62 past the window. 64 is that number rounded up.
`neighbors` has the same 134-byte shape with a 24-byte record and reaches 159; `password <new>`
reaches 159; nothing else comes close.

It cannot happen **today**: `fw.version` is index 0, so it is either skipped or the first line,
and with our five keys the longest listing is 148 bytes. It can happen as soon as task 06 adds a
sixth key, which is why the guard is there and why the key order is chosen rather than
alphabetical (`src/app/Settings.cpp` has the arithmetic above the table, and
`test/test_settings` runs upstream's own loop over our table):

- a freshly booted node lists **all five on one page**, 148 bytes of the 160;
- a node whose counters have grown wide (`link.errors` 65535, `walter.seen` seven digits) lists
  four and `... next:4`, and `sensor list 4` is how `clock.state` is then read. The key that gets
  pushed off is pushed by a width, which is why the two counters are last and `clock.state`
  — four possible words — is behind them.

If a line ever does write into the guard, the session counts it (`cliOverruns()`) and sends the
window's own bytes, which is exactly what the console would have printed. **Truncation, never an
overrun**, and the bytes decide rather than the length the interpreter reports.

## Deviations from the spec or the task

- **`SLEEP_NOTICE` answers `ERR_UNSUPPORTED` when there is no attention machine, and §4's table
  calls it "always".** The belief that the Walter is asleep lives in the machine — it is the same
  §8 state as a pending attention — so a build without that interface has nowhere to keep it, and
  this session's rule throughout is that a capability is an interface that is there. On every
  board this firmware builds the machine is present and the answer is `kOk`; the only caller that
  can see the refusal is a test. The same shape was p1-03's for `TIME_*` and p1-04 resolved it the
  same way.
- **Attention reason 1 is never raised on this board.** The task says it is sent after `EV_BOOT`
  *only if* the Walter was believed asleep in the surviving RAM of task 04 — and task 04 found
  that no place in this board's RAM can be shown to survive a reset, so that fact cannot be
  known. `AttentionMachine::noteBoot(reset_reason, walter_was_asleep, now)` is the seam, it is
  tested both ways, and `src/link/BoardLink.cpp` passes `false` with the reason in a comment. An
  awake Walter learns everything that event carries from `EV_BOOT`, which is queued either way.
- **The pending reason is cleared when the request that ended it has been *answered*, not when it
  arrived.** §8 says the repeats end at "any valid request" and that the reason "stays visible in
  `STATUS` until the Walter has made a request, so a Walter that woke for its own reasons sees it
  too". Clearing it on arrival would make the second sentence useless in the one case it is for —
  a Walter that wakes and asks `STATUS` would read 0 and never learn why it was wanted. So the
  request stops the sends at once and the reason survives into that request's own response; the
  next request reads 0. One extra interface method (`requestAnswered`) and a test either side of
  it.
- **A retried `SLEEP_NOTICE` does not wake the node's belief.** §3 answers a retry from the
  one-entry memory without running the handler, so a `noteRequest` that cleared the flag for
  every request type would leave a Walter that lost its response believed awake. The machine is
  told which request arrived and leaves the flag alone for that one type; its own handler is what
  sets it.
- **`decodeCli` refuses a line that is not plain text**, which is a rule the task states and §5.7
  only implies ("1 to 160 bytes of UTF-8"). It is in the codec beside the length rule, because
  both are "a field is not a legal value" (§3, `kErrMalformed`), and the predicate is
  `isPlainText` in `src/link/codec/Bytes.{h,cpp}` with its own list of what it refuses. The
  fixture's own `CLI` cases are ASCII and unaffected.
- **`src/link/session/Interfaces.h` grew on two interfaces p1-03 declared.** `CliAccess::runCommand`
  takes `char*` rather than `const char*` — upstream's `handleCommand` writes into the line in
  place (`MyMesh.cpp:1232`), and the session hands it a copy for exactly that reason — and
  `AttentionAccess` gained the six methods the session drives §8 with. Everything else about that
  file is unchanged, and a null pointer still means `kErrUnsupported`.
- **`src/board/target.cpp`'s settings table moved into `src/app/Settings.{h,cpp}`** and the board
  keeps the six-line host behind it. The task asks for native tests of the order, an unknown key
  and a read-only `set`, and `TwinOakSensors` cannot be compiled on a host; this is the
  repository's own rule that logic goes in portable files. `fw.version` keeps the place p1-01 gave
  it and `walter.wake` is inserted after it; `link.errors` and `walter.seen` keep p1-03's relative
  order, and `clock.state` moves from fourth to last for the paging reason above.
- **`SerialTransport::worstPassMicros()` still has no way to be read without a debugger.**
  `docs/bench.md`'s p1-03 line said to "wait for task 05's `CLI` over the link"; the console
  arrived, but upstream's interpreter has no such command and this task added no settings beyond
  the five `docs/ARCHITECTURE.md` §4 names. Exposing it would be a sixth key — which is also the
  key that paging would hide — so the bench line is corrected to say "read it with the debugger"
  and the reviewer can have the key in task 06 if the number is wanted in service.

## Decisions taken without asking

- **The reply window is 160 and the guard is 64**, for the reasons measured above. The guard is
  checked after every line and two counters (`cliTruncations()`, `cliOverruns()`) are kept; they
  are not on the link and nothing reads them but a debugger and this report. A reply that filled
  the window counts as a truncation, because 159 characters is where upstream stops being able to
  tell a complete answer from a cut one.
- **The line is copied into the session's own buffer** (`line_`, 161 bytes) rather than passed as
  the frame's bytes, because the interpreter writes into it; and both buffers are members in
  `.bss` rather than locals, because this board's stack is 2 KB (p1-04's reading of the linker
  script) and 385 bytes of it is a quarter.
- **`walter.wake` accepts `1` and nothing else**, and accepting it means "the machine was asked".
  Whether an attention was actually raised is the hourly limit's business, and upstream's CLI has
  only two words for a `set` — `ok` and `can't find custom var` — so there is nothing to say "yes
  but not now" with. `sensor get walter.wake` is where that is read, and it answers `1` while
  **any** reason is pending, which is what `docs/ARCHITECTURE.md` §4 asks for.
- **A queued reason is stamped with the rate limit when it enters the machine**, not when it
  becomes pending. "Counted from when it was raised" is ambiguous for a queued one; the queue
  normally drains within seconds of the next request, so the two readings differ by nothing that
  matters, and stamping on entry cannot be gamed by a reason that sits in the queue for an hour.
- **A promoted reason starts its own sequence, wake bytes and all.** The Walter has just made a
  request so it is awake, but that reason has never been sent and two `0x00` bytes on an idle line
  cost nothing; a receiver reads them as two empty frames and drops them (`linkcli.py` already
  did, from p1-03).
- **The queue is five deep** — one reason pending and the other five behind it, and no reason can
  be in it twice, so it cannot overflow. The depth is `kAttentionReasonMax - 1`, with a bounds
  check all the same so that a seventh reason added by a later minor version fails visibly.
- **The wake bytes are the one thing this session sends that is not a frame.** `outgoing()` now
  returns a pointer and a length that are usually the writer's and are those two bytes when §8
  asks for them; the transport is unchanged and does not know the difference.
- **An attention gets the wire only when nothing else wants it**: a waiting request is handled
  first (the Walter is talking) and an unsent frame is never interrupted. A send is counted when
  the bytes have gone, not when the frame was built, so a pass where the UART had no room does not
  cost a repeat.
- **The attention machine keeps no clock of its own.** Every method takes `now_ms`, and every
  comparison is a signed difference, so a `millis()` wrap is one subtraction and a test can wind
  time in a line. It also means the hourly limit is forgotten on a reset, which errs towards
  telling the box rather than not.
- **`SLEEP_NOTICE`'s `expect_back_s` is recorded and not acted on.** §8 gives it no behaviour
  (0 = unknown), and inventing one — ending the belief when the time passes, say — would make this
  node guess at the other box's business. It is readable (`expectBackSeconds()`) for the day the
  supervisor wants it.
- **`eventAllowed(type)` is public on the session.** §8's holding rule has no visible effect today
  — the only events this firmware sends are the two it exempts — so the rule is a predicate with
  its own tests, and phase 2's `EV_MESH_REPLY` asks it before it sends. The alternative was to
  write the rule in phase 2 instead, where this task's acceptance criterion could not see it.
- **The fake console in `tools/linkloop/` answers upstream's `sensor` branch and six canned
  lines.** It compiles the firmware's real settings table and the real machine behind
  `walter.wake`, and reproduces upstream's 134-byte cut-off, so what `cli "sensor list"` prints
  through the pipe is what the board prints. What it cannot be is upstream's interpreter; its
  header says so, and the four restarting words really do end the process.
- **`linkloop` waits on `stdin` with `select()`** (POSIX; it is built by `check.sh` on Linux or in
  the container, never on Windows) so that one program both answers requests and emits an
  attention on time. `--wake` raises one at startup, which is what lets `listen` show the whole
  sequence with nothing but a laptop.
- **`linkcli.py cli` treats the four restarting words as prefixes**, as upstream's `memcmp` does,
  and reports silence after one of them as the expected outcome — including the broken pipe that
  the loopback's own exit produces, which means the same thing.
- **The rails test forbids printing anywhere under `src/link/`**, rather than looking for a
  password or a reply beside a print. The directory has no reason to print at all, the allowlist
  of `Serial` calls is six entries long, and a rule that cannot be worked around by renaming a
  variable is worth more than one that can.
