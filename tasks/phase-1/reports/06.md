## The power-management question, from the source at the pin

**Can upstream's nRF52 power management shut this node down, and at what voltage?** Short answer:
**only at boot, only below 3 300 mV — and on this board, from this task on, it cannot at all,
because the reading it checks is 0 at that moment.** The long answer is the one the task asked
for, read out of the pinned tree (`d9296435`), because this is a decision for the reviewer:

**At boot.** `RAK4631Board::begin()` calls `checkBootVoltage(&power_config)` after configuring
`SX126X_POWER_EN` as an output and *before* pulling it high
(`variants/rak4631/RAK4631Board.cpp:63`). That function
(`src/helpers/NRF52Board.cpp:108`–`:135`) does:

1. `initPowerMgr()` — which is also the only thing that copies `RESETREAS` into the board object,
   and therefore the reason the box link's `STATUS` has a reset reason at all (p1-03);
2. `boot_voltage_mv = getBattMilliVolts()` (`:112`);
3. returns at once if `config->voltage_bootlock == 0`, or if `isExternalPowered()` — USB
   attached — is true (`:114`, `:117`–`:121`);
4. **`if (boot_voltage_mv > 1000 && boot_voltage_mv < config->voltage_bootlock)`** →
   `initiateShutdown(SHUTDOWN_REASON_BOOT_PROTECT)` (`:128`–`:132`), which never returns.

`voltage_bootlock` is `PWRMGT_VOLTAGE_BOOTLOCK`, **3300** mV
(`variants/rak4631/variant.h:109`), and `NRF52_POWER_MANAGEMENT` is defined for our environment
(it is in upstream's `variants/rak4631/platformio.ini:12` and in our copy of that block).
`RAK4631Board::initiateShutdown` (`RAK4631Board.cpp:28`–`:36`) pulls `SX126X_POWER_EN` low, calls
`configureVoltageWake(PWRMGT_LPCOMP_AIN, PWRMGT_LPCOMP_REFSEL)` — **AIN3, which `variant.h:112`
names as P0.05 = `PIN_VBAT_READ`**, with REFSEL 4 = 5/8 VDD — and enters SYSTEMOFF. So the node is
off until that comparator sees the pin rise, until USB is plugged in, or until the power is cycled.

**At run time: nothing.** `SHUTDOWN_REASON_LOW_VOLTAGE` exists (`src/helpers/NRF52Board.h:11`,
commented "Runtime low voltage threshold") and `RAK4631Board::initiateShutdown` tests for it, but
**no code at this pin ever passes it**: `grep -rn "initiateShutdown\|SHUTDOWN_REASON_LOW_VOLTAGE"`
over `src/`, `examples/simple_repeater/` and `variants/rak4631/` finds the definition, the string
in `getShutdownReasonString` (`NRF52Board.cpp:101`), the comparison, and exactly one call site —
`checkBootVoltage`'s, with `SHUTDOWN_REASON_BOOT_PROTECT`. There is no low-voltage shutdown while
the node runs, and nothing of ours adds one.

**What that means on this board, and what this task chose.** `getBattMilliVolts()` is now
INA3221 channel 2's bus voltage out of the reader's cache, and **0 when that channel is not
valid** (`src/board/target.h`). At `checkBootVoltage()`'s moment the reader has not run — it is
brought up in `TwinOakSensors::begin()`, which `src/main.cpp` calls later in `setup()` — so the
reading is 0, which fails upstream's own `> 1000` guard against "an ADC glitch or an
uninitialised read". **The protection therefore never fires on this board.** That is deliberate,
for two reasons:

- the wake source it would arm is **AIN3 = P0.05**, the pin this adapter does not wire
  (`docs/ARCHITECTURE.md` §3). A repeater on a mast that enters SYSTEMOFF with a comparator
  watching a floating pin may never come back, and the one thing worse than a node that drains
  its pack is a node that is silently off;
- the pack has its own protection board (Meshnology, `PROJECT-KNOWLEDGE.md` §5) and the Walter is
  the supervisor with the reset and kill lines. Attention reasons 2 and 3 are this firmware's way
  of saying "the battery is going", and they go to the box that can do something about it.

**It is the reviewer's to change, and the way to change it is one call.** Sampling channel 2
inside `TwinOakBoard::begin()` *before* `RAK4631Board::begin()` — which means bringing `Wire` up
ourselves first, because upstream's `begin()` is what calls `Wire.begin()` — would give
`checkBootVoltage()` a real number and turn the protection on, at 3 300 mV, with the LPCOMP wake
left unwired. I have not done it.

**And it removed a hazard.** Until this task `getBattMilliVolts()` was upstream's eight ADC
samples of `PIN_VBAT_READ` with `ADC_MULTIPLIER` = 3 × 1.73 × 1.187 × 1000
(`variants/rak4631/RAK4631Board.h:9`, `:23`–`:33`), and that pin is `pinMode(…, INPUT)` and not
wired on this adapter. A floating input needs to read only 16 % to 54 % of the ADC's full scale
for the result to land inside 1 000–3 300 mV, so **the p1-05 image could have refused to boot on
battery, with a wake source that cannot fire**. Nothing has ever been measured; the bench list
has a line for `get pwrmgt.bootmv` (which now says `0 mV`) and for confirming that a node with
the pack at 3.2 V does come up.

## Upstream's BME280 had to leave the build too

The task let this task choose: read the BME280 "either through upstream's manager or beside it,
and the report says which and why". **Beside it**, and upstream's own support is out of the board
environment (`ENV_INCLUDE_BME280` no longer defined; `test/test_rails` holds it and
`ENV_INCLUDE_INA3221` out of every board environment). The reason is the acceptance criterion
about I2C, and it is not something `docs/ARCHITECTURE.md` §3 foresaw:

- upstream's `query_bme280` samples the part **inside `querySensors`**: `MODE_FORCED` set at
  init, then `takeForcedMeasurement()`, which writes `ctrl_meas` and spins on the status register
  until the conversion finishes (`src/helpers/sensors/EnvironmentSensorManager.cpp:271`–`:290` at
  the pin; `Adafruit_BME280.cpp`'s own loop);
- `querySensors` is on the path of **`LPP_GET`** — that message has to answer with *exactly* what
  a mesh telemetry request gets, and a mesh telemetry request goes through
  `MyMesh::handleRequest` → `sensors.querySensors` (`examples/simple_repeater/MyMesh.cpp:250`);
- so with it in the build, a request on the box link would do I2C **and wait ~10 ms for a
  conversion**, inside the 250 ms the protocol gives the whole answer and inside the slice
  `loop()` gives the link.

Two drivers on one chip is not an option either: upstream's instance is a file-static
(`static Adafruit_BME280 BME280;`), so a second one of ours would fight it over `ctrl_meas`.
Ours therefore drives the part — with the **same pinned Adafruit library**, for Bosch's
compensation arithmetic, which is not something to write twice — in **`MODE_NORMAL`** with a
one-second standby, X1 oversampling and the filter off. A sample is then three register reads and
no waiting, it happens on our own schedule (every five seconds), and the one cached sample serves
`ENV_GET`, `LPP_GET` and the mesh alike. "The link's numbers and the mesh's agree" is not a
property to be checked here: they are the same bytes of the same struct.

## The LPP: one field list, two appliers

`LPP_GET` must answer with the bytes a mesh telemetry request gets. The mesh's bytes are
upstream's buffer written by upstream's library (`MyMesh::handleRequest`, `MyMesh.cpp:241`–`:259`:
`addVoltage(1, batt)`, then `sensors.querySensors(perm, lpp)`, then `addTemperature(1, mcu)`
unless it is NaN), and `CayenneLPP` is neither host-portable nor something a link handler may
reach for. So:

- **one field list**, portable and tested: `ourFields()` is what `TwinOakSensors::querySensors`
  adds, and `telemetryFields()` is that list with upstream's two channel-1 fields around it, in
  upstream's order;
- **two appliers**: `querySensors` walks `ourFields()` and calls `addVoltage`/`addCurrent`/
  `addTemperature`; `LPP_GET` walks `telemetryFields()` and encodes it with `encodeLpp()`, twenty
  lines that mirror `CayenneLPP::addField` at **1.6.1** — the same multiplier table, the same
  truncation towards zero of the float product, the same two's complement, the same most-
  significant-byte-first order, the same overflow check, and the same cap
  (`MAX_PACKET_PAYLOAD - 4` = **180**, `MyMesh.cpp:866` with `MeshCore.h:20`).

`test/test_power` holds the two compositions against each other for every `perm_mask` from 0 to 7
and both against hand-computed bytes, and `tools/linkloop/` prints the real thing from a laptop:

```

  channel 1  self       voltage        4.000 V
  channel 2  panel      voltage       18.090 V
  channel 2  panel      current        0.120 A
```

**The channel table is `docs/link.md` §2d** — 1 upstream's own, 2 panel, 3 battery, 4 load, 5 the
enclosure — and `test/test_power` holds it with a `static_assert`, because a renumbering is a
change to something MeshMaster will have named and not something a test run should have to find.

### CayenneLPP 1.6.1 cannot encode humidity or pressure

> **14 November 2026 — this section is wrong, and the rest of it is left standing so that the
> mistake can be read.** `isType()`'s gate is a `switch` whose cases *fall through* to one
> `return true`, and each case is wrapped in `#ifndef CAYENNE_DISABLE_<type>`. The list below is
> the cases this report's author could see between the `#ifdef` lines; the gate in fact names
> **every** type the header names — `LPP_RELATIVE_HUMIDITY`, `LPP_BAROMETRIC_PRESSURE` and
> `LPP_POWER` among them — and nothing in this build defines a `CAYENNE_DISABLE_*`. So
> `addRelativeHumidity` and `addBarometricPressure` write their bytes and always did, as
> upstream's own `query_bme280` assumes they do. The enclosure's humidity and pressure were off
> the mesh for a year because of this paragraph; `p3.12-01` put them on LPP channel 5 and added
> `test/test_cayennelpp`, which links the library in `[env:native]` so that no claim about it is
> ever a transcription again. `LPP_POWER` is still not sent, now by choice: meshmaster.dk
> computes the watts from the volts and the amps it already has.

Worth knowing, and it is upstream's library and not our choice. `CayenneLPP::addField` refuses
any type its `isType()` gate does not list, and that gate lists only `LPP_DIGITAL_INPUT`,
`LPP_DIGITAL_OUTPUT`, `LPP_VOLTAGE`, `LPP_CURRENT`, `LPP_ANALOG_INPUT`, `LPP_ANALOG_OUTPUT`,
`LPP_TEMPERATURE`, `LPP_ACCELEROMETER`, `LPP_ALTITUDE`, `LPP_GYROMETER` and `LPP_GPS`
(`src/CayenneLPP.cpp`, `isType`) — while `getTypeSize` and `getTypeMultiplier` in the same file
handle twenty-odd more. So **`addRelativeHumidity`, `addBarometricPressure` and `addPower` write
nothing and return 0**, silently, and a stock MeshCore repeater with a BME280 reports temperature
and altitude only. Consequences here:

- our LPP carries the enclosure's **temperature** and not its humidity or pressure. `ENV_GET` on
  the box link carries all three, which is where MeshMaster reads them;
- `addPower` (watts per channel, which upstream's own INA3221 query calls) would have written
  nothing either, so nothing is lost by our not calling it;
- `src/power/Telemetry.cpp`'s mirror has a table of **only the three types this firmware
  writes**, so a field of a new type has to be added there deliberately rather than silently
  dropped.

## Deviations from the spec or the task

- **Upstream's BME280 support is out of the build, which `docs/ARCHITECTURE.md` §3 said would
  stay in.** *Upstream's BME280 had to leave the build too*, above, has the whole reason: it
  samples the part inside `querySensors`, and `querySensors` is on `LPP_GET`'s path. §3 is
  corrected, `platformio.ini`'s "left out on purpose" list says why in nine lines, and
  `test/test_rails` fails a board environment that turns it back on. The library itself stays a
  pinned dependency: we use it for the compensation arithmetic.
- **The enclosure's humidity and pressure are not in the Cayenne-LPP.** CayenneLPP 1.6.1 refuses
  those two types (above). The task asks for "the three channels' voltage and current" in the LPP,
  which is satisfied; what is missing against a reasonable reading of "the link's numbers and the
  mesh's agree" is two quantities the library cannot carry. They are on the link, and the
  alternative — writing them as `LPP_ANALOG_OUTPUT`, which the library does encode — would be
  inventing a meaning for a channel MeshMaster has to interpret, so it is the reviewer's call and
  not a session's.
- **`sensor list` can no longer print every key on one page**, and on a *release* image the first
  page is two bytes longer than upstream's reply window and comes back cut at 159 characters.
  Seven keys cannot be ordered to avoid that: the `fw.version` line is 69 bytes plus the version
  string, which the release build chooses, and upstream's 134-byte cut-off then lands wherever it
  lands. The session's 64 guard bytes absorb the write and count it (p1-05 built them for exactly
  this), `sensor get <key>` always works, `sensor list 5` prints the pair, and
  `test/test_settings` measures all three cases including the one that is cut. The alternative was
  renaming the two keys shorter than the task spells them.
- **`src/power/` is not free of floating point**, where `src/clock/` and `src/link/` are. Cayenne-
  LPP's own arithmetic is `float`, and reproducing the library's bytes means reproducing its
  `float` multiply and truncate exactly; the BME280's driver answers in `float` too. The INA3221's
  conversion, the reader and the thresholds are integer-only, which is where it matters — those
  are the numbers the link reports and the ones an attention is raised from.
- **`PowerAccess::readPower` and `EnvAccess::readEnv` always return true.** p1-03 declared them
  with a `bool`, and the session answers `kErrFailed` on false. There is no case in which this
  firmware has nothing to say — a channel that could not be read has its validity bit clear,
  which is the protocol's own answer for it — so the `false` branch is reachable only from a test.
  It is kept because a board that could genuinely fail to answer would need it.
- **`LPP_GET`'s bytes are written into the response payload directly** rather than through
  `encodeLppResponse()`. That payload is a status byte followed by the bytes verbatim, so the two
  are the same thing; going through the encoder would need a second 180-byte buffer on a board
  whose stack is 2 KB (p1-04's reading of the linker script). `encodeLppResponse` is still held to
  that shape by `test/test_link_codec` against the fixture, and the handler says so where it
  deviates.
- **The I2C transaction timeout is a budget, not a deadline.** The task asks the reader to "give
  up on a transaction that takes too long". It does — `PowerReader` and `EnvReader` compare what
  the bus reports against a budget and put the device in a five-second back-off when it is
  exceeded — but the Adafruit core's TWIM driver busy-waits with **no deadline of its own**
  (`libraries/Wire/Wire_nRF52.cpp:166`, `:169`, `:230`, `:234` at the core's pinned commit
  `d541301`: `while(!_p_twim->EVENTS_RXSTARTED && !_p_twim->EVENTS_ERROR);`). An absent or
  unpowered device makes the hardware raise `EVENTS_ERROR` on the address NACK and the call
  returns at once, which is the failure this board actually meets and the one the bench will
  produce by unplugging the ribbon. A bus **held low** by a stuck slave would hang that loop, and
  nothing short of our own TWIM driver with a timer could bound it. The budget is what notices a
  bus that is merely slow; the residual risk is on record here and nowhere else.

## Decisions taken without asking

- **The INA3221 is configured as `CURRENT-SENSE.md` §6.7 asks**: continuous shunt and bus, 1.1 ms
  conversions, AVG = 64, all three channels. One sample set is then 64 × 6 × 1.1 ms ≈ 422 ms, so a
  reader that sweeps once a second always finds a fresh average and never waits for a conversion.
  AVG 64 rather than 256 because 256 would take 1.7 s, which is longer than the sweep.
- **The manufacturer ID is checked before the configuration is written.** A device that answers at
  `0x42` but is not an INA3221 is not one to write a configuration word into; `0x5449` ("TI") is
  the datasheet's value for register `0xFE`. Upstream's own scan does the weaker thing (address
  only) and then calls a library.
- **One channel per pass, three passes a sweep.** Two register reads at 100 kHz are about half a
  millisecond; a whole sweep in one pass would be 1.5 ms out of a `loop()` that also has a radio
  to serve. The protocol's own budget (250 ms for an answer) is not the constraint — forwarding
  is.
- **A failed register invalidates its channel; a slow one drops the device.** A missing reading is
  per channel, because the fake bus can produce it and because a stale value with its bit still
  set is the one thing §5.8 forbids. A transaction past its budget is a bus in trouble and not a
  channel's problem, so it stops the sweep and starts the back-off. Every channel failing in one
  sweep is the device being gone.
- **The back-off is five seconds.** Long enough that a dead sensor costs the loop two transactions
  a minute instead of two a pass; short enough that a B-board plugged back in is found before
  anybody has finished writing it down.
- **The BME280 is sampled every five seconds, the INA3221 every one.** The air in a sealed
  enclosure does not change in a second, and the power sweep is the one with a deadline (the
  thresholds and `status`).
- **The thresholds' window is 2 500–4 300 mV and the pair must be more than the hysteresis
  apart.** Below the floor the pack's own protection has already disconnected; above the ceiling
  the charger never gets there (VCC regulates at 4.200 V). More than 100 mV apart because
  otherwise leaving *critical* would enter *low* and leaving *low* would enter *critical* at the
  same voltage. A `set` outside that is refused and nothing changes; upstream's CLI has one word
  for "no" and that is the word it says.
- **The minimum time below is one minute and the hysteresis 100 mV, and the same minute applies in
  both directions.** The sag of a 1.5 A Walter burst through the series path is 0.25–0.35 V
  (`CURRENT-SENSE.md` §3.3) — far more than any hysteresis — so it is the *time* that stops a
  burst raising an attention, and the hysteresis only keeps a level from flickering at its own
  edge. One rule in both directions is also one rule to test, and it stops a charging burst from
  clearing a level that is really there.
- **A recovery raises nothing.** Section 8 has no reason for "the battery came back", and the
  Walter reads the voltage with `POWER_GET` whenever it is awake.
- **`getBattMilliVolts()` returns 0 for an invalid channel rather than a last-known value.** It is
  what §5.8 means by a channel whose bit is clear, it is what keeps upstream's boot protection out
  of the way (above), and a `status` that says 0 mV is read as "this node cannot see its battery"
  where one that says 3.9 V from an hour ago is read as a fact.
- **The LPP channels are fixed numbers, 2 to 5**, and not `next_available_channel`'s. Upstream's
  sensor table is empty in this build — no GPS, no INA3221, no BME280 — so nothing of upstream's
  ever hands one out, and fixed numbers are what "never renumber them" means. A board of this
  family whose manager does find a sensor of its own must give it a channel above these; the
  comment in `src/power/Telemetry.h` says so, and the two rails tests are what keep the
  assumption true for this board.
- **A channel whose validity bit is clear is left out of the LPP entirely** rather than reported
  as zero volts. A chart with a gap in it is honest; one with a zero in it is not. The numbers of
  the channels that are present do not move because of it, which is the whole value of fixed
  channel numbers.
- **The preferences file is ours, `/power`, with a magic that carries its version.** Upstream's
  `/prefs.json` is a fixed C struct that `CommonCLI::savePrefs` writes whole, so a field of ours
  in it would either mean editing upstream or being overwritten by the next `set name`. The
  record is the clock file's shape (magic, values, flags, one check byte) and a pair outside
  today's window is refused on load, so a file written by a firmware with a wider window cannot
  put this node outside it.
- **A `set` of a threshold writes the file at once**, and a write that fails leaves the running
  value set and the file as it was. The alternative — refusing the `set` because the file could
  not be written — would leave a node that cannot write flash unable to be configured at all, and
  the thresholds are re-settable by the Walter on every boot anyway.
- **The two new settings are appended to task 05's five.** It is the only place a new key can go
  without renumbering one that `docs/link.md`, `docs/bench.md` and p1-05's report already name,
  and upstream's paging counts in that order.
- **`src/power/` has its own `EnvReadings`/`PowerReadings` types and `src/power/LinkPower.*`
  converts them to the link's**, the way `src/clock/LinkClock.h` does for the clock keeper. The
  `static_assert`s at the top of that header tie our bit values and permission bits to the link's,
  so the two cannot drift silently.
- **`tools/linkcli.py` reads the LPP back field by field** rather than printing hex. The hex is
  printed too, because that is what goes in a report, but the channel table is the thing a person
  needs and a tool that cannot read its own protocol's telemetry is a tool somebody will write
  twice.
- **`tools/linkloop/` gained a fake I2C bus with real register values**, so `power`, `env` and
  `lpp` through the pipe exercise the firmware's own conversion rather than a stub, and
  `--drop-ina` is the bench's "unplug the B-board" case with no board at all. It is the cheapest
  way to be sure the signs are right before a multimeter is ever connected.

## New libraries (with the one-line justification)

None. `Adafruit BME280 Library @ 2.3.0` and `CayenneLPP @ 1.6.1` were already pinned
dependencies — MeshCore's `src/helpers/sensors` needs them whether a sensor is fitted or not — and
this task uses the first directly and mirrors the second.

## Not verified here (and why)

Added to `docs/bench.md` as section **5. Power**, tagged **p1-06**; `docs/link.md` §2d is the page
that walks them, and the hardware repository's `CURRENT-SENSE.md` §6 is the fuller procedure for
the block. Everything below needs the thing no session has: **a board, a pack, a panel and a
multimeter** — and for two of them a phone on the mesh.

- **`linkcli.py power` against a multimeter: sign first, then size.** Channel 1 positive with the
  bench supply standing in for the panel; **channel 2 positive while charging and negative with
  the panel off**; channel 3 equal to the two radios' draw. The conversion is a native test
  against hand-calculated registers, but **no current has ever flowed through a shunt of this
  board into this firmware**, and the one thing a wrong wiring assumption would show as is a sign.
- **The same three numbers in a phone's telemetry view**, on LPP channels 2, 3 and 4, **and the
  battery voltage in its `status`**. `LPP_GET` and the mesh share one field list and one cap, and
  the equality is a native test — but no radio has ever carried this node's telemetry, and the
  mesh half of it is upstream's `handleRequest` with upstream's `CayenneLPP`, which only a board
  has.
- **`linkcli.py env` against a thermometer**, and the enclosure's temperature on LPP channel 5.
  The compensation arithmetic is the Adafruit library's and has never run against a real part
  here; what a session can say is that a value outside the part's range is refused.
- **The thresholds with a battery simulator**: below 3 500 mV for a minute → attention reason 2
  with the millivolts as `detail`; below 3 300 mV → reason 3; a dip of seconds → nothing; a
  second reason 2 inside the hour → nothing. The machine and the rules are native tests with a
  fake clock; what the bench adds is a real pack's sag under a real LTE burst, which is the thing
  the minute exists for.
- **The thresholds survive a restart**: `sensor set power.low_mv 3600`, `reboot 0`, still 3600.
  The record is a native test; **littlefs on this board's own flash is not**, and the clock's file
  is the only one that has ever been written there (p1-04, also unverified).
- **The INA3221's bus unplugged, and plugged back in.** `power` answers `valid 0`, the repeater
  keeps repeating, `ping` still answers inside 250 ms, and the channels come back within about
  five seconds. This is the one bench line that exercises the failure path the core's unbounded
  TWIM loops make interesting (*Deviations*), and the honest version of it includes **shorting
  SDA low** to see what a bus held down really does to this firmware — which is a line worth
  adding to the bench's own list if the reviewer wants the answer.
- **`sensor list` really pages**: `7 vars`, five keys and `... next:5`, then `sensor list 5`. The
  arithmetic is a native test over upstream's own loop; only a board has upstream's
  `EnvironmentSensorManager` in front of ours and upstream's interpreter behind it.
- **The boot-voltage behaviour.** A node with the pack at 3.2 V **does** come up, `get
  pwrmgt.bootmv` says `0 mV` and `get pwrmgt.support` says `supported`. That is the behaviour this
  task chose and the reviewer may want changed; it has never been seen.

And, not on the bench list because no rig is involved:

- **`tools/linkloop/check.sh` on a machine with its own `g++`.** It ran in the container here, as
  in p1-03, p1-04 and p1-05; the host path of that script has still never run.
