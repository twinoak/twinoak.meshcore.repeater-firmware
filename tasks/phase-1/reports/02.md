# p1-02 — the-link-codec

The box link is bytes now: CRC-16/CCITT-FALSE, COBS, packets, a frame receiver that counts what it
drops, a frame writer, and one function per message of protocol 1.0 — a decoder for every request,
an encoder for every response and every event — all of it under `src/link/codec/`, with no Arduino
include, no MeshCore include, no heap, no recursion, and every function bounded by the buffer it is
given. Every case of `spec/fixtures/link/link-v1.json` passes, in both directions the firmware
needs, and a coverage test fails if the fixture ever gains a case nothing here exercises. Nothing
touches a UART; task 03 puts it on the wire. Done in one session.

## Deviations from the spec or the task

- **`docs/ARCHITECTURE.md` §4 said "one encode/decode pair per message".** On this side of the link
  only one direction of each message is ever needed — in 1.0 the Walter sends every request and the
  RAK sends every event (`spec/LINK-PROTOCOL.md` §3) — so the codec has a decoder for every request
  and an encoder for every response and every event, and the other half of each pair is the
  Walter's firmware's, tested against the same fixtures in its own repository. §4's first item now
  says that, and names the files. The task file asked for exactly this; it is `ARCHITECTURE.md`
  that was loose, and this is the correction that task made to it.
- **`docs/link.md` is not written here.** `ARCHITECTURE.md` §1 lists it among `docs/`, but nothing
  of this task is visible on a console, on the wire or in a flashing procedure — the codec is bytes
  in, bytes out, and the page belongs with the thing a person can watch. Task 03 puts the link on
  `Serial1` and writes a bench tool that speaks it; that is the task that has something to
  document.
- **`docs/bench.md` gains nothing**, as the task says ("Not verified here: nothing"). There is no
  bench line to add: every claim above is a native test on this machine.
- **The spec and the task agree everywhere else**, and no disagreement with `spec/` was found. Two
  places where the specification is deliberately quiet are recorded as decisions below.

## Decisions taken without asking

- **Where the specification names a status other than `ERR_MALFORMED` for a bad value, the codec
  decodes the value and passes it up.** `REBOOT`'s `mode` is `ERR_RANGE` when the board cannot do
  it (§5.5) and `SEND_TRACE`'s `hash_size` of 3 is `ERR_RANGE` (§6.2): a codec that refused them
  would turn both into `ERR_MALFORMED` and the session could not give the answer the protocol asks
  for. What the codec *does* refuse is a length or a range the specification states as part of the
  layout: a path's `path_mode` over 2, a `hash_size` outside 1–3, a `hop_count` outside 1–63, more
  than 64 bytes of hops, a `CLI` line that is not 1–160 bytes (§5.7), a `SEND_CLI` line that is not
  1–148 (§6.2), a `SEND_LOGIN` password over 15 (§6.2), and any `str8` whose length byte promises
  more than the payload holds. Each has a test.
- **A decoder never checks that it consumed the whole payload.** Trailing bytes it does not know
  are ignored, because a later minor version adds fields at the end of a payload (§5.1,
  "Versions"); `MalformedRequests.TrailingBytesAreIgnored` is that rule as a test.
- **A path's two size bytes are read whatever the mode says, and ignored unless the mode is
  `hops`** — the reference implementation's behaviour (`spec/tools/linkref.py`, `dec_path`), so a
  Walter that leaves junk in them for mode 0 or 1 is answered rather than refused. The decoded
  `hash_size` and `hop_count` are then 0, as §6.1's table has them.
- **`Bytes` is a borrowed view** (`const uint8_t*` and a `uint8_t` length, since a payload is at
  most 240 bytes), not a copy: a decoded `str8`, password or path points into the payload it came
  from, and the header says in as many words that it lives exactly as long as those bytes do. It is
  what keeps the codec out of the heap and off the stack.
- **A `Reader` and a `Writer` that fail stickily.** The first read that does not fit sets a flag,
  every later one does nothing, and the caller asks once (`ok()`): that is what lets every decoder
  read its fields in a straight line and still say *malformed* instead of reading out of bounds.
  An encoder is all-or-nothing — it returns the number of bytes written, or 0, and never leaves
  half a message in the buffer.
- **`FrameReceiver` is fed and asked, never called back.** `feed(data, len)` takes bytes until one
  completes a packet and returns how many it took, so a transport loops `feed` / `hasPacket()` /
  `packet()` with nothing of the session inside the receiver (the loop is in the header). The
  packet's body points into the receiver's own buffer and is valid until the next feed. There is
  also `feedByte` for a byte-at-a-time transport and for the tests.
- **Two 246-byte buffers, not one.** The frame is collected in one and decoded into the other,
  which is what lets a 245-byte packet be reported as *oversize* rather than as a COBS failure —
  the distinction the fixture's `invalid` list makes. 492 bytes on a 256 KB part is the right side
  of that trade.
- **The drop counter saturates at 65535, total and per reason** (`STATUS`'s `link_errors`, §5.3),
  and the reasons are COBS, short, oversize, CRC and overflow. An overflow is counted when the
  terminator arrives and not before, as §2 says, so the tail of an over-long frame cannot be taken
  for a frame of its own.
- **`cobsEncode` refuses a run of 254 non-zero bytes** rather than emitting the `0xFF` code: a
  packet is at most 244 bytes, so such a run is a caller's bug, and a decoder of ours would drop
  what the encoder produced (§2). `cobsDecode` refuses the code, a zero inside a frame, a block
  that runs past the end, and a decoding that does not fit.
- **`encodeCliResponse` refuses a reply over 160 bytes** (§5.7) rather than truncating it, and
  `encodeObsPullResponse` refuses a record set that does not fit one payload rather than cutting a
  record in half. How many records to hand out is the session's arithmetic, in task 03 and §7.
- **The fixture's `why` word is not asserted.** §11 says the reason is informative — a receiver has
  to drop and count the frame, not agree on a word — so the fixture test asserts the drop and the
  count, and a separate test holds our own five reasons against frames built for them. (They do
  agree with the reference today, for all six `invalid` frames.)
- **The ASan run is a one-off, not part of `tools/verify.ps1`.** `out/p1-02/asan.py` (under the
  git-ignored `out/`) appends `-fsanitize=address` and is passed to one container run with
  `PLATFORMIO_EXTRA_SCRIPTS`. It has to be a **`pre:`** script: as `post:` the link flag arrives
  but no source is instrumented, and the run then proves nothing — which is exactly what happened
  on the first attempt (`out/p1-02/native-asan-experiment.log`). Worth knowing for any later task
  that wants a sanitiser.

## Not verified here (and why)

Nothing for the bench, and `docs/bench.md` gains no line: this task is bytes in and bytes out, and
every claim is a native test that ran on this machine. Two notes for the reviewer all the same:

- **The native tests under AddressSanitizer** ran in the container and are green: all 39 cases of
  the four suites, with `src/link/codec/` instrumented — `out/p1-02/native-asan.log`, and the
  binary links `libasan.so.8`. That run has teeth: a deliberately wrong view, a one-byte buffer
  described to `decodePing` as four bytes, was caught at `src/link/codec/Bytes.cpp:32` with
  `AddressSanitizer: heap-buffer-overflow … READ of size 1 … 0 bytes after 1-byte region`
  (`out/p1-02/native-asan-report.log`, captured by running the test binary directly, because
  PlatformIO's runner does not show the sanitiser's stderr — only `Program received signal SIGHUP`
  and `ERRORED`). The deliberate test was then removed and the clean run above is the one on
  record. ASan is not in `tools/verify.ps1`: it is a tool for a task that adds parsing, not a
  per-commit cost, and CI has no sanitiser step.
- **The Walter's half of every message** is tested in `twinoak/meshmaster-agent-firmware`'s own
  repository against the same fixture file. Nothing here encodes a request or decodes a response,
  so a disagreement between the two codecs can only be a disagreement with `link-v1.json`, which
  both sides hold themselves against.
