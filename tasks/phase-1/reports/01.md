# p1-01 — our-application

The design holds. Our `main.cpp` constructs a `TwinOakMesh`, a subclass of MeshCore's unmodified
`MyMesh` compiled from the pin (`repeater-v1.17.1`, `d9296435`); every virtual
`docs/ARCHITECTURE.md` §2 names is overridden with `override` and the compiler accepts all eight;
`src/board/target.cpp` is the board target and upstream's is not in the link; a boot that finds no
saved preferences draws itself a random admin password and never prints it. Not one file of
upstream's tree is edited (`git status` in the pinned checkout is empty after the build). Done in
one session.

```

Flash: [=====     ]  47.2% (used 384328 bytes from 815104 bytes)  phase 0: 383752 (+576)
```

(`out/verify/build-repeater_rak4630_single.log`.) The 576 bytes are the eight pass-through
overrides, the vtable, the first-boot code and the password generator; nothing of upstream's left
the image, because upstream's `main.cpp` was replaced by one that does the same things minus the
display and Ethernet, which were not compiled in before either.

## Deviations from the spec or the task

- **The password is 15 characters, not 16.** `NodePrefs::password` is `char[16]` at the pin
  (`src/helpers/CommonCLI.h:29`); `StrHelper::strncpy` truncates to 15 and the login compares with
  `strcmp` (`MyMesh.cpp:102`), so a sixteenth character can neither be stored nor matched. The
  generator fills whatever buffer it is given (`sizeof(prefs->password)`), the test holds it to
  15 + NUL. Spec S-13 says only "random … that nobody knows"; 15 alphanumerics are 89 bits.
- **`-Werror` on `src/` did not survive upstream's headers by itself.** Phase 0's promise held
  only while our one source included no upstream header. Under `-Wextra`, `MeshCore.h`,
  `Dispatcher.h`, the SoftDevice's `nrf_soc.h`/`nrf_sdm.h` and `RAK4631Board.h` warn (599 unused
  parameters, 96 reorders, 4 string literals as `char*`, in `out/build-p1-01-third.log`), and
  RadioLib's `#warning` for `RADIOLIB_GODMODE` is an error under `-Werror=cpp`. The fix is the
  agent firmware's (`src/mesh/MeshCoreHeaders.h`): `src/board/UpstreamHeaders.h` and
  `src/app/UpstreamMyMesh.h` include upstream as system headers (`#pragma GCC system_header`, which
  GCC extends to what they include), and `build_src_flags` gains `-Wno-error=cpp` for the one
  diagnostic a system header does not silence. A first attempt with an `-isystem` flag per
  directory (`out/build-p1-01-fourth.log`) silenced the warnings but made the core's `WString.h`
  conflict with itself on this toolchain, and was dropped. A file of ours now includes one of the
  two wrappers and never an upstream header directly. Our own sources compile with no warning but
  that `#warning`, which is checked in the build log.
- **The variant sources are compiled by a *post*-script into a small static library, not by a
  pre-script into the program's sources.** A pre-script runs before the platform has configured
  the toolchain and the core's include paths (`'CC' is not recognized`,
  `out/build-p1-01-second.log`); a post-script sees the finished environment but the program's
  source list is closed, so `tools/pio/meshcore_variant.py` builds `libmeshcore_variant.a` from a
  clone of the environment with MeshCore's `src/` and the core's `Wire` library added to the
  include path, and adds it to `LIBS` — inside the `--start-group` PlatformIO already puts around
  every library. The task's intent — the two files compiled from the pin, never copied, by a
  `tools/pio/` script — is met.
- **`variant.cpp` is the only pin map, not one of two.** Phase 0's report (item 8) said the
  Adafruit core compiled its own `WisCore_RAK4631_Board/variant.cpp` beside MeshCore's; there is no
  such directory in the core at the pin, and PlatformIO builds an empty "variant library" from the
  missing path without a word. MeshCore's `variant.cpp` is therefore genuinely needed, as the task
  said. `docs/ARCHITECTURE.md` §3 and §11 say so.
- **`ENV_INCLUDE_INA3221` is removed now, not in task 06.** ARCHITECTURE §3 — in this task's
  reading list — says upstream's INA3221 support is left out, and with the define upstream would
  put wrong currents (one shunt for three channels) into mesh telemetry on a fitted board.
  Task 06 still owns the rails-test line that holds it out; this task only takes the define away
  and says why in `platformio.ini`.
- **`UITask.cpp` is still compiled, not excluded.** The task allows excluding "whatever else of the
  example is display-only"; a second `-D EXCLUDE_FROM_EXAMPLE=UITask.cpp` is a macro redefinition
  warning in every translation unit, ours included, under `-Werror`. Without `DISPLAY_CLASS`
  nothing references the object and the linker leaves it out (no `UITask.cpp.o` in the map).
- **Our `main.cpp` keeps only the nRF52 branches** of upstream's `setup()` (the ESP32, RP2040 and
  STM32 file-system `#if`s are gone; the external-watchdog `#ifdef`s stay), drops the debug-only
  5-second delay and the `MESH_DEBUG_PRINTLN` lines (the rails test forbids the name in `src/`),
  and declares the console loop's `len` as `size_t` where upstream has `int` — `-Wsign-compare`
  against `sizeof(command)`. The loop is otherwise upstream's line for line.
- **`src/version.{h,cpp}` moved to `src/app/Version.{h,cpp}`**, as ARCHITECTURE §1 places the
  version string and as phase 0's report asked the task that creates `src/app/` to do; the native
  filter and `test_version`'s include follow. The `[reviewer]` follow-up about that test's pin
  literal is untouched.
- **The rails test also fails a board environment that does not define `ADMIN_PASSWORD` at all**,
  not only one that defines it as upstream's word: without the define upstream's `MyMesh.cpp:33`
  supplies that word itself, which is how phase 0's image came to carry it. `src/app/FirstBoot.cpp`
  has the same rail as `#error`.
- **`docs/bench.md`'s section 1 is headed as the task names it** ("The repeater alone on USB"),
  where phase 0 had written "The repeater on the rig".
- **`docs/upstream.md` has eight places, not seven**: the two wrapper headers and the
  `<target.h>` shadowing are a dependency on upstream a compiler does not catch; the sync template
  and its README follow.

## Decisions taken without asking

- **`ADMIN_PASSWORD` is `"not-a-password"`.** Upstream's constructor copies the define into
  `_prefs.password` (`MyMesh.cpp:897`), so a value is unavoidable. It never survives first boot:
  `setup()` tests for saved preferences the way `CommonCLI::loadPrefs` does (neither `/prefs.json`
  nor `/com_prefs` exists) *before* `the_mesh.begin()`, and after it — before `loop()` has run once,
  so before any packet is processed — draws the random password straight into the preferences and
  saves them; every later boot loads the saved one over the define. Belt and braces: it is also
  replaced when the loaded preferences still carry the define's value, whatever the files said
  (`needsFreshPassword`, tested). The literal is in the image's `.rodata` once, as any constructor
  default is; it is not a secret and is on the bench list as a login that must fail.
- **The alphabet is A–Z, a–z, 0–9**, 62 characters, with rejection sampling (a byte ≥ 248 is thrown
  away) so no character is likelier than another; no space, quote or anything upstream's command
  line treats specially, so `password <new>` and a login payload carry it unchanged.
- **The RNG is upstream's `RadioNoiseListener`** (radio noise xor the CC310 generator), exposed
  from the target as `radio_random()` — the same source `radio_new_identity()` draws the node's
  key from. The portable generator takes a `RandomSource` interface; the tests use a replay source
  and a seeded one.
- **The first boot prints one line without the password**: `First boot: a random admin password
  was set (not shown; set yours with 'password <new>')`, so the bench can tell a first boot from a
  reboot.
- **`fw.version` is read-only**: `TwinOakSensors::setSettingValue` returns false for it and
  upstream's CLI answers `can't find custom var` — upstream's wording, not ours to change; task 05
  owns the settings' tests.
- **Our settings come after upstream's own** in `sensor list` (none on this board without a GPS),
  so upstream's keep their indices if a bump adds one.
- **`TwinOakBoard` constructs `NRF52Board` itself** with `const_cast<char*>("RAK4631_OTA")`:
  `NRF52Board` is a virtual base and its constructor takes a `char*` it only reads
  (`Bluefruit.setName`, `NRF52Board.cpp:417`); upstream passes the bare literal, which our `-Werror`
  refuses.
- **The build writes `firmware.map`** on every build (`tools/pio/linkmap.py`) and
  `tools/verify.ps1` keeps it with the images, so the acceptance criterion above is checkable by
  a reviewer without rebuilding.
- **`-I $PROJECT_DIR/src/board` is first in the board environment's `build_flags`**, ahead of
  `variants/rak4631`, which is what makes upstream's `#include <target.h>` resolve to ours in the
  MeshCore library's own translation units (`MyMesh.cpp`, `UITask.cpp`, `NRF52Board.cpp`) as well
  as ours. `-I …/examples/simple_repeater` puts `MyMesh.h` on the path.
- **`PROJECT_DIR` is passed to the native build** for the rails test, as the agent firmware does;
  the test falls back to the nearest ancestor of the working directory with a `platformio.ini` if
  that path has none.
- **The rails test's walk of `src/` forbids the two define names anywhere in a line**, which also
  forbids upstream's `MESH_DEBUG_PRINTLN` macro in our sources — on purpose, and said so in the
  test.
