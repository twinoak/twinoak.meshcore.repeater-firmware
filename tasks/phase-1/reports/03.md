# p1-03 — the-link-session

The link is alive on `Serial1`. A peer that sends `HELLO` learns what this firmware is; `PING`
answers with the uptime; `STATUS`, `IDENTITY` and `REBOOT` work; a restart announces itself with
`EV_BOOT`; a request sent twice is executed once; and `tools/linkcli.py` speaks all of it from a
laptop through a USB-UART dongle — and, because no board exists yet, through a pipe to the
firmware's own session compiled for the host (`tools/linkloop/`), which is how the tool was tested
before the bench. The session is portable (`src/link/session/`, no Arduino, no MeshCore, no heap)
and the part that touches the board is 994 bytes of flash. Done in one session.

## `Serial1`'s buffers: 64 bytes, and now 256

The Adafruit nRF52 core at the pinned core commit (`framework-arduinoadafruitnrf52 @ d541301`)
sizes a `Uart`'s receive ring **and** its transmit buffer with `SERIAL_BUFFER_SIZE`, which defaults
to **64** and is `#ifndef`-guarded (`cores/nRF5/RingBuffer.h:28`, `cores/nRF5/Uart.h:61`).
`platformio.ini` raises it to **256**, for two reasons and not one:

- **Reading.** 64 bytes is 5.5 ms of line time at 115200 and a frame is up to 246 bytes. One pass
  of a repeater's `loop()` is not reliably under 5.5 ms, so a frame would be torn apart between two
  passes. The ring holds `SERIAL_BUFFER_SIZE - 1` usable bytes — 255 — which is one whole frame
  with its leading zero and room to spare.
- **Writing without blocking.** `Uart::write()` takes a binary semaphore with `portMAX_DELAY`
  (`cores/nRF5/Uart.cpp:241`): it blocks only while a previous DMA transfer is in flight, and it
  copies at most `SERIAL_BUFFER_SIZE` bytes per round. `availableForWrite()` returns
  `SERIAL_BUFFER_SIZE` when nothing is in flight and 0 when something is
  (`cores/nRF5/Uart.cpp:255`). So *"write what fits without blocking"* on this core is exactly:
  write the whole frame when `availableForWrite() >= its length`, which needs the longest frame
  (247 bytes with the leading zero) to fit in `SERIAL_BUFFER_SIZE`. 256 is the smallest power of
  two that does.

The define is the core's only lever and it is global, so it costs **1 536 bytes of RAM in four
places that are not `Serial1`**: `Serial2`'s two buffers, and the two `RingBuffer`s of each of
`Wire` and `Wire1`. Roomier I2C buffers harm nothing; the figure is in the table above and the
reason is in `platformio.ini` beside the define.

## What one pass of the link costs

A board is needed for the real figure and this session had none, so there are three answers, from
the hardest evidence to the softest.

**1. Measured, on the host.** `tools/linkloop --bench 20000` runs the worst pass this task can
produce — a 246-byte frame in (a `HELLO` whose `fw_version` fills the payload, so the CRC runs over
242 bytes), one handler call, and the longest response this firmware builds framed out — with a new
`seq` every time so the retry memory never short-circuits it:

```
passes            20000
answered          20000
request frame     246 bytes
mean  per pass    1.99 us
worst per pass    32.59 us
```

(`out/p1-03/linkcli-loopback.log`; `-O2`, in the container.) The worst is the container's
scheduler, not the code; the mean is the figure.

**2. Counted, from the image this build produced.** The cost is dominated by CRC-16/CCITT-FALSE,
which is bitwise (`src/link/codec/Crc16.cpp`). In the built image GCC unrolls its inner loop
completely: the per-byte body of `twinoak::link::crc16` is **45 instructions**
(`out/p1-03/firmware.dis`, `0x3a000`–`0x3a05c`, counted by hand and by script). On a Cortex-M4 all
but two are single-cycle — `ldrb.w` with writeback is 2, and the taken backward branch costs up to
3 with no branch prediction — so **≤ 48 cycles per byte, 0.75 µs at 64 MHz**. The pass runs the CRC
twice:

| Pass | CRC bytes | CRC time | Everything else (estimated) | Total |
|---|---:|---:|---:|---:|
| `STATUS` or `PING`, the heartbeat shape | 2 in + 21 out | 17 µs | ~26 µs | **~43 µs** |
| a `HELLO` request with a 13-byte version string | 20 in + 67 out | 65 µs | ~52 µs | **~117 µs** |
| the absolute worst: a 240-byte payload in | 242 in + 67 out | 232 µs | ~178 µs | **~410 µs** |

"Everything else" is the 246 `feedByte` calls (two out-of-line calls each, ~25 cycles), COBS in and
out (~8 cycles a byte), the handler's `Writer` calls for a 65-byte payload, and `Uart::write`'s
semaphore and `memcpy`. Those rates are estimates; the CRC term is not.

So a Walter pinging once a second costs the loop about 43 µs a second, and ten times a second about
0.4 ms a second — 0.04 % of the loop. The absolute worst, 0.4 ms, happens only if the Walter sends
a request with a full payload, which none of this task's five requests needs.

**3. Instrumented, for the bench.** `SerialTransport::worstPassMicros()` and `lastPassMicros()`
keep the board's own figure, from `micros()` around the whole pass. Reading them needs a debugger
until task 05 puts the console on the link; that is on the bench list.

If the bench shows the CRC term matters, a 512-byte lookup table would cut 48 cycles a byte to
about 6. That is a change to p1-02's file for a reason no measurement has yet given, so it is not
in this task — it is a line for the reviewer.

## Deviations from the spec or the task

- **`TIME_SET`, `TIME_GET` and `SLEEP_NOTICE` are answered `ERR_UNSUPPORTED`, and §4 calls all
  three "always".** They are tasks 04 and 05, and this task's *Out of scope* says so. The spec and
  the task disagree here and the task is the narrower of the two; a Walter that asks gets a
  definite answer rather than silence, which is the behaviour §3 defines for a type the firmware
  does not know. It is temporary by construction: each of those tasks adds its handler, and no
  capability bit has to change for `TIME_*` or `SLEEP_NOTICE` because they have none.
- **`caps` is `0x00` on the board today.** Every capability is an interface that is there
  (`src/link/session/Interfaces.h`), and this task implements three interfaces that carry no
  capability bit — the firmware identity, the system and the node identity. So a `HELLO` from the
  bench reports no capabilities at all, which is correct and is what `docs/link.md` says to expect.
  `test_link_session` runs the session with all seven interfaces present, which is how the
  fixture's `caps 0x7F` response is reproduced byte for byte.
- **`LppAccess` contributes no capability bit.** `spec/LINK-PROTOCOL.md` §4 gates `LPP_GET` on
  `CLI`, not on `POWER` or `ENV` or a bit of its own. That is what the table says and what
  `capsOf()` does, so a build with a console but no LPP source will advertise `CLI` and answer
  `LPP_GET` with `ERR_UNSUPPORTED`. Worth a reviewer's eye: it may be what the specification means
  (the LPP bytes are what the *console* would report) or it may be an oversight, and either way it
  is task 06 that has to live with it.
- **`reset_reason` 7, "left the bootloader", is never produced.** The nRF52840's `RESETREAS` has no
  bit for it: the UF2 bootloader restarts the chip when it is done, so the boot after a DFU reads
  as 4, *software* — which is literally what happened. `resetReasonFromNrf52` says so in a comment
  and a test asserts that no input produces 7. Giving it a real answer would need a marker of our
  own in a retained register, and `GPREGRET` is the bootloader's while `GPREGRET2` is MeshCore's
  shutdown reason (`src/helpers/NRF52Board.cpp` at the pin), so there is no free one.
- **A frame that passes the CRC but carries a response or an event type is dropped silently and is
  *not* counted in `link_errors`.** §3 says only the Walter sends requests in 1.0 and §2 says
  `link_errors` counts "frames dropped by the RAK's receiver"; this frame was not dropped by the
  receiver, it was refused by the session. Answering it would put a packet of type `0xE0` on a link
  where nothing reads such a thing. Tested
  (`Malformed.AFrameThatIsNotARequestIsDroppedUnanswered`).
- **`docs/ARCHITECTURE.md` §4 is corrected**, not only extended: it said the session talks to the
  firmware through "a clock, a CLI, power, the mesh client" and it is seven interfaces plus two
  that are not optional, and it did not say that `caps` is derived from them rather than declared.
  §3's "Transport" row now names `BoardLink` as well, and the "never stalls the mesh" paragraph now
  says what happens to a request that arrives with an answer still unsent, and gives the buffer
  size. `docs/upstream.md` places 1 and 5 gained the new dependencies on upstream (below).

## Decisions taken without asking

- **All four `REBOOT` modes work on this board.** 0 is `NRF52Board::reboot()` → `NVIC_SystemReset`;
  1, 2 and 3 are the Adafruit bootloader's, entered by the magic word the core writes into
  `GPREGRET` before the reset (`cores/nRF5/wiring.c` at the core's pinned commit `d541301`:
  `enterUf2Dfu` `0x57`, `enterSerialDfu` `0x4e`, `enterOTADfu` `0xA8`). The RAK4630 ships with that
  bootloader — it is what the field USB port flashes through — so `canRestart()` accepts 0 to 3 and
  nothing is `ERR_RANGE` here. The session still asks before it schedules, and a board added in
  phase 3 that cannot do one of them only has to say so; the `ERR_RANGE` path is tested with a fake
  that refuses.
- **`restartNow()` flushes both UARTs before it goes.** §5.5's delay "leaves time for the response
  to leave the UART", but the response was handed to a DMA transfer, and a Walter may ask for
  `delay_ms` 0. `Serial1.flush()` and `Serial.flush()` block until the transfers finish — which is
  safe in the one function that never returns — so the answer always leaves. The *delay itself* is
  the session's and is portable: it starts when the transport says the bytes went to the UART, and
  the restart fires on a later pass. Tested to the millisecond against a fake clock.
- **The session is fed one byte at a time and says when to stop.** `feedByte` returns true when a
  complete request is waiting, and the transport stops reading then — so the bytes of the *next*
  frame stay in the core's 255-byte ring rather than in a buffer of ours, and a request that
  completes while the previous answer is unsent is neither lost nor able to overwrite it. The
  alternative, feeding a block and keeping the remainder ourselves, would need a third buffer for
  no gain.
- **The one-entry memory records every request that was answered**, including the malformed ones
  and the unknown types, not only the ones a handler ran. The remembered answer is the same answer
  either way, and the rule §3 exists for — a retry must never do the work twice — is kept by the
  wider version too. `Session::executed()` counts handler calls and is what the tests assert on.
- **An encoder that refuses is answered `ERR_FAILED`.** No handler here can produce it (every
  response this task builds fits 240 bytes with room to spare), but a silent request is a dead link
  as far as the Walter can tell, so the `n == 0` path says something rather than nothing.
- **The leading `0x00` is decided when the frame is built, not when it is sent.** The gap is one
  pass — tens of microseconds — and the rule is about a line that has been quiet for 100 ms. The
  session tracks the last time the *transport said it sent something*, so a frame that waits a pass
  for the UART does not reset the clock twice.
- **`highestMinorBothKnow()` is a function of two runtime values** (`src/link/codec/Numbers.h`).
  Written as `m.proto_minor < kProtoMinor`, with `kProtoMinor` at 0, it is a tautology and
  `-Werror=type-limits` refuses it — rightly. The rule is still the rule, and it will still be
  written once when 1.1 exists.
- **`fw_version` in `HELLO` is the release's version alone** (`0.0.0-dev` locally), and `upstream`
  is `<tag>+<pin8>` — `repeater-v1.17.1+d9296435`. `spec/LINK-PROTOCOL.md` §5.1's examples are a
  bare semantic version and a separate `upstream` field, and `spec/FIRMWARE-MANIFEST.md` §4 says
  the descriptor's `version`, `board` and role "are what the running firmware reports in the link's
  `HELLO`". The console's `sensor get fw.version` still answers the one long sentence p1-01 chose;
  `twinoak::formatUpstream` and `upstreamString()` are the new portable pieces, with tests.
- **`boot_id` is four bytes of the radio's noise listener**, drawn once in `linkBegin()` — the same
  source `radio_new_identity()` and the first-boot password use (`src/board/target.h`). It is slow
  and it runs once, after `radio_init()`.
- **`radioUp()` returns true.** `src/main.cpp` halts when `radio_init()` fails, so the link only
  ever runs with the radio up; the flag goes through the interface all the same, so a board that
  one day carries on without a radio only has to answer differently.
- **`walter.seen` reads `never`** until the first valid request, and otherwise whole seconds, which
  is what `docs/ARCHITECTURE.md` §4 asks for. A frame the receiver dropped does not count as having
  seen the Walter; a request of an unknown type does. Tested.
- **The no-allocation rail now covers `src/link/session/` as well as `src/link/codec/`**
  (`test/test_rails`, renamed `NothingUnderThePortableLinkAllocatesOrHoldsAString`). The session is
  the other portable half of the link and has the same reason not to touch a heap. The transport is
  deliberately outside it: it is the file that is allowed to know about Arduino.
- **`tools/linkloop/` and its `check.sh` are committed, and are not in `tools/verify.ps1`.** They
  need a host C++ compiler, which this machine does not have and CI does not need: what they prove
  about the session is already `test/test_link_session`, and what they prove about `linkcli.py`
  is a one-off before the first board. The script runs anywhere with `g++` and `python3`, and in
  the container otherwise; `docs/link.md` §4 has both commands.
- **`tools/linkcli.py` imports `spec/tools/linkref.py` for every byte.** It never encodes or
  decodes a field itself, so it cannot drift from the specification without the specification
  moving — and `spec/` is a copy that is verified against its manifest on every run. `--pipe` is
  the one thing in it that is not about a real link, and its docstring says so.
- **Section 10's timing table is now in `src/link/codec/Numbers.h`.** Only two of its numbers are
  the RAK's (the 100 ms idle rule, the 250 ms answer budget), but splitting the table across two
  files would be the start of a second home for the protocol's numbers.

None. `pyserial` is needed by `tools/linkcli.py --port` on a laptop and is not a dependency of the

## Not verified here (and why)

Added to `docs/bench.md` under "2. The link from a laptop", tagged **p1-03**, in the order the rig
is brought up. `docs/link.md` is the page that walks them.

- **A 3.3 V USB-UART dongle on the adapter's link pins** (J4/J5 on 1–2; dongle TX to P0.15, dongle
  RX to P0.16, grounds together): `linkcli.py --port <port> hello` prints protocol 1.0, role 1,
  slot 0, `max_payload` 240, `caps 0x00`, a non-zero `boot_id`, `0.0.0-dev`, `rak4630-single` and
  `repeater-v1.17.1+d9296435`.
- **`ping`, `status`, `identity`** answer, and `status`'s `reset_reason` is **1** after a power
  cycle, **2** after the reset line and **4** after `reboot 0` — the mapping has a native test but
  no board has ever set that register. `boot_id` changes across both.
- **`reboot 0` is answered before the node goes**, and `listen` then shows `EV_BOOT`. **`reboot 1`
  enters the UF2 bootloader and the way back is a power cycle**: worth doing once, deliberately,
  because it is the mode a person at the field USB port uses, and 2 and 3 are the same kind of
  one-way door. Nothing here has ever entered a bootloader.
- **Through both bulkhead filters** (470 Ω and 2.2 nF on each line, D-sub pins 8/9): the same five
  commands, and `link.errors` stays 0 over an hour of `ping` once a second. The electrical half of
  the link has never been exercised.
- **Repeating is unaffected while `ping` runs ten times a second**, and the board's own
  `worstPassMicros()` agrees with the ~43 µs this report computes for that shape. The computation
  is from this build's disassembly; only the board can confirm it, and reading the counter needs a
  debugger until task 05 puts the console on the link.
- **A frame mangled on purpose is dropped, counted and never answered**, with `link_errors` going
  up by one. The native tests do this with bytes; a real line does it with noise.

And, not on the bench list because no rig is involved:

- **`tools/linkloop/check.sh` on a machine with its own `g++`.** It ran in the container here, so
  the host path of that script (no `apt-get`, a system `g++`) has never run. CI does not run it at
  all, on purpose.
- **`linkcli.py --port` against a real serial port.** `SerialWire` is the one class of the tool that
  the loopback does not exercise: `pyserial` is installed on this machine but there is nothing to
  open. Everything above it — the framing, the retries, the event skipping, the printing — ran
  against `--pipe`.
