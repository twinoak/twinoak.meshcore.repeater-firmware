# p1-04 — the-clock

A repeater whose clock never runs backwards, on a board with no RTC. `src/clock/` is the rules
(portable, 38 native tests), the board's ports, and twenty lines that make the keeper the box
link's `ClockAccess`: at boot a hardware RTC with a sane time, else the lower bound kept in
`/clock` plus the save interval; `TIME_SET` and `TIME_GET` with every rule of
`spec/LINK-PROTOCOL.md` §5.4; the boot advert held until the clock is set or sixty seconds pass;
`HELLO`'s `caps` now `0x40` (`TIME_PERSIST`); `clock.state` on the console and over the mesh; and
`tools/linkcli.py time` / `time set` / `time set --force`, exercised against the firmware's own
session behind a pipe. Not one file of upstream's is touched. Done in one session.

**The surviving-RAM memory of the task's first bullet is not implemented, and the second half of
that bullet is why**: no place in this board's RAM can be shown to survive a reset, so the file
ships alone and the port stays, tested, behind a null pointer. The reading is below, under *Where
the surviving RAM would live*; it is the one thing in this task a reviewer should read before the
code.

## Where the surviving RAM would live — and why nothing is safe

The task asks for two memories and says: *"Establish where such memory can safely live on this
board … and cite what you found; if no place is safe, say so and ship the file alone."* Nothing is
safe. Four readings, each reproducible:

**1. The application's RAM is wholly accounted for.** The core's
`cores/nRF5/linker/nrf52840_s140_v6.ld` gives `RAM : ORIGIN = 0x20006000, LENGTH = 0x20040000 -
0x20006000` — everything below that belongs to the SoftDevice — and `nrf52_common.ld` then lays
out `.data`, `.bss`, `.heap` and the stack with no hole: `.heap`'s `. = ALIGN(__StackLimit)` makes
the heap fill everything up to the stack. In this image (`out/p1-04/firmware.map`):
`__data_start__ 0x20006000`, `__bss_start__ 0x200065c8`, `__bss_end__ = __HeapBase 0x2000e63c`,
`__HeapLimit = __StackLimit 0x2003f800`, `__StackTop 0x20040000`.

**2. The startup code writes three of those four ranges on every reset**
(`cores/nRF5/linker/gcc_startup_nrf52840.S`, the core's pinned commit `d541301`):

- lines 232–243 copy from `__etext` into `__data_start__ … __bss_start__` — deliberately up to
  `__bss_start__` and not `__data_end__`, and upstream's own comment at line 227 says why: "by
  using `__bss_start__` the user can add their own initialized data section before BSS";
- lines 248–255 fill `__StackLimit … __StackTop` with `0xADADADAD`, so the top 2 KB is out;
- `.bss` is zeroed from `__bss_start__` to `__bss_end__` — by the C library's `_start`, because
  `__STARTUP_CLEAR_BSS` is not defined by this platform (the loop at lines 267–282 is `#ifdef`-ed
  out, and `-u _printf_float`/`--specs=nano.specs` bring newlib's own crt0, which does it).

**3. So a linker orphan has exactly one place to land, and it is the wrong one.**
`out/p1-04/noinit-probe.sh` (log beside it) does three experiments with the project's own
toolchain and the core's own script:

- `__attribute__((section(".noinit")))` on an uninitialised variable produces a **PROGBITS**
  section — it has contents and is loadable;
- ld puts that orphan at **`0x20006008`**, between `.data` and `.bss`, with a load address in
  flash — which is inside the copy loop's range, so it is overwritten from flash at every boot.
  A `.noinit` of the usual kind would therefore do nothing at all on this core;
- declared in assembly as `%nobits` it lands at **`__bss_end__`** (`0x20006104` in the probe,
  between `__bss_end__` and `__HeapBase 0x2000610c`): not copied, not zeroed, and reserved by the
  linker. That is the only gap there is, and in the real image it is **`0x2000e63c`**.

**4. `0x2000e63c` is inside the RAM the Adafruit bootloader uses for itself, and the bootloader
runs before us on every reset.** The RAK's own bootloader is not in this repository, so what can be
read is the one the pinned core package ships (`bootloader/pca10056/pca10056_bootloader-0.9.1_s140_6.1.1.hex`);
`out/p1-04/bootloader-ram.py` reads it:

- its vector table at `0xf4000` gives an initial stack pointer of **`0x20040000`** — the top of
  RAM, which is also what the startup's `0xADADADAD` fill covers;
- the literal **`0x20007f7c`** sits in its flash at `0xfbab8`, in a literal pool beside
  `0x200082c4`. That is `DFU_DBL_RESET_MEM`, the double-reset word the task names as the evidence
  that *some* RAM survives — and it is deliberately just **below** `0x20008000`, outside what the
  bootloader itself zeroes, which is the shape of a bootloader whose own RAM begins at
  `0x20008000`;
- the RAM addresses its code holds as literals run from `0x200082a4` (8 times) up to at least
  `0x2000e7f8` (`0xf861c`, in a pool with `0x20008028` and `0x2000b04a`) and `0x2000cbc8`
  (10 times). `0x2000e63c` is inside that span, 444 bytes below `0x2000e7f8`.

A bootloader zeroes its own `.bss` when it starts, so a value there does not survive — and even if
this reading of a bootloader binary were wrong by a few kilobytes, the address is `__bss_end__`:
**it moves with every firmware**, so it could never be *shown* safe, which is the criterion the
task set. The honest answer is the file alone.

What that costs, exactly: after a reset the clock is up to an hour **ahead** instead of exact, and
a node that resets repeatedly with no Walter gains up to an hour each time (never backwards —
which is the property that matters). The one case where it would have mattered most is covered
another way, below: a restart the firmware performs itself writes the file in that second and the
next boot uses it without a margin.

**For the reviewer.** Two ways to get the second memory later, neither in this task's scope: a
hand-fitted RV-3028 makes the whole question moot (`time_state 3`, no hold, and the port already
reads it); or the project takes over the core's linker script — a copy of
`nrf52840_s140_v6.ld` with one `(NOLOAD)` section carved out of the low RAM the bootloader does
*not* use, below `0x20007f7c`. That is a fork of a file of a pinned dependency, with a build-time
guard needed to keep it honest, and it is a decision about `docs/upstream.md`'s place 7 rather
than a line of code.

## The flash-wear arithmetic for the file

In `src/clock/ClockKeeper.h`, above `kSaveIntervalSeconds`, and in short here. The file system is
littlefs over **seven 4096-byte pages** at `0xED000` (the core's `InternalFileSystem.cpp`:
`LFS_FLASH_ADDR 0xED000`, `LFS_FLASH_TOTAL_SIZE 7 * FLASH_NRF52_PAGE_SIZE`, `LFS_BLOCK_SIZE 128`),
and the nRF52840's flash endurance is **10 000 erase cycles per page**. A 10-byte file lives
inside a littlefs metadata pair, and a write to it erases at most one 4096-byte page — the core's
flash layer erases the page a 128-byte block sits in when the bytes are not already blank
(`cores/nRF5/flash/flash_nrf5x.c`, `fal_erase`). So the honest upper bound is one page erase per
save:

| Interval | Saves a year | 10 000 cycles reached in |
|---|---:|---|
| once a minute | 525 600 | about a week |
| once an hour | 8 760 | about 14 months |
| once a day | 365 | about 27 years |

That bound is worst-case twice over — littlefs appends several commits into a block before it has
to erase one, and the saves of a running node spread over the pages its pair compacts into — but an
hour is the shortest interval whose *worst* case is years rather than weeks, which is why the task
says an hour and not a minute. **A unit that runs for ten years and is never reset writes about
87 600 times**, so the reviewer may want this longer: the only cost of a longer interval is a
clock that is further ahead of the truth after a power cut, and the Walter corrects it within
seconds of `EV_BOOT` anyway. The interval is one constant, with this table above it.

Three things keep the real rate at or below that bound:

- the file is rewritten **by value**, not by a timer: only when what it holds is more than the
  interval behind the clock. "At most once an hour **however often the time is set**" is therefore
  exact, and `TheFile.IsWrittenAtMostOnceAnHourHoweverOftenTheTimeIsSet` sets the clock 3 601
  times in an hour of clock time and counts one write;
- a clock that is not a time is never saved: a node that is never told the time writes nothing
  at all (`TheBootOrder.WithNoMemoryAtAllTheStateIsUnset`);
- the extra writes are bounded by events, not by time: one per restart the firmware performs
  (plus one on the boot after it, to spend the *clean* flag) and one per forced backwards set.

## Deviations from the spec or the task

- **The surviving-RAM memory is not implemented.** The task's own escape clause, taken with the
  reading above. The `RetainedMemory` port, its checksummed record and every rule that uses it stay
  and are tested with a fake, so the day a place is found it is one class in `BoardClock.cpp`.
- **A *clean* file needs no margin.** The task says the restore is "the file's value **plus the
  save interval** … the node cannot know how long it was down". For one case it *can*: a restart
  this firmware performed itself writes the file in that second, and the nRF52's `RESETREAS` says
  whether this boot followed a software reset — the register is cleared only by a power-on reset,
  so reason 4 proves the chip kept power. So the file carries one flag bit, and a *clean* record
  read after a software reset is used as it stands. This is what makes the bench line
  "`time set`, then `reboot 0`: after the restart `time` is a few seconds on" true without the RAM
  memory. The flag is spent on the boot that uses it (one extra write), so a crash an hour later
  cannot restore an hour-old time as if it were fresh; `ACleanFileStillGetsTheMarginAfterAnyOtherKindOfReset`
  is the other half of the rule.
- **`TIME_SET` refuses an epoch outside a sane window, with `ERR_RANGE`, even with *force*.** §5.4
  does not say this; it says *force* is "for a clock that was set wrong". A clock set to before
  2026 (or after 2099) is not a correction — this firmware did not exist then — and the node could
  not recover from it by itself, because every later set would be "forward". The window is one
  constant, `kSaneEpochFloor` = 2026-01-01, and it does double duty: it is also how the board tells
  "an RTC answered" from "upstream's volatile clock answered" (below).
- **The boot advert's delay is 1500 ms, not upstream's 16 000.** Upstream's example sends it from
  `setup()` with a 16-second delay; ours sends it from `loop()` when the hold lifts, which has
  already waited for either the clock or a minute, so the long delay has nothing left to do. 1500 ms
  is what upstream's own `advert` console command passes (`CommonCLI.cpp:193`). The timestamp is
  taken when the packet is *created*, not when it is sent, so the delay does not affect it either
  way.
- **`src/link/session/Interfaces.h` gains a method on an interface p1-03 declared.**
  `ClockAccess::setTime` is new; everything else about that file is unchanged, and the session
  still answers `kErrUnsupported` when the pointer is null, which is how a build with no clock
  behaves. `tools/linkloop/` and both test suites were updated with it.
- **`docs/ARCHITECTURE.md` §5 is rewritten rather than extended**, because what it described was
  two memories and the one that exists is the file; §1, §2 and §10 are corrected with it, and §11's
  closing paragraph now lists what this task changed. `docs/bench.md`'s p1-01 line said
  `sensor list` answers `1 vars` and p1-03's said `caps 0x00`; both were already or are now stale
  (`4 vars`, `caps 0x40`) and are corrected in place.
- **`tools/linkloop/`'s output directory moved** from `out/p1-03/` to `out/linkloop/`: it is a
  tool two tasks now use, and its clock file lives beside its binary.

## Decisions taken without asking

- **"An RTC answered" is decided from the answer, not from a flag.**
  `AutoDiscoverRTCClock::getCurrentTime()` falls back to the volatile clock when it found no part,
  and its four `*_success` flags are file-static in `AutoDiscoverRTCClock.cpp` at the pin — there is
  nothing to ask. So `BoardRtc::read()` returns `rtc_clock.getCurrentTime()` and the keeper believes
  it only if it is sane; upstream's volatile default of 1715770351 (2024) is years below the floor,
  and so is an RV-3028 that lost its backup. A sane RTC also needs no `setCurrentTime` at boot,
  because on this board the RTC **is** upstream's clock.
- **A boot that restores the clock sets it even when that moves it down.** The only way to reach
  that branch with a later clock is an RTC whose answer failed the sane test — a part reading a date
  in the next century — and leaving the node there would poison every timestamp it ever sends. The
  set also writes such a part, which repairs it.
- **A backwards jump made behind our back is not followed.** The only console command that can make
  one is `clkreboot`, which sets the clock to upstream's 2024 default and reboots immediately; the
  keeper's memories are a high-water mark, so the boot after it restores the saved time. That
  defeats what `clkreboot` is for, and it is the correct behaviour for this firmware — "a clock
  that never runs backwards across a reset" is the task.
- **Four virtuals count as "a timestamp has left this node".** `sendSelfAdvertisement` (which our
  own boot advert and the console's `advert` both go through) and `onAnonDataRecv`,
  `onPeerDataRecv`, `onPeerPathRecv` — the three receive paths upstream answers with a reply
  carrying our clock (`MyMesh.cpp:135` and `:743` take it from `getCurrentTimeUnique()`,
  `:148`–`:200` from `getCurrentTime()`). The last three are read as *may have*: upstream decides
  whether to reply at all, and a request a rate limiter threw away still counts, which errs towards
  refusing a backwards set. Upstream's **periodic** adverts are deliberately not hooked: at the
  default `advert_interval` of 1 the first local one is `futureMillis(1 * 2 * 60 * 1000)` from
  `begin()` — **two minutes** — and the flood one is 47 hours (`MyMesh::updateAdvertTimer`,
  `MyMesh.cpp:1044`; the sends are at `:1294`–`:1305`), both later than the 60-second hold, by
  which time our own boot advert has already said so.
- **`logTx` is not the hook.** It is called for every packet this node transmits, forwards
  included, and a `mesh::Packet` carries no flag that tells an originated packet from a forwarded
  one — so using it would refuse a backwards set as soon as the repeater forwarded anything, which
  on a busy channel is the first second. The four virtuals above are the exact set instead.
- **`rtc_clock.tick()` is called once in `setup()`, before the keeper begins.**
  `VolatileRTCClock` accumulates `millis()` between ticks and its `prev_millis` is set when the
  global is constructed, so the first tick of `loop()` would hand the keeper the whole of `setup()`
  at once — a second or three, including its `delay(1000)` — and the jump poll would read that as
  somebody setting the clock. Upstream's `main.cpp` ticks only in `loop()`; one extra tick in
  `setup()` is the smallest fix and the comment where it is called says so.
- **The jump poll's slack is two seconds.** A clock read a moment after the millisecond clock, or
  an RTC that rounds, may run one second fast; a console `time` sets a clock months out. Two
  seconds is comfortably between them and is a named constant.
- **The file is written in place, not removed and recreated.** `FILE_O_WRITE` is
  `LFS_O_RDWR | LFS_O_CREAT` and seeks to the end (`Adafruit_LittleFS_File.cpp` at the core's pin),
  so a `seek(0)` makes it a rewrite of a fixed-size record. Upstream removes and recreates
  `/prefs.json` instead; in place is fewer commits into littlefs for the same bytes, which is the
  point of the save interval.
- **`/clock` is ten bytes with a magic and a check byte**, and the two records use different magics
  so that one can never be read as the other. littlefs checksums its own blocks; this is against a
  file that is ours in name only, and against the garbage RAM holds after a power cut — which is
  the rule the unimplemented port still needs.
- **Both of the board's deliberate stops write the file first.** `TwinOakBoard::reboot()` and
  `powerOff()` are virtual on `mesh::MainBoard` (`MeshCore.h:54`, `:55`), and every restart this
  firmware performs goes through one of them — the console's `reboot`, `clkreboot` and
  `poweroff`/`shutdown` (`CommonCLI.cpp:184`, `:186`, `:190`) as well as the link's `REBOOT`. The
  link's own `restartNow` saves too, because its bootloader modes 1–3 call the core's DFU entry
  points and never touch the board object. Saving twice in a row writes the same second twice and
  changes nothing.
- **An unknown `TIME_SET` `source` is accepted and ignored.** §5.4 lists 1, 2 and 3; a later minor
  version may add one, and §5.1's versioning rule says a minor adds things. Nothing here behaves
  differently for any of them.
- **`time_state` becomes `set` even on a board with an RTC.** §5.4's table calls 3 *rtc* and the
  task says "a set makes the state 2"; the task is followed literally. On a board with a fitted part
  the next boot reads 3 again, so the only visible difference is between a set and the reboot after
  it, and no batch-1 board can show it.
- **`linkcli.py time` takes its words as one list.** argparse fills a second positional only from
  the arguments *before* an option, so with `epoch` declared as a positional the documented form
  `time set --force <epoch>` would silently lose the epoch (it did, on the first run of the
  loopback script). The sub-command therefore takes `nargs=REMAINDER` and reads `set`, the epoch,
  `--force` and `--source` out of it wherever they appear; `--force` and `--source` are still
  declared so that `--help` lists them. Every form was tried.
- **`tools/linkloop/` gained `--emitted`.** A node that has put a timestamp on the air is the only
  state in which a backwards `TIME_SET` is refused, and the loopback has no radio to do it with. It
  is one flag, and it is what makes the `ERR_RANGE` path and `--force` visible from a laptop.
- **The no-allocation rail now covers `src/clock/`** as well as the box link's two portable
  directories (`test/test_rails`), `BoardClock.cpp` included: the file system's own allocation is
  inside the core's `File::open`, and nothing of ours has a reason to add to it.

## Not verified here (and why)

Added to `docs/bench.md` as section **3. The clock**, tagged **p1-04**, and `docs/link.md` §2a is
the page that walks them. In short, and each for the same reason — no clock has ever ticked on a
RAK4630:

- **`time` on a freshly flashed node** says `unset` and a date in May 2024, with `status` flag bit
  3 set.
- **`time set`, then `reboot 0`**: after the restart `restored`, a few seconds on, not 2024 and not
  an hour on — the *clean* file path, which is the one deviation in this task that only a board can
  confirm.
- **The reset switch and a watchdog reset**: `restored`, but up to an hour ahead rather than a few
  seconds, because those give the firmware no chance to write and this board has no surviving RAM.
  That difference is the whole of the finding above, and the bench is where it becomes real.
- **A power cycle**: `restored`, the saved time plus an hour or less, `reset_reason 1`.
- **The hold, on the air**: with no laptop attached a nearby companion sees the advert about a
  minute after boot and not before; with `time set` within a second of `EV_BOOT`, at once. No
  session can hear a radio.
- **A companion that saw this repeater before a power cycle still accepts its adverts after it** —
  the point of the whole task, and only a second node can say it.
- **The console**: `sensor get clock.state` matching `status`, and upstream's own `time <epoch>` and
  `clock sync` moving the state to `set` within one pass. The poll has a native test against a
  fake; upstream's CLI has never run.
- **An RV-3028 hand-fitted**: `time_state 3`, no hold, and a set written through to the part. The
  part is on worldwide allocation and no board has one.
