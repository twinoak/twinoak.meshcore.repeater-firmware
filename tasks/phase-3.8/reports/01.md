# p3.8-01 — HELLO says its band

Link **1.1** on the radio. `kProtoMinor` is `1`, `HELLO`'s answer and `EV_BOOT`
end with the image's `band` — `868`, read out of the running image's own
descriptor and not from a define — and a Walter that asks in 1.0 is answered in
1.0, without it. Nothing else of the link changed: no new type, no new
capability bit, no change to any payload that existed.

The one place the firmware says which minor it speaks is now `kProtoMinor`
(`src/common/link/codec/Numbers.h`). The image descriptor's `link_minor` was
already built from it; `tools/release/build_release.py`'s `link_version` now
reads it too, instead of a fixture file's `link` field — which had stopped being
the answer the moment 1.1's fixtures arrived beside 1.0's, because
`link-v1.json` is 1.0's and never changes. Both board images now carry
`link 1.1` in their descriptors, and a dry-run manifest says
`{"major": 1, "minor": 1}`.

`tools/verify.ps1` is green on this machine, every step.

## Deviations from the spec or the task

- **None of substance.** The specification and the task agree; `spec/` was not
  edited, and `python spec/tools/specsync.py verify spec` passes (41 files).
- The task says *`build_release.py`'s `link_version`, which reads
  `link-v1.json`* and then asks for the firmware's constant instead. Taken as
  written: it now reads `kProtoMajor`/`kProtoMinor` out of
  `src/common/link/codec/Numbers.h` and raises `ReleaseError` naming the missing
  constant if either line is gone, so a rename stops a release rather than
  letting it guess
  (`test_the_link_version_is_refused_when_the_constants_are_gone`). A second
  test holds the newest fixture file in `spec/fixtures/link/` against that
  constant, so firmware and specification drifting apart is a red release step.
- **Two tests belonging to earlier tasks had the old minor written into them and
  had to change.** `tools/release/test_release.py`'s
  `TheDescriptor.descriptor()` synthesised a descriptor with
  `link_major, link_minor = 1, 0`; with the manifest at 1.1 that made
  `test_with_the_flag_a_matching_descriptor_passes` fail with *link_minor is 0,
  the manifest says 1*. It now takes the link version from `build_release` — the
  same place a release reads it — so the next bump does not break a test that is
  about the version string and the board, and a new test covers the mismatch
  deliberately (`test_a_descriptor_of_another_link_minor_is_refused`).
  `tools/bench/test_walk.py`'s and `test_bench.py`'s canned `linkcli` output now
  say `protocol 1.1` with a `band` line, which is what the tool prints.

## Decisions taken without asking

1. **`band` is gated on the body's own `proto_minor`, not on a flag the session
   passes.** §5.1 says *present when this body's `proto_minor` is 1 or more*, so
   the body carries the whole truth about itself and the encoder needs nothing
   else. `Session::helloBody()` fills `band` in at every minor; only the encoder
   decides. That is what makes `EV_BOOT`'s *as the RAK speaks it* and `HELLO`'s
   *highest minor both ends know* the same one line of code.
2. **An empty band in a 1.1 body is a zero-length `str8`, not an omission.** A
   role with no band to report still writes the field, because a receiver reads a
   `str8` there and a body that simply stopped would be a 1.0 body claiming to be
   1.1 (`TheBand.AnEmptyOneIsAZeroLengthStringAndNotAnOmission`). Nothing in this
   repository reaches it — the repeater always has a band — but `Firmware::band`
   defaults to `""` and the rule had to be one way or the other.
3. **Only the repeater speaks the link, so only the repeater reports a band.**
   Read, as deliverable 2 asks: `src/roles/scanner/` has no `Session`, no
   `SerialTransport` and no `HELLO` — it speaks NDJSON on the same UART
   (`spec/LINK-PROTOCOL.md` §9, `docs/noisescope.md`), and its only mention of
   the link is a comment saying `Serial1` is where it is. It was left as it is.
   Its *descriptor* does move to `link 1.1`, because `ImageDescriptor.cpp` builds
   that field from `link::kProtoMinor` for every image — which is right: the
   manifest's `link` is one field for the whole release and
   `build_release.py` checks every image's descriptor against it, so the two
   images must agree.
4. **Both fixture files are run, not just the newest.** The task says *add the
   new file beside the old one*. `cases()` is the concatenation, each `Case`
   carries which file it came from (so a failure names the file), and
   request/response pairing is within a file — 1.1's HELLO answer at seq 41 is
   not 1.0's at seq 1. The four parts of a fixture file that 1.1 did not touch —
   `crc16`, `cobs`, `invalid`, `stream` — are proved byte-identical between the
   two files once (`TheTwoFixtureFiles.DifferOnlyInTheirCases`) and then read
   from 1.0's file; a generator that ever made one of them depend on the minor
   fails that test and names the part.
5. **`test/test_clock` was left reading `link-v1.json` by name.** It drives only
   the `TIME_SET`/`TIME_GET` cases through a real session, and those are the same
   bytes in both files; 1.0's file is the one that can never change, so naming it
   is the stabler choice. Nothing in that suite touches `HELLO` or `EV_BOOT`.
6. **The run record keeps the band in `board_said`, not as a field of its own.**
   `RunRecord.FIELDS` is what `bench restore` decides from (the role, the
   version, the identity, the image); the band is something the board *said*,
   which is what `board_said` is for.
7. **`tools/verify.ps1`'s `link` step has one row and one log per fixture file.**
   `Invoke-Logged` writes a log rather than appending to one, so a loop over two
   files inside one row would have thrown the first file's output away.
8. **The bench lines were written for §2 and §8, in the order the rig comes up**
   — the dongle and `linkcli.py` in §2; §8's existing
   descriptor-against-the-unit line gained `band`, and its anchor text is
   unchanged so `bench walk 8 --tick` still finds it.
