# p3.2-01 — a bump can be green

The two `ThisBuildSaysThePinOfPlatformioIni` tests built the strings they
expected out of `repeater-v1.17.1` and `d9296435` as literals, so every
MeshCore bump was red before a line of upstream's had been read, and tier one
of `docs/upstream.md` — a green pull request a person merges — was unreachable
for free. They now build what they expect out of the same two defines the code
reads, and still fail a build whose defines did not arrive. A rehearsal bump
proved it where it matters: CI on the pull request the upstream watch opened
was **green**, with no session anywhere near it.

## What the tests say now

`versionString()` and `upstreamString()` are `formatVersion` and
`formatUpstream` over four defines (`src/common/version/Version.cpp`), so there
are two statements to make and they are now made separately:

- **the defines reach the string** — `Version.ThisBuildSaysThePinOfPlatformioIni`
  and `Upstream.ThisBuildSaysThePinOfPlatformioIni` build what they expect from
  `TWINOAK_MESHCORE_TAG` and `TWINOAK_MESHCORE_PIN` and, before that, `ASSERT`
  that the tag is not empty and that the pin is forty hex digits — a git
  commit. A build whose `-D` did not arrive fails on the assertion, with the
  macro's value in the message; a build whose defines arrived but are not
  plumbed through to the string fails on the comparison. That is what the
  literals were doing, minus the release.
- **the shape** — `Version.TheShapeDoesNotDependOnTheRelease`, through the seam
  those two functions are, with a made-up tag and pin (`repeater-vX.Y.Z`,
  `0123abcdef…`): `twinoak-repeater 1.0.0 on MeshCore repeater-vX.Y.Z
  (0123abcd)` and `repeater-vX.Y.Z+0123abcd`, and the eight digits of the one
  are the eight digits of the other. `spec/LINK-PROTOCOL.md` 5.1's field keeps
  its own fixture tests in `test_link_session`, which pass the tag in as data.

`tools/release/test_release.py` gets the same treatment one level up: its
synthetic `buildinfo.json` — a build directory that was never built — says
`repeater-vX.Y.Z` and a plainly synthetic commit, both out of one module
constant `UPSTREAM`, and `test_the_upstream_pin_is_the_builds` holds the
manifest's whole `upstream` block against it instead of a tag it restated.

## Deviations from the spec or the task

- **"the seven places of `tasks/sync/TEMPLATE.md`" is eight.** The task's
  `docs/upstream.md` deliverable calls the re-read list seven places;
  `docs/upstream.md`'s table and the template's step 3 have had **eight** since
  phase 1 (the eighth is what our sources take from upstream's headers). The
  "seven" is `.github/workflows/upstream.yml`'s pull-request body, which lists
  seven and leaves the headers out. Eight is what the rewritten section says.
  That body is not a deliverable here and is left as it is — but it is exactly
  what a person reads before merging a green bump, so the one-word drift is a
  reviewer's to close.
- **Four more tests in `test_version.cpp` carried the real tag and pin**, as
  arguments rather than as the subject: `Version.FormatsTheThreeParts`,
  `Version.TruncatesAndSaysSo`, `Upstream.FormatsTheTagAndEightDigitsOfThePin`
  and `Upstream.TruncatesAndSaysSo`. The acceptance criterion's grep allows no
  literal tag or pin in the file at all, so those four take the same made-up
  pair. Every expectation but the tag's own characters is unchanged, and the
  two truncation cases cut in the same place because `repeater-v` is the same
  ten characters either way.
- The task allowed "say so and keep the macro-based assertion only" if
  `versionString()` had no seam for its inputs. It has one — `formatVersion`,
  which is what the file's other cases already use — so the shape test was
  written.

## Decisions taken without asking

- **A synthetic constant in `test_release.py`, not a read of
  `platformio.ini`.** The task allowed either. That file already reads
  `platformio.ini` where the subject *is* the real thing (`platformio_images`,
  for the `[img_*]` names); the subject here is a build directory the test
  invented, so a value that is plainly not a release says it better and keeps
  the test readable as "whatever the build said".
- **The pin is held to forty hex digits; the tag only to being non-empty.** A
  pin is a git commit and that shape is upstream-proof. What a tag looks like
  is MeshCore's business, and `repeater-v*` is already asserted where it
  belongs — `tools/upstream-check.ps1`, which is what picks the tag. A test
  insisting on `repeater-vX.Y.Z` would be a new way for a bump to be red.
- **The same made-up pair in both languages** (`repeater-vX.Y.Z`,
  `0123abcd…`), so that one grep finds every synthetic site in the repository.
- **The bench line is an amendment of an existing one, not a new one.** This
  task's *Not verified here* is the first real bump, which is already
  `docs/bench.md`'s p0-03 line; a second line for the same walk would be a
  second thing to tick. That line now says what green means and names this
  task and this report.
- **`origin/main` was two commits behind the local trunk** — `c155a1d`
  "p3.1 review" and `aa8652b` "Phase 3.2; spec refreshed", the reviewer's own,
  carrying this phase's task files and the `spec/` refresh — so a pull request
  from this branch would have contained them. They were pushed to `main`
  first, a fast-forward, which is where they were going anyway; this pull
  request is this task's one commit and the report.
- **The rehearsal was dispatched on this branch's ref**, not on `main`:
  `workflow_dispatch` takes the workflow *and the tree* from the ref it is
  given, and the point was to see the new tests in a bump's CI. Its held run
  was approved with the `gh api` line `docs/upstream.md` gives, which is the
  same click that page says a person makes for a real bump.

## Not verified here (and why)

- **The first real bump: the next `repeater-v*` tag MeshCore publishes.**
  `repeater-v1.17.1` is still the newest tag upstream has (`git ls-remote
  --tags` of `[meshcore].url`, 14 October 2026), so the rehearsal bumps from
  `repeater-v1.17.0` to the pin we are already on: it proves the path, the
  pull request, the approval click and a green CI, but not a tree nobody here
  has compiled yet. `docs/bench.md`'s p0-03 line is that walk, amended by this
  task; it needs the Monday and the tag, and neither is a session's to make.
- **A future tag longer than `repeater-v1.17.1` moves an arithmetic no test of
  ours would notice.** `sensor list` is cut at upstream's 134 bytes and
  `fw.version` carries the whole version string, the tag included
  (`src/roles/repeater/app/Settings.cpp`); `test_settings`' `SensorList.*`
  cases count those bytes off a fake whose version string is a fixed-length
  literal, so a two-character-longer tag changes what the device prints and
  not what the tests assert. That is green CI not speaking for the device —
  the kind of thing place 5 of `docs/upstream.md` exists for — but those fakes
  are not a bump's to fix and this task did not touch them. It is worth a
  follow-up for whoever owns `Settings` if the paging line of `docs/bench.md`
  §5 ever reads differently from the test.
