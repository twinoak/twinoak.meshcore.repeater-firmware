# p3.4-01 — the base in the release

A factory RAK4630 carries RAK's RUI3, not the MBR, the SoftDevice S140 6.1.1
and the bootloader this firmware is linked against. The Walter writes that base
once, on a person's `rak provision` (`spec/SYSTEM.md` S-5a), from the release's
`provision` file (`spec/FIRMWARE-MANIFEST.md` §4a). This task puts that file in
the release: a binary nobody here built, vendored byte for byte at a pinned
source, its hash written down, held to §4a on every run, and refused by the
release when it is missing or has changed.

**What was vendored:** RAKwireless' combined bootloader + SoftDevice
`wiscore_rak4631_board_bootloader-0.4.4_s140_6.1.1.hex` from
`RAKWireless/WisBlock` at `d3da249c0e4df56fb972021cf6e99239f27857bf`
(2026-07-23), `bootloader/RAK4630/Latest/`, git blob `0d8085df…`, SHA-256
`e19bad05e2be9fbdd4f4ec564eb1ff605d495ffe42eb90410e5162792e1ca5bd`, 509 804
bytes. Bootloader 0.4.4 (RAK's build of the Adafruit nRF52 bootloader for the
WisCore RAK4631, built Jun 17 2026), SoftDevice S140 6.1.1. `manifestref.py
base` against `0x26000`..`0xED000`: bootloader at `0x000F4000`, MBR parameter
page `0x000FE000`, 185 328 flash bytes, UICR words `NRFFW[0]` and `NRFFW[1]`
only. `boards/base/rak4630/README.md` is the long form.

**The two candidates, the three questions** (the task's order of preference:
passes §4a, built for the RAK4631, MDK 8.40.2 or later):

| | RAK's 0.4.4 + S140 hex | Adafruit's release for the RAK4631 |
|---|---|---|
| passes §4a | **yes**, every rule, against the release's region | **no such file**: `adafruit/Adafruit_nRF52_Bootloader` has no `wiscore_rak4631_board` under `src/boards/` (51 boards at `0.11.0`) and no release of its 33 carries an asset with *rak* in its name. Its PCA10056 file of the same shape passes §4a, for what that is worth |
| built for the RAK4631 | **yes**: the file's own strings (`Model: WisBlock RAK4631 Board`, `Board-ID: WisBlock-RAK4631-Board`), RAK's 0.4.3 board directory, RAK's README | **no** |
| MDK 8.40.2 or later | **unknown from the source — the first board says** (below) | **no**: `lib/nrfx` at `0.11.0` is `7a4c9d94`, MDK 8.29.0, and the Makefile compiles that MDK's `system_nrf52840.c` |

Only one candidate exists for this board; it passes the first two questions.

**The APPROTECT question.** RAK does not publish 0.4.4's source (its README:
*"Full bootloader source is maintained separately"*; no RAKwireless repository
on GitHub is it). The 0.4.3 source RAK publishes beside the file is Adafruit's
bootloader *0.6.2-11* with nrfx vendored in at **MDK 8.29.0** — no APPROTECT
handling. The bootloader region of the 0.4.4 file (not the SoftDevice: its
licence forbids that) was disassembled with the pinned toolchain's
`arm-none-eabi-objdump` and compared with two bootloaders of known MDK 8.29.0
(RAK's 0.4.3; Adafruit's 0.9.1 for the PCA10056, nrfx v2.0.0, which the pinned
Arduino core ships): all three reach UICR through `mov.w rX, #0x10001000` and
read only `REGOUT0`, `PSELRESET` and `NFCPINS`; none reads `UICR.APPROTECT`
(`+0x208`) and none stores to `APPROTECT.DISABLE`/`FORCEPROTECT`. That is
evidence the 0.4.4 build has no APPROTECT handling — but it is a binary read
without a positive control, so the README records it and writes the answer the
task asked for when the source cannot tell: **unknown, the first board says**.
Two consequences worth stating plainly: (1) if the first radio is a revision 3
part (`INFO.VARIANT` `AAF0`), the port will most likely read *closed* after
`rak provision`'s reset, which is the hardware repository's
`software/FIRST-UNIT.md` step 8 — stop and decide a bootloader built from MDK
8.40.2 or later; (2) the application does not rescue it, because the pinned
Arduino core (MeshCore's fork of `Adafruit_nRF52_Arduino`) is MDK 8.30.2 and
does not touch `APPROTECT` either (`out/p3.4-01/` has the disassemblies and
`scan.py`).

- **The task's stop clause on the MDK was read against the deliverable's

## Decisions taken without asking

- **The vendored file keeps RAK's name** (`wiscore_rak4631_board_bootloader-0.4.4_s140_6.1.1.hex`)
  and the release renames it to the task's. A reader comparing the repository
  with RAK's directory sees the same name; the hash is the pin either way.
- **`base.json` beside the README.** The task asks that the check hold the
  file's hash and summary to *the README's*; parsing a Markdown table in CI is
  brittle, so the pin is a small JSON the check reads, and the check also
  holds the README to it (`check_readme`: the hash, the file name, the
  versions, the source commit and path, the bootloader's and MBR page's
  addresses and the byte count must all appear in the README's text). A README
  that says other numbers fails (`test_a_readme_that_says_other_numbers_is_refused`).
- **Which boards need a base is one tuple**, `FAMILIES = ("rak4630",)` in
  `tools/base/check.py`: an image whose `board` is `<family>-…` must carry the
  family's base, and a family image with no pin directory is a refused release
  rather than a release without a base. `rak4630-dual-a`, when it exists, gets
  the same file with no change; a board of no family (the fixture's `walter`)
  gets none.
- **The notices file is in the release but not in the manifest.** It is not a
  way of delivering an image, so it is not a `files` entry; it lies beside the
  manifest, `SHA256SUMS` covers it, and `gh release create out/release/*`
  uploads it. The workflow's release notes list it.
- **`selfcheck.py` runs the base check as its own stage** (`--only base`),
  between the tests and the dry run, so a changed file fails with the check's
  own line before the dry run would.
- **`sign_manifest.py` checks the base before it touches a key**, so a manifest
  without its base produces no `.sig` and the refusal never carries a key.
- **The disassembly was of the bootloader region only** (`0xF4000`–`0xFD858`),
  never of the SoftDevice: Nordic's licence clause 5 forbids disassembling the
  SoftDevice binary, and the question was about the bootloader. The outputs
  stay in `out/p3.4-01/` (git-ignored) for the reviewer.
- **The release-notes table lists the base once**, not under each image: it is
  one file under several images, and a table with the same row twice reads
  like a mistake.
- **`docs/ARCHITECTURE.md` §9's flash map now names the base's pages**, the
  MBR parameter page (`0xFE000`) and the bootloader's settings page
  (`0xFF000`, not in the base; the bootloader writes it), and `boards/README.md`
  says that `base/` is not upstream's and that a pin bump does not touch it.

## Not verified here (and why)

`rak provision`, the hardware repository's `walter-swd-bench`, or a probe).
The line is in `docs/bench.md` §0, *p3.4-01*, in the order the rig is brought
up — before everything else, because nothing else boots without it:

- **The base boots.** After `rak provision` and its one reset, the radio
  enumerates as the RAK4631 bootloader (VID `239A`, the `RAK4631` drive on a
  double-tap) and `INFO_UF2.TXT` reads `UF2 Bootloader 0.4.4`, `SoftDevice:
  S140 6.1.1`, `Date: Jun 17 2026`: the file that was vendored is the one that
  boots. The Walter's phase 6 task 03 is where this first happens; this pile's
  02 starts from the radio it leaves.
- **`INFO.VARIANT`** of the first part, and **the port after the reset** as
  `rak provision` reports it. *Closed* on a build code `F` part means this
  bootloader was built from a Nordic MDK before 8.40.2 (what the binary read
  predicts) and S-5's SWD path is gone after every reset: `FIRST-UNIT.md`
  step 8, stop and decide. *Open* settles §10.2 the other way. Either answer
  goes into `boards/base/rak4630/README.md`'s APPROTECT section and the
  hardware repository's `PROJECT-KNOWLEDGE.md`.
- **The Walter's half of §4a** — that its reader refuses each `base-*.hex`
  fixture with the same words and accepts this file against *its* board region
  (§5's 5p) — is `twinoak.meshcore.walter-firmware`'s own tests.
- **A tagged release** with the real key, carrying this file: Thomas pushes
  the tag (`software/FIRST-UNIT.md` in the hardware repository). The dry run
  here and in the workflow's *Run workflow* path is the same code.
