# p3.4-02 — The first board

A RAK4630 on the production adapter, with RAK's bootloader and S140 under it and **no application
at all**, on this machine's USB as `E926F6BEB407A412`, a 50 Ω dummy load on the antenna port and
`"identity": "disposable"`. The four walks of `docs/bench.md` have met a board for the first time:
**§1, §8, §9 and §10 walked, 13 of the page's lines ticked as *bench*, one *differs* left** (the
whole-range `scope` baseline, which is a radio finding and a follow-up), and the board left
running this commit's repeater image with the identity its last first boot made.

The board did what the page says almost everywhere. What it did not do was mostly *this tool's*
picture of a board rather than the firmware's behaviour, and twelve such things are fixed here,
each with a host test first: a port Windows lists before it can be opened, a console that dies
under its own `reboot`, a boot banner no host can catch, the touch's own DFU product id,
`adafruit-nrfutil` exiting 0 on a failed write, upstream printing every digit of the floats it
keeps, this build's node name, and a scanner whose watchdog ends the DFU that would replace it.
`tools/bench`'s host tests went from 79 + 43 to **100 + 51** cases.

## What the walks found, and what was done about it

Each of these was found by a board and none of them could have been found without one. Every fix
is in `tools/bench/` with its host test written first, and the test names say p3.4-02.

1. **A port Windows lists before it can be opened.** The very first `bench flash` wrote the image
   (`Device programmed.`), the application enumerated as COM30, and the open of it failed with
   `FileNotFoundError(2)`. `Ports.open_ready(device, baud, timeout_s)` now retries an open until
   the deadline, and every console open of a port that has just come back goes through it
   (`ThePortLayer`, and `AFlash.test_a_port_listed_before_it_can_be_opened_is_waited_for` with a
   fake whose first opens raise). The bootloader's port is proved the same way before
   `adafruit-nrfutil` is handed it.
2. **A console dies under its own `reboot`.** `reboot` resets the part as the line is taken and the
   USB device goes with it, so the next read of the open handle raises
   (`SerialException … OSError(22) … 433`) instead of timing out — `bench record` died there.
   `RepeaterConsole.send_reset` is the line for a reset: the port going away *is* the reset. The
   fake board now takes its port down on a reset too, which is what made the rest of this list
   testable. Measured on the board: the port is gone 0.2 s after the line and listed and openable
   again at **1.4 s**.
3. **The boot banner is not readable, and the key is.** `Repeater ID:` is printed about a second
   after boot and only while a host holds the port, and the port is not back before 1.4 s: neither
   the first open nor the `reboot` the tool used to perform caught it. Upstream's own
   `get public.key` is the same 32 bytes (`src/helpers/CommonCLI.cpp:902` at the pin `d9296435`,
   `mesh::Utils::toHex(getSelfId().pub_key)`), so the record, the restore's identity check and §1
   read it from there — and **§1 now resets nothing at all**. p3.3-02's report says upstream has no
   line that prints the public key; the board says otherwise.
4. **The touch's DFU is product id `0x002A`.** `bench walk 8` waited 15 s for `0x0029` while the
   board sat in the serial-only DFU under the other id. `boards/rak4631.json` lists all four ids,
   and `ports.py` now takes both bootloader ones and both application ones — held to that file by a
   test, so the two lists cannot drift from the board file the build uses.
5. **`adafruit-nrfutil` exits 0 when its write failed.** It printed the traceback of
   `WriteFile failed (PermissionError(13) … ERROR_BAD_COMMAND)` and exited **0**, so the tool
   believed the flash and then waited 40 s for an application that was never written. What the tool
   holds it to now is its own `Device programmed.` line.
6. **The scanner's watchdog ends the DFU that would replace it.** `wdtBegin()` starts the
   nRF52840's WDT at 8 s and a soft reset does not stop it, so after the touch the bootloader has
   about eight seconds to take a 414 KB image and does not get there: the DFU dies mid-write, the
   watchdog resets the part, and the board comes back in its full bootloader with no application —
   twice in a row, each time ending `bench walk 9` with a failed restore. The tool now waits for
   the port the DFU died on to **go**, finds the bootloader the board is in now, and runs
   `adafruit-nrfutil` once more (never twice). On the board: `3b. … the board reset under the DFU
   and is in its bootloader on COM29 - once more` → `Device programmed.` → the repeater back with
   its identity. Whether the scanner should keep a watchdog it cannot be updated through is a
   decision for its role and is an open item in `tasks/phase-3/FOLLOWUPS.md`.
7. **Upstream prints every digit of the floats it keeps.** `get radio` answers
   `869.6179809,62.5,8,8` for the band's `869.618` (a `float` holding 869.618 MHz to 19 Hz) and
   `get lat` answers `55.3250007` for `set lat 55.3250`. The walk compares those as numbers now
   (`same_radio`, `same_number`), and the spreading factor and the coding rate are still exact. The
   page's quoted frequency is unchanged, because it is right.
8. **The node name is this build's, not upstream's.** §10 held `get name` to upstream's `repeater`;
   `platformio.ini:410` builds with `-D ADVERT_NAME='"RAK4631 Repeater"'`, which is what a fresh
   unit answers. The walk reads it out of `platformio.ini` (as it already read the band's numbers)
   and `docs/bench.md` §10 now quotes this build's name with upstream's beside it.
9. **The scanner's `boot` line is a race, and `info` is not.** When no `boot` line was caught, 9.1
   is held to `info`'s own `fw`, `role`, `board`, `ver`, `reset` and `radio_ok`, with a note saying
   so — the same fields, from a line that is answered rather than announced.
10. **A walk whose restore cannot flash keeps its result file.** The two failed restores raised out
    of the walk and took twenty minutes of evidence with them. A restore is a step like any other
    now: a *differs*, and the file is written.
11. **A `scope` that stopped itself says why in the result file.** The baseline's step printed
    `0 frame(s) in 20 s` and kept the reason only in the NDJSON; it now prints the device's own
    `err` line, which is how 9.9's finding became readable.
12. **`test_walk.py`'s fixture starts from an unticked page.** The walks' own tests copy
    `docs/bench.md` and assert what ticking does to a line; a page with ticks in it (which is the
    point of this task) made three of them red. The copy is unticked in `setUp`, and the bullets'
    text — what the anchors are held to, both ways — is the committed one.

## Deviations from the spec or the task

- **The page was wrong in three small places and is fixed here rather than followed up**, because
  in each the board is right and the page quoted something else: `get name` (upstream's default
  instead of this build's `ADVERT_NAME`, §10) and the two float read-backs of `get radio` and
  `get lat`, which the walk now compares as numbers. `spec/` says nothing about any of the three.
- **§10's two `First boot:` lines are *needs a person* when they are not caught.** They are printed
  before any host can hold the port; one run of the walk caught them and three did not. What they
  leave behind — a new key and `firstboot.state` → `done` — is checked either way, and the page
  says what a person needs (a terminal already open across the reset button). The run whose result
  file is in the table above caught both lines, so 10.1 is ticked on its own evidence.
- **The task's order is `status`, then walk 1, 8, 9, 10; the board needed a flash first.** It
  arrived with no application, so `bench walk 1` had nothing to talk to: the first `bench flash` of
  this commit's repeater image gave it one (and its first boot, §10's own *First boot*, made the
  identity `A76C9F71…`), and the walks followed. That first flash is the one that found finding 1.
- **A second `bench record --image …` was needed to make the run restorable.** A board found in its
  bootloader records `role: None`, which no restore can read; the state to put back on a first unit
  is this commit's repeater image. Item for the reviewer in [`FOLLOWUPS.md`](FOLLOWUPS.md) — the
  message should name the command, or `bench flash` should record the image it is about to write.
- **`bench walk 9` still exits 1**, because 9.9 is a real *differs*: the walk's own rule is that a
  *differs* is never fixed by the walk. The other eleven lines of §9 are ok or a person's.

## Decisions taken without asking

1. **A radio that arrives with a base and no application is a valid start, and its first boot is
   the identity it keeps.** The task's own deliverable says so; what this adds is which identity
   that was (`A76C9F71…F997DE`) and that §10 then replaced it twice, by design, on a bench whose
   `identity` is `disposable`.
2. **Every fix above is in `tools/bench/`, none in `src/`.** The firmware did what the page says
   everywhere a board could show it. The one firmware-shaped finding — the scanner's watchdog
   against its own DFU — is a decision about the role (keep the watchdog and take two DFUs, or drop
   it), not a line to change in this task, so it is an open follow-up with the ways out written
   down.
3. **One retry of `adafruit-nrfutil`, never two.** The failure mode is a board left in a bootloader
   with no application: the next attempt from there is what writes the image, and a third would
   hide a board that is genuinely not taking it. The tool says what went wrong both times and still
   ends with the double-tap sentence.
4. **The `-707` baseline is a follow-up, not a fix.** `scope 150 960 2048` stops at the third
   segment with `RADIOLIB_ERR_SPI_CMD_FAILED` out of `armSegment`, and which of its four RadioLib
   calls returned it cannot be told from the host. Eleven spans were measured to bracket it (one
   and two segments stream; four and more fail or go silent) and the table is in
   `tasks/phase-3.1/FOLLOWUPS.md`. Changing `src/roles/scanner/` for it is phase 3.1's line and
   needs the radio in front of whoever does it.
5. **The three `[3.3]` items of phase 3's follow-ups are answered in that file, not ticked** (the
   reviewer ticks): `radio_ok` is true with the power pin high, the scanner → repeater round trip
   kept the identity (in two DFUs), and the power cut during a first boot is written as *needs a
   person* with the exact moment to pull the power.
6. **The serial numbers are in the repository.** `bench.local.json` is git-ignored because it is a
   machine's file, not because a FICR device id is a secret; the task asks for the two numbers in
   the page, and the table there is what lets the next session recognise this board.

## Not verified here (and why)

Nothing below can be done by a session: each needs a radio, a phone, an instrument, a hand on the
board or another repository. The page's own right-hand column (`docs/bench.md` §0b) is the list,
and these are the lines of it still open after this walk.

**§1, the repeater alone on USB**
- **The adverts and the repeating**: `neighbors` after a few minutes on the roof antenna, and a
  message through it from a phone. A session cannot hear a radio.
- **The passwords**: that a phone login with `password` and with `not-a-password` is refused, that
  one set with `password <something>` is accepted and survives a power cycle with no `First boot:`
  line. The console refuses to send a password line unless the bench is disposable.
- **`INFO.VARIANT`** off the bootloader's own drive (the tool never mounts it), for the Walter's
  flasher.
- **I2C at 100 kHz** on a scope probe at P0.14, and a BME280's telemetry from a phone.
- **The two USB serial numbers by hand**: the double-tap reset and the power cycle. All three modes
  of this board reported the same number (§0a), but a session cannot press the button.
- **What the tool refuses with `rf: antenna`** in `bench.local.json`: the person's own file.

**§8** — the Walter's half, which is `twinoak.meshcore.walter-firmware`'s own tests against the
same fixtures. And **8.2**, `hello` over the link, was skipped: no dongle in `bench.local.json`
(`dongle_serial`), so the link's half of §8 and §10's provisioning over the link are untried on
this board.

**§9, NoiseScope**
- **`pwr` against the repeater's `power`** on the production connector boards, with a bench supply:
  the scanner's numbers are in the result file; the repeater's half needs the other firmware on the
  same board and a reading to compare.
- **The watchdog**, which needs an induced hang. The one thing this session saw of it is that it is
  live enough to end a DFU (finding 6), which is evidence that it runs — not that a hang ends in
  `reset` reading `wdt`.
- **The fast sweep's three instrument lines**: the image check with the tinySA Ultra as a generator
  (the line that may lower `kScopeSegmentMhz`), the site through the cavity filter
  (`scope 791 960`, six segments, so it needs the `-707` finding settled first), and ten minutes of
  `scope` from the Walter UART with two consoles open at once.
- **The whole-range baseline** (`scope 150 960 2048`): not a person's line in principle, but it
  cannot be captured until the segment finding is fixed. The NDJSON of the attempt, with the
  device's own `err`, is `out/bench/baseline-150-960-20261022-174804-9fb721b.ndjson`.

**§10, first boot and provisioning**
- **A power cut in the middle of a first boot**, three or four times: `bench console "erase"`, then
  pull the USB power **within the first second** of the boot that follows, before the two
  `First boot:` lines appear; on the next boot read `sensor get firstboot.state`,
  `get path.hash.mode` and `get dutycycle`. What must never be seen is no `First boot:` line
  together with `path.hash.mode` `0` or `dutycycle` `> 50.0%`.
- **The two `First boot:` lines read on purpose**: a terminal already open across the reset button.
- **A phone logging in as admin** — and for this unit that means setting a password of your own
  first: the one the walk used is a bench unit's and nobody has it.
- **Provisioning over the link** (`linkcli.py provision`), which needs the 3.3 V dongle on the
  adapter's link pins.

**§0, before the rig** — p3.4-01's four base lines (the `INFO_UF2.TXT` of the file that was
vendored, `INFO.VARIANT`, the port after the reset, the first ordinary install) are still a
person's: this board's base was written before the session started, so nothing here shows that
*the release's* `twinoak-base-rak4630-0.4.4-s140-6.1.1.hex` is the file that booted it.

**The board, as it was left.** This commit's repeater image; `Repeater ID`
`3A51B0931439A3795A00BCD80183C821BFE8CA8AAC828D3AEF139D8BE8541052`; name `bench-walk`;
`region default` `dk`; the lat and lon of `docs/provisioning.md` §3's bench values; an admin
password nobody has; `firstboot.state` `never`; no run open and no lock held. A spare, which is
what `"identity": "disposable"` said it was — if it is to become a unit, `erase` it and provision
it for the site.
