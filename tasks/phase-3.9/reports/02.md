# p3.9-02 — The local request (link 1.2)

else: the link had no request that yields a status, a neighbour list, an access list or the owner
info, so meshmaster.dk showed that repeater *stale* for good. Link 1.2's `LOCAL_REQUEST`
(`spec/LINK-PROTOCOL.md` §5.9) is the answer Thomas settled on on 7 November, and this task makes
the repeater speak it — **with upstream's own request handler, and not one file of MeshCore

## Deviations from the spec or the task

- **The fixtures add no 1.2 `EV_BOOT` case, and a 1.2 radio's `EV_BOOT` is not 1.1's bytes.**
  `spec/fixtures/link/link-v1.2.json` has two `EV_BOOT` cases and both are older — *boot event*
  (minor 0) and *boot event, 1.1: the band at the end* (minor 1, `caps 0x7f`). But §5.1 says
  `EV_BOOT` carries the `HELLO` body "as the RAK speaks it", so a 1.2 radio's boot event has
  `proto_minor` 2 and `caps` with `0x80` in it, and neither case is those bytes. 1.1 did add an
  `EV_BOOT` case for exactly this reason; 1.2 did not.
  **What was done:** `test/test_link_session`'s EV_BOOT test is now
  `TheBootEventIsTheNewestHelloBodyAfterAResetReason` and holds the event against the **1.2 HELLO
  response case's own payload** past its status byte, with the reset reason in front — which is
  the whole of what §5.1 defines `EV_BOOT` to be. The payload compared is still the fixture's own
  bytes; only the framing is this firmware's, and the codec suite holds `FrameWriter` against
  every frame of every file. 1.0's and 1.1's `EV_BOOT` cases are still encoded byte for byte by
  the codec suite. **For the specification's owner:** `spec/tools/linkref.py`'s 1.2 case list
  could add a `boot event, 1.2` the way 1.1's did, and then this test goes back to comparing a
  frame.

  edited (`specsync verify`: 42 files, all as the manifest says).

## Decisions taken without asking

- **`caps` carries `0x80` whatever minor the body is at.** §5.1 says a minor adds new capability
  bits and that unknown bits are ignored, and `caps` is a fixed `u32` field rather than something
  at the end of a payload — so a 1.2 radio answering a 1.1 Walter reports `0xff` and that Walter
  ignores the bit it does not know. The fixture's 1.1 HELLO case carries `0x7f` because it is a
  **1.1 radio**, not because a 1.2 radio must hide the bit. So the session suite's `arrange()`
  now gives the session **exactly the interfaces that case's own `caps` word names**
  (`applyCaps()`), which is how this firmware decides that word anyway — and is what keeps 1.0's
  and 1.1's files checkable, byte for byte, against a firmware that speaks 1.2. The alternative
  (hiding the bit below minor 2) would have been a second list of what a build can do, which
  `Interfaces.h` exists to avoid.
- **`LocalRequestAccess::localRequest()` returns `int`, with `kLocalRequestNoAnswer` (-1).** §5.9
  distinguishes *an empty answer* (an access list with nobody on it: `OK`, no bytes) from *no
  answer at all* (`ERR_RANGE`), and `size_t` cannot. 0 is the empty answer; negative is the
  refusal.
- **§5.9's table of four lives in the session, not in the board's service.** `isLocalRequestType`
  is in `Numbers.h` and `Session.cpp` refuses outside it, so the rule is portable, is tested
  natively for all 256 values, and *telemetry is provably never put to the node* — which is the
  point of refusing it rather than letting upstream answer it twice.
- **The buffer upstream's handler is given is `MAX_PACKET_PAYLOAD` wide and zeroed, not 33 bytes.**
  `handleRequest` does not look at `payload_len` at all: its neighbours branch reads `payload[1]`
  to `payload[6]` whatever the request's length was. §5.9 requires the bytes past `data` to read
  zero; the buffer is as wide as the plaintext a mesh request could hand the same function, so a
  branch that read further at some future pin still finds zero rather than something else.
- **`sender_timestamp` is 0**, the same value `BoardCli` passes for a console line ("there is no
  `sender_timestamp` via serial"). Nothing in the status, access-list, neighbours or owner-info
  branches reads it, and §5.9 drops the four tag bytes it is reflected into.
- **The `ClientInfo` is a member, zeroed with `memset` per call** (upstream's own `ClientACL`
  constructor does the same to its whole table), with `out_path_len = OUT_PATH_UNKNOWN`. A member
  and not a local because it is some 190 bytes and a request handler runs on the main loop's 2 KB
  stack — as is the request buffer.
- **The idiom is a portable header; the two tags that name upstream's members are one file.** The
  task asked for the idiom "in one file"; `src/roles/repeater/link/LocalRequest.cpp` is the one
  file that names either private member, and the mechanism itself is
  `src/common/cxx/PrivateMember.h` — portable, no MeshCore, so that
  `test/test_private_member` can hold it in the native environment where no board is needed. The
  tags must live in the template's own namespace (the friend's declaration and its definition have
  to be one function), which the header says and `LocalRequest.cpp` does by reopening
  `twinoak::cxx`.
- **`-Wnon-template-friend` is silenced in that header and nowhere else.** GCC warns that a friend
  declaration inside a template declares a non-template function; it is on by default and this
  repository builds `-Werror`. A friend that is not a template is exactly what the idiom wants,
  and the warning's own advice — a function template and an explicit specialisation defined inside
  a class template — is harder to read for no gain. The pragma is guarded to GCC, because clang
  does not know the option's name and would fail on that instead.
- **`tools/verify.ps1`'s link step reads `spec/fixtures/link/` off the directory.** It had a
  written-out list of two files, so `link-v1.2.json` — copied in before this task started — was
  checked by nothing. Reading the directory is the same habit as the board environments, which are
  read off `platformio.ini`, and means the next minor's file needs no edit here. This is the one
  change to the verification script, and it is why the task's third `linkref check` row exists.
- **`linkcli.py local …` and a miniature of upstream's handler in `tools/linkloop/`.** Not in the
  task's deliverables, but `docs/link.md` is the laptop tool's page and §2i could not be written
  honestly without a command behind it — and the bench list has to be "precise enough to be
  walked". The miniature builds the four answers in upstream's own layouts (the status block is
  the fixture's own 56 bytes, so what comes back through the pipe is the fixture's bytes), honours
  the neighbours request's count, offset, order and prefix length, and reproduces upstream's two
  silences. `tools/linkloop/check.sh` runs all of it, so `verify.ps1`'s native step now exercises
  §5.9 end to end — the real session, the real codec, the real refusals — with no board.
  `linkcli.py` also refuses to build a `local` request with more than 32 bytes of data, because
  the reference implementation refuses to: a Walter at 1.2 cannot send one, and the node's own
  `ERR_MALFORMED` for a frame that carried more anyway is the native test.
- **Discovery and trace are not in 1.2, and that is now what 1.2 left out.** 3.8's follow-up
  listed five jobs the Walter could not serve for the unit's own repeater; §5.9 answers four.
  Discovery and trace are mesh exchanges *with another node* and have no local form at all, so
  those two stay *Failed* — said in `tasks/phase-3.8/FOLLOWUPS.md` where the item is ticked, so
  that nobody looks for them in 1.2.
- **The scanner's descriptor also reads `link 1.2`.** `link_minor` in the image descriptor is
  `kProtoMinor` for every image, and the scanner speaks no link at all; it advertises nothing and
  has no `LocalRequestAccess`. Unchanged from 1.1, and not a thing this task introduced.
- **`tools/bench/test_walk.py`'s `HELLO` fixture now says `protocol 1.2` / `caps 0xff`.** The walk
  reads `role`, `board` and `band` out of that output and nothing else, so the change is cosmetic
  — but the fixture is meant to be what a radio of the day prints. 188 bench-tool tests still OK.

## The request to upstream

Drafted for Thomas to file at `meshcore-dev/MeshCore`; nothing was opened from here.

> **Title:** `simple_repeater`: make `MyMesh::handleRequest` and `reply_data` `protected`
>
> **Body:**
>
> We build a repeater as a subclass of `examples/simple_repeater`'s `MyMesh`, compiled from a
> pinned commit with none of MeshCore's tree edited (`81dbae59`, `repeater-v1.18.0`). The design
> works because everything a subclass needs is a public or protected virtual — `handleCommand`,
> `onAdvertRecv`, `logRx`/`logTx`, `searchPeersByHash`, `getPeerSharedSecret`, `onPeerDataRecv`,
> `onPeerPathRecv`, `onTraceRecv`, `onAnonDataRecv`, `sendSelfAdvertisement`, `savePrefs`. Thank
> you for that; it has meant a MeshCore release can be adopted here without a merge.
>
> Two members are the exception, and they are the two we need for one thing:
>
> ```cpp
> uint8_t reply_data[MAX_PACKET_PAYLOAD];                                    // MyMesh.h:90
> int handleRequest(ClientInfo* sender, uint32_t sender_timestamp,
>                   uint8_t* payload, size_t payload_len);                   // MyMesh.h:124
> ```
>
> Both are above the class's first `protected:`, so both are private.
>
> **What we want to do with them.** Our repeater sits in a box with a second board (an LTE
> management board) on a UART. That board has to read *its own* repeater's status and neighbour
> table and report them upstream, and it must do it **without transmitting**: a node that asks
> itself over the air wastes airtime, and on a duty-cycled band it is airtime a repeater needs. So
> we answer `REQ_TYPE_GET_STATUS`, `REQ_TYPE_GET_ACCESS_LIST`, `REQ_TYPE_GET_NEIGHBOURS` and
> `REQ_TYPE_GET_OWNER_INFO` over that UART by calling the node's own handler and copying its reply
> out — the same bytes a mesh admin would have been sent, with nothing on the air and nothing
> re-encoded.
>
> **Why not re-implement the four.** `acl`, `neighbours`, `_prefs` and `RepeaterStats`' sources are
> private too, so a re-implementation would be a copy of four reply layouts that drifts at every
> release — and the drift would be noticed on the air, by a client reading one field as another,
> rather than in a build. We would rather call your code.
>
> **What we do today.** We take pointers to both members through `[temp.explicit]` — "the usual
> access checking rules do not apply to names used to specify explicit instantiations" — which is
> standard C++ and not a cast, but it is still a workaround, and it means a rename in `MyMesh.h`
> breaks us at link time rather than at a seam you can see.
>
> **The ask.** Move `handleRequest` (and, if you are willing, `reply_data`) below the existing
> `protected:` in `examples/simple_repeater/MyMesh.h`. That is one line moved; it changes no
> behaviour, no ABI that matters to a monolithic firmware build, and nothing about what the class
> does. A subclass could then answer the node's own requests locally without reaching around the
> access specifier. If you would prefer a narrower seam than `protected:` — a
> `virtual int handleLocalRequest(...)` that defaults to `handleRequest`, say — we would be glad
> to take that instead and can send a patch for whichever shape you prefer.

If it lands, `docs/upstream.md`'s place 9 becomes two deleted template tags and a direct call, and
`spec/SYSTEM.md` S-2's exception of 7 November 2026 can go.
