# p3.9-01 — The key that was lost

The first radio became a new node because **this firmware formatted its own file system**.
Upstream's `setup()` — ours is a copy of it — calls the Adafruit core's `InternalFS.begin()`,
which erases the whole region and formats it when the volume will not mount, and then finds no
`/_main.id` and draws a new key, without a word. The volume had stopped mounting because one of
its seven 4 KB pages was torn: the core keeps LittleFS in 128-byte blocks on 4096-byte pages and
rewrites a page by erasing it and programming it again, so a reset, a halt over SWD or a power
dip inside that window takes 32 blocks at once — and the first page holds the superblock pair and
the root directory. The other three candidates are ruled out below, each with its line.

The fix is a rule — **a key is made only where no node was** — and a mode for the other case: a
region that is blank is a first boot, a mounted volume with neither key nor settings is a first
boot, the saved key is the node, and everything else (a torn volume, a key file that does not
read, settings without a key) is a **lost identity**, on which no key is made, nothing is written,
the mesh is not started, and the radio says `IDENTITY LOST` on its console every ten seconds and
on the link (`IDENTITY` → `ERR_STATE`, attention 6/1) until a person types `erase` and `reboot`.
`docs/flashing.md` §3a is rewritten around what actually happened and what to expect.

`tools/verify.ps1` is green on this machine, every step, on the final tree.

## The cause, from the code

### What happened to the radio, as the evidence says

- The next `HELLO` after the `.uf2` carried a new key (`agent.companion_changed`, meshmaster.dk).
- The admin password was a random one nobody knew and the repeater had to be registered again
  (`tasks/phase-3.9/README.md`). `ensureAdminPassword` draws a password only when **no settings
  file** was found or the build's placeholder is in it (`src/roles/repeater/app/AdminPassword.h`,
  `FirstBoot.cpp`), so the settings were gone with the key. A lost `/_main.id` alone would have
  made a new key wearing the old name and the old password. **The whole volume was gone**, and
  only a format does that.

### Candidate 1 — a half-written application ran: **ruled out**

- The Walter's flasher at `v0.1.0` (`components/core/flasher/flasher.cpp`, read with
  `git -C ../twinoak.meshcore.walter-firmware show v0.1.0:…`): `flash()` scans, halts, then
  `settingsInvalidate()` writes *bank 0 holds nothing* **before** `programPages()`, whose step 4
  erases the vector-table page first and whose last act is `programPage(first_page)`;
  `settingsValidate()` comes only after `readBack()` has hashed the whole image. On a resume the
  same `flash()` runs again: `programPages` skips the first page's erase only when it is already
  blank (*a resumed flash*), and `settingsInvalidate` leaves a record that already says invalid
  alone — so from the first erase to the last verified write the settings page said *invalid*
  without a gap. Every failure after the halt leaves through `finish(…, reset=true)`, a system
  reset into the bootloader.
- The bootloader: RAK's **0.4.4**, which has no published source. `bootloader_app_is_valid()` was
  found in the vendored 0.4.4 binary (`out/p3.4-01/rak-0.4.4_s140_6.1.1.dis.txt`, `0xF5468`) and
  compared with 0.4.3's (`0xF548C`, `out/p3.8-02/sdk11-bootloader.c:148`): the same two-word
  `0xFFFFFFFF` test on the application's first words, the same `bank_0 == 1` test
  (`ldrh r2,[r3]; cmp r2,#1`), the same optional CRC — instruction for instruction. `main` calls
  it (`bl 0xf5468` at `0xF48A4` and `0xF4910`) and the DFU start keeps both shapes
  (`movw r1,#3000` for a single tap or a UF2/serial magic; `r1 = 0`, no timeout, otherwise). So
  the half-written image never ran. 0.4.4 has one path 0.4.3 has not — it runs when the
  application is invalid and brings the BLE stack up (`cmp r7,#0xa8`, `DFU_MAGIC_OTA_RESET`,
  around `0xF4848`–`0xF48E0`): the *BLE OTA recovery* of RAK's changelog. What it does to the
  USB drive was not read out with certainty; §3a says so and keeps steps 2 and 3.
- And had it run: a torn image's behaviour is undefined, but it would have had to erase pages at
  `0xED000`, and nothing in this firmware or upstream's reaches the file system except through
  LittleFS after a mount.

### Candidate 2 — the file system was reformatted: **the cause**

- **The format.** `InternalFileSystem::begin()` at the pinned core `d541301`
  (`libraries/InternalFileSytem/src/InternalFileSystem.cpp`):

  ```c
  if ( !Adafruit_LittleFS::begin() ) {
    // Erase all sectors of internal flash region for Filesystem.
    for ( uint32_t addr = LFS_FLASH_ADDR; addr < LFS_FLASH_ADDR + LFS_FLASH_TOTAL_SIZE; addr += FLASH_NRF52_PAGE_SIZE )
      VERIFY( flash_nrf5x_erase(addr) );
    this->format();
    if ( !Adafruit_LittleFS::begin() ) return false;
  }
  ```

  `LFS_FLASH_ADDR 0xED000`, `LFS_FLASH_TOTAL_SIZE 7*4096`, `LFS_BLOCK_SIZE 128`. Upstream's
  `examples/simple_repeater/main.cpp:72-85` at the pin `81dbae59` calls it and then
  `if (!store.load("_main", …)) { new identity; store.save }`; ours
  (`src/roles/repeater/main.cpp`) was the same two lines until this task.
- **Why a volume stops mounting.** `flash_cache_flush` (`src/flash/flash_cache.c`, same library):
  a one-page cache; when the page's bytes differ it does `fc->erase(cache_addr)` and then
  `fc->program(cache_addr, cache_buf, 4096)`. `_internal_flash_erase` of a 128-byte LittleFS block
  is a write of `0xFF` through that cache, so **every block erase is a 4 KB page erased and
  programmed again** — about 85 ms of erase and two half-page writes. LittleFS 1.7
  (`Adafruit_LittleFS/src/littlefs/lfs.c`: `lfs_format` puts the superblock at the pair `{0, 1}`
  and allocates the root directory next) keeps its superblock pair and root directory in blocks
  0–3, all inside the first page. A reset, a halt over SWD or a power dip between that erase and
  the end of that program leaves the first page blank or torn, `lfs_mount` answers
  `LFS_ERR_CORRUPT`, and the core formats.
- **When this firmware writes that page.** `ClockKeeper::begin` restores `saved + 3600` with
  `file_epoch_ = saved`, so the first `loop()` a second later finds `t > file_epoch_ + interval`
  and writes the clock file (`src/roles/repeater/clock/ClockKeeper.cpp`, the pass; `test_clock`
  *the first second past the hour writes*). When the Walter then sets the time, the clock comes
  *down* from that margin and `saveBoth(epoch, force_file = epoch < prev_epoch)` writes again.
  Each is a copy-on-write of a 10-byte file and a commit to the root directory: the first page,
  erased and programmed, **twice in the first seconds of every boot that restored a clock** —
  which is when the next reset is likeliest (the Walter's own power-up glitches nRESET for
  ~60 µs, `wake_reason.cpp:116` at its `v0.1.0`; the bootloader's double-tap window; a person's
  hand). The hourly save and every `set` (`CommonCLI::savePrefs` removes and recreates
  `/prefs.json`) are the same page too.
- **The first boot after the `.uf2`** did what the code says: mount failed, the region was erased
  and formatted, `/_main.id` was absent, a key was drawn and saved, and `hasSavedPrefs` found
  nothing, so the first-boot profile ran and a random password was set. Every observed fact
  follows.

### Candidate 3 — a first boot regenerated the key: **ruled out**

- `FirstBoot.cpp` and `firstboot/Profile.cpp` run console lines and the password rail; nothing in
  them touches `self_id` or the identity store. The marker is `/prefs.json` (`hasSavedPrefs`), and
  its absence runs the profile, never a key.
- The key's path and format did not change between the image that made the key and `v0.1.0`:
  `git -C .pio/libdeps/…/MeshCore diff d9296435 81dbae59 -- src/helpers/IdentityStore.* src/Identity.*`
  is **empty** (the `0.0.0-dev` was built from `main` on or after 22 October, at either pin), and
  `git diff 81a1d08 2577a00 -- src/roles/repeater/main.cpp` touches only the console's length
  clamp and `board.loop()`. `IdentityStore(InternalFS, "")` → `"/_main.id"`, 64 bytes, at both.

### Candidate 4 — a page outside the image was erased: **ruled out**

- The flasher erases only through `nrf_.erasePage(plan->pages_region, addr)`, whose region is
  the pages the image covers — `0x26000`..`0x26000 + 102 × 4096 = 0x8C000` for the 417 284-byte
  `v0.1.0` — and the settings page through a region of exactly that page; the nRF52 layer refuses
  any other address (*the one function that writes outside the application region*, `flasher.cpp`).
- The `check` entry's zero hash (the Walter's `tasks/phase-8/FOLLOWUPS.md`) is the journal
  writing `check` before the candidate's record is loaded; the image the run was about is the one
  on its bad list, `003a8895…`, repeater `v0.1.0`, 102 pages, inside the region. The `.uf2`'s
  blocks: p3.8-02 walked all 1 631 of them, `0x26000`..`0x8BF00`, and the 0.4.4 handler refuses a
  block at or above `0xEA000`.

### Which reset tore the page: not from the code

Two triggers leave the same torn first page and the code cannot tell them apart: a reset or
power dip of the radio inside one of its own boot-time commits during the evening's power cycles,
or the flasher's halt (step 3, after a scan of about ninety seconds at 125 kHz) landing inside a
commit the Walter's time set had just forced. The region was erased by the format, so nothing on
the radio says which. The bench line that tells them apart next time — read page `0xED000` over
SWD before any recovery; blank is a page lost between erase and program, partial is a page lost
mid-program — is in *Not verified here*, and from this task on the firmware itself says *would
not mount and is not blank* instead of formatting.

## The fix

- **`src/roles/repeater/app/IdentityGuard.{h,cpp}`** (host-portable): `Volume` (mounted, blank,
  unmountable, format failed), `KeyFile` (loaded, absent, unreadable), `decide(volume, key,
  prefs_present)` → `kUseSaved` / `kMakeNew` / `kRefuse` with a reason; `regionIsBlank`; the lost
  mode's `LostIdentityCli` (a `link::CliAccess`: `erase` → the one action, `reboot` → the other,
  everything else → the explanation) and `explainLost`; `kFaultCodeIdentityLost = 1`.
- **`src/roles/repeater/main.cpp`**: `InternalFS.Adafruit_LittleFS::begin()` — the mount alone —
  then the region read as the chip maps it (`0xED000`, 28 672 bytes), the core's format only when
  every byte is `0xFF`, `exists("/_main.id")` and `store.load` for the key file, `hasSavedPrefs`
  for the settings, `decide`. `kMakeNew` is upstream's own lines unchanged. `kRefuse` prints the
  line, brings the link up in its lost shape, and `loop()` runs `lostLoop()`: the console into
  the lost mode's handler, the line again every ten seconds, the link.
- **`src/common/link/session/Session.cpp`**: `IDENTITY` with no identity interface is
  `ERR_STATE`. **`BoardLink.cpp`**: `linkBeginIdentityLost(cli)` — firmware, system, the handler
  behind `CLI`, the attention machine; nothing else, so `caps` is `0x21`; attention 6 raised once
  with detail 1.
- **Tests.** `test/test_identity`: the region's constants against the core's, the blank test,
  every row of the table (and the property *a key is made only where no node was* over the whole
  table), the explanation, `erase`/`reboot`/everything-else through fakes, the reply window
  (1 to 160 bytes, a guard behind it), null lines and buffers. `test_link_session`:
  `Identity.WithNoIdentityInterfaceItIsErrState`. Both in `[env:native]`; the link loop builds
  the changed session too.
- **What did not change.** A radio after `rak provision` (the region blank) boots as before;
  upstream's `erase` (a format that leaves nothing) is followed by a first boot as before; the
  scanner touches no file system; the clock keeper, the first boot and the settings are
  untouched.

## Decisions taken without asking

1. **Refuse, rather than format and announce.** The task offered *keep the key, or refuse in a
   way a person sees*. The key cannot be kept once the first page is torn, so it is a refusal:
   a node that was known to a mesh and to MeshMaster does not become a stranger by itself, the
   server is never told a key nobody decided to make, and whatever is left in the other six pages
   stays readable over SWD for as long as nobody types `erase`. The cost is a repeater that does
   not repeat until a person acts; the identity it would repeat under would be useless to the
   people who registered it anyway (S-1, S-13).
2. **Blank means every byte `0xFF`, and blank is formatted by the firmware itself.** A radio
   after `rak provision` has to reach its first boot unattended (S-5a), and a chip erase leaves
   exactly that. The core's own `begin()` does the format, so a fresh radio runs the code it
   always ran.
3. **Settings without a key is a refusal too**, not a first boot: it is the one case upstream
   turns into a new node wearing the old node's name and password.
4. **The lost mode keeps the link up**: `HELLO`, `PING`, `STATUS`, `REBOOT`, a `CLI` that knows
   two words, attention 6/1; `IDENTITY` is `ERR_STATE`; no clock, telemetry, mesh client or
   observations, so `caps` is `0x21` by construction. `radioUp` stays true — the SX1262 did
   initialise — so STATUS tells the truth and the news travels in `IDENTITY` and the attention.
5. **`erase` and `reboot` are the two words**, upstream's own, with upstream's reply shape, so
   that `rak cli erase` and `rak cli reboot` from the Walter need nothing new.
6. **The clock keeper was left alone.** Its two boot-time writes are the exposure, but the first
   of them is what keeps a quick reset from restoring a time behind an advert already sent, and
   moving the file to a page of its own or deferring the write is the clock's owner's call:
   a `[reviewer]` item in `tasks/phase-3.9/FOLLOWUPS.md`.
7. **The 0.4.4 reading stopped at `bootloader_app_is_valid` and the DFU start's two shapes.**
   The whole of `check_dfu_mode` was not reconstructed from the binary; §3a says what was read
   and keeps the steps that do not depend on it.
8. **The region's constants are cited, not asserted against the core.** The core does not export
   `LFS_FLASH_ADDR`; `test_identity` holds `kRegionStart`/`kRegionBytes` to the documented
   values and the comment names the file and the pin.
