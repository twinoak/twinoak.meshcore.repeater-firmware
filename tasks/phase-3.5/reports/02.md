# p3.5-02 — The scope across the band

`scope 150 960 2048` streams on the first board. The `-707` that stopped every span of four or
more segments at its third segment was the **image calibration** — RadioLib's own, made by
`SX1262::setFrequency()` before every move of 20 MHz or more — and the chip's `GetDeviceErrors`
says so (`IMG_CALIB_ERR`). What the board taught, in one sentence: **after a plugin sweep that
ended below about 205 MHz, this SX1262 refuses any image calibration reaching more than about
20 MHz above where the sweep left it, and every calibration after that one, until it is
hardware-reset.** Nothing short of a reset clears it; a reset and the plugin uploaded again does,
and the same arm is then accepted. So the arm of a segment is host-portable code now
(`armScopeSegment`, `src/roles/scanner/Sweep.cpp`): the frequency first with the driver's
calibration skipped, the segment's own calibration, the chip asked whether it took, and a refused
calibration answered by one reload and the same arm once more. On this board that is one reload
per pass over 150–960 MHz, at the second segment, and every span tried streams.

The `err` line names the call and its code for good (`call`, `code`, additive; the device errors
in `msg`), and the "silent" spans of p3.4-02's table were the console's: the `err` had been
written before a second open of the port, and `bench console --scanner "<line>" --collect N`
now keeps one open across both.

## The probes

All on the first board (`E926F6BEB407A412`, `rom` `SX1261 V2D 2D02`, the dummy load on the
antenna port), through `bench console --scanner`, with the scanner flashed by `bench flash` and
the repeater put back by `bench restore` / the walk. Two probe builds were made and stripped
again: `out/patch5.py` / `5b` (the arm instrumented, `probe*` verbs) and `out/patch8.py` (hand

`GetDeviceErrors` word after the call. `status=0x22` is STDBY_RC with the last command fine,
`0x2a` the same mode with *failure to execute*, `dev=0x0010` is `IMG_CALIB_ERR`.

**7. What does not clear it** (`07-repairs.log`, `11-candidates.log`), each after a fresh

**8. Frequency first, alone, was not enough** (`08-skipcal-spans.log` against
`10-final-build-spans.log`): with RadioLib's calibration skipped every span streamed — but that

**9. What does clear it** (`13-reload-walk-by-hand.log`): the 26 segments of the baseline armed

(`12-reload-build-spans.log`): all thirteen spans stream — `150 960 2048` at `sps` 21 (two

**The five questions of the task.** *Which segment fails first:* the first whose calibration
reaches about 216–220 MHz after a sweep that ended at or below about 205 — segment 2 of
`150 250`, segment 1 of `150 960 2048` once RadioLib's narrower calibration was out of the way;
never segment 0. *The number of segments or what the segment before did:* what the segment
before did — its sweep. `200 250` (two segments) streams and `150 250`'s segment 2 at the same
frequency is refused; `300 400` and `500 600` (four segments each) stream. *Which call:*
`setFrequency` — RadioLib's `CalibrateImage` inside it, surfaced by the `SetRfFrequency` after
it — and, with that one skipped, our own `calibrateImageRejection`, visible only through
`GetDeviceErrors`. *Does a stop or the reset clear it:* the hardware reset does (`stop`'s
`g_radio.reset()`, and the reload); nothing else tried does. *Where the silent case stops:* it
does not — both spans stream; the silence was the console's second open of the port.

## Deviations from the spec or the task

- **The fix is a workaround for the chip, not a correction of our order alone.** The task's
  candidates included the order of the four calls and the CalibrateImage parameters; the reading
  confirmed the first (RadioLib's calibration before the move is the refused one) and ruled out
  the second (every byte pair is accepted from a clean chip). But the refusal is the chip's
  reaction to the plugin's sweep, and no sequence of commands clears it — only a reset. The
  smallest workaround in our code is to ask the chip and reload when it refuses, which costs about
  30 ms once per pass of the whole range on this board. It is a finding for the plugin's author
  (follow-up) rather than a RadioLib issue: RadioLib's calibration is correct for a chip that has
  not run the plugin.
- **`kScopeSegmentMhz` is unchanged.** Lowering it would not have helped: the refusal is about
  where a calibration reaches relative to where the sweep ended, not about a segment's width,
  and the image check with a generator (9.10) is still the line that decides the width.
- **The report's thresholds are one board's.** "About 205 MHz" and "about 20 MHz above" bracket
  what was measured (a sweep ending at 200.2 refuses 228; one ending at 212.3 accepts 252;
  after 175, 212 is accepted and 220 refused) and are not in any datasheet. The code does not
  use them: it asks the chip.

## Decisions taken without asking

1. **The `err` carries the device errors in `msg` and not as a third field.** `call` and `code`
   are what the task asked for; the chip's word is for a person reading the line and goes in the
   text, so the line's schema grows by exactly the two fields the page documents.
2. **A refused calibration is retried once, after a reload, and only that call.** A `standby`,
   `setFrequency` or `setSweep` that fails is an `err` at once: those were never seen to fail
   and a retry would hide a chip that is really gone. The reload is one and not more: a chip that
   refuses twice from a fresh reset is a chip to report, not to loop on.
3. **The arm reads `GetDeviceErrors` after every calibration** — one SPI read in standby, about
   a hundred microseconds — rather than trusting a status the driver cannot see. The cost is
   nothing against the 7–9 ms the calibration itself takes; the gain is that a sweep is never
   taken through an image rejection the chip said it did not calibrate.
4. **`bench console` gained the line-then-collect form** rather than a new command, because the
   probing the task prescribes (`bench console --scanner`) was impossible without it, and the
   fake's test shows the one open.
5. **The walk was run twice**, before and after the commit, and the first run's tick of 9.9 was
   reverted so that the tick on the page names the commit the code is in (`479f482`). Both
   result files are kept, with the same counts.
6. **matplotlib was installed into PlatformIO's Python** (`pip install -r
   tools/noisescope/requirements.txt`) so that the walk could draw the picture, as the task
   allows. It is not a dependency of anything that builds or tests; nothing in the repository
   names it beyond the file that already did.
7. **The probe code is not in the tree.** The two probe builds were applied and stripped by
   scripts under `out/` (git-ignored); the final sources were built, flashed and walked after
   the stripping, and `test_rails` holds the scanner's sources as before.
