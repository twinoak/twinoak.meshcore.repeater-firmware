## What a person would have had to type otherwise, and why this way

The follow-up offered two ways: a better message, or recording the image. **Recording the image is
the one that removes the hand from the loop**, and the hand is the point: the message would have
told the person to type

    python tools/bench/bench.py record --image out/build/repeater_rak4630_single/firmware.zip

*after* the first flash and *before* `bench restore` — which is exactly what p3.4-02 did by hand,
and which no unattended session can do, because the tool is the only way a session touches a board
and nothing in a walk pauses for a person. A walk of §8 or §9 on a new unit would still have ended
in a *differs* on its restore line, and the walk's own rule is that a *differs* is never fixed by
the walk. With the image recorded there is nothing left to type: the first flash opens a run that
can be put back, and the restore says so in words that name the case.

Two things were deliberately kept:

- **`how` stays `bootloader`.** The record is honest about where it came from — the role and the
  version were read from a *file*, not from a board — and `describe()` says so in as many words
  (*read from the image, not from the board: it arrived with only its bootloader*), so a run file
  can never be mistaken for one a console answered.
- **The capitals are still there when they are true.** `bench record` with no `--image` on a
  bootloader-only board still records nothing restorable and `bench restore` still answers
  `RESTORE NOT POSSIBLE: THE RUN RECORDED NO RECOGNISABLE ROLE ON THE BOARD (bootloader)`
  (`RecordAndRestore.test_restore_with_no_role_recorded_still_says_so_in_capitals`). What changed
  is the normal case, not the refusal.

## Deviations from the spec or the task

- **`flash.log`'s first line is not a bootloader-only board**, and the task's reading of it
  (*walk 8 failed … on a radio that had no application*) does not survive the code. The line is
  `{"touched": null, "bootloader_port": null, "result": "failed: the bootloader's port did not
  appear within 15 s of the touch", "what": "walk 8"}` at 17:19:52, and *the touch* can only have
  been reached with an **application** port present (`flash_image`'s `if boot is None:`). The run
  record of 17:17:36 — three minutes earlier — already reads `repeater 0.0.0-dev … Repeater ID
  A76C9F71…`, so the board had an application by then. That failure is p3.4-02's **finding 4**: the
  touch put the board into the serial-only DFU (`239A:002A`) and the tool was waiting for
  `0x0029`. It was fixed there, by `boards/rak4631.json`'s four ids and `RAK_BOOT_PIDS`. Deliverable
  2's *no touch on a board with no application* was already true of the code (02's `else` branch);
  this task adds the test that holds it, which is what the deliverable asks for in that case.
- **The walk records the repeater image, not whatever it is about to write.** `bench flash`
  records the file it is writing, as the deliverable says. A *walk* is given the choice between
  the image of the step and the image the walk leaves on the board, and for a bootloader-only
  board it records the **repeater** image (`Walker._repeater_image`): every walk of
  `docs/bench.md` ends with the repeater back on the board — §9's own last line is *Flash the
  repeater back* — so recording the scanner image in §9 would have left a scanner on a new unit
  and called it restored. `spec/` says nothing about either; this is the smaller surprise.
- **`bench record --image <zip>` on a bootloader-only board is restorable too.** The task names
  `bench flash`; the same rule through `record` is the command p3.4-02 had to type by hand, and
  leaving it refusing in capitals while `flash` succeeded would have been two answers to one
  question. Test: `test_record_of_a_bootloader_only_board_with_an_image_is_restorable`.
- **The image on the board is not byte for byte the one p3.4-02 left, and no source changed.**
  Same role, same version, same 414 052 bytes, same descriptor, same identity — but
  `application_sha256` is `0480087f…` where 02's log says `c792e897…` (`package_sha256`
  `ff3d0dcc…` against `6219fd1f…`). Nothing under `src/` or `platformio.ini` differs between
  `9fb721b` and this branch (`git log 9fb721b..HEAD -- src/ platformio.ini` is empty): the
  **compile time is in the image**, through the Crypto library's RNG seed tag
  (`.pio/libdeps/repeater_rak4630_single/Crypto/RNG.cpp:475`, `tag = __TIME__ __DATE__`) and
  RadioLib's build string (`RadioLib/src/BuildOpt.h:656`). So a rebuild of the same commit is a
  new hash by design, the flash and the walk are unaffected, and it is written down here so that
  the two reports' hashes can be read side by side without being mistaken for a code change.

## Decisions taken without asking

1. **The run file gains one field, `found_descriptor`.** The deliverable asks for the descriptor
   to be recorded and there was nowhere to put it: `board_said` is for what a board said, and this
   board said nothing. It is the descriptor dict as `images.Image` carries it (role, board, band,
   version, slot, flags, link major/minor), so a reviewer reading a run file can see which file the
   restore will write without opening the zip.
2. **`--found` wins over the image being written.** A person who names the image that belongs on
   the board is saying what must go back on it; the file about to be written is only the best guess
   available when nobody said. Both are inspected by every guard first, as before.
3. **The *already ticked* list is said only when it is not empty**, like the *not found* one, so an
   ordinary first walk prints exactly what it printed before.
4. **A bullet that is neither `- [ ] ` nor `- [x] ` is still *not found*.** A page whose bullet
   shape moved is a page the walk should not edit, and that is the message it had.
5. **§8 was walked twice on the board**, once before the commit and once after, so that the
   evidence file names the commit the code is in (`…-8bf9094.md`). The first run's file is kept
   beside it; both are green and identical in their counts. Four flashes in all, each logged.
