## How a release goes now

1. *Actions → release → Run workflow*, branch `main`, **dry run** unticked. Nothing is typed.
2. `ci-green`: `gate.py check` (the three refusals), the version from `VERSION`, the signing key,
   the board environments, and `ci` green for the commit.
3. `build`: unchanged, one job per environment, the version baked in.
4. `publish`: the body is `release_notes.py top` — the waiting lines in merge order, then
   `standing.md` — and then what the manifest generates, unchanged. `gh release create "$TAG"
   --target "$SHA" --latest` makes the tag on the commit that was built and publishes it.
5. **the move**, in the same job and only after the release is out: `release_notes.py move`, one
   commit of `VERSION` and `release-notes/`, pushed as `release-notes/vX.Y.Z` and filed as a pull
   request the job opens and squash-merges itself.

A rehearsal is the same button with **dry run** ticked, from any branch, and may name a `ref`.
It compiles the same top, signs `0.0.0-dryrun+<sha7>` with the specification's test key, and
publishes nothing.

## Deviations from the spec or the task

- **`spec/` says nothing about how a release is started**, so there is nothing to disagree with:
  `spec/FIRMWARE-MANIFEST.md` governs what a release *carries* and none of that changed. The
  manifest, the signature, `SHA256SUMS`, the descriptor check and the base are byte for byte the
  same path; `python spec/tools/specsync.py verify spec` passes, 42 files.
- **The task says the top's *link to the flashing guide* is generated; it is, and
  `standing.md` names it too.** The generated part under the divider carries the real link at
  the release's own tag, which only the manifest can know. `standing.md` carries the bare words
  `docs/flashing.md` as a cross-reference, because the one check that has held every release note
  readable since p3.7-01 — *does this file point a reader at the flashing guide* — reads the
  **top** and would otherwise have had to be dropped for every generated one.
- **A line is at most 240 characters**, where meshmaster.dk's bound is 120. The task asks for
  "a sentence or two"; 120 is one short sentence. The rule is `release_notes.MAX_LINE`, in one
  place, and `docs/release.md` and `tasks/RUNBOOK.md` quote it.

## Decisions taken without asking

- **`VERSION` at the root, not a key in `platformio.ini`.** `platformio.ini` is what the build
  reads; the release's version is not a build setting (the build takes it as a flag). A file of
  one line is also what the workflow's own commit can rewrite without touching a build file, and
  deliverable 7 wants that commit to carry nothing a build could notice.
- **The rehearsal compiles the same top as the release would, with the version `VERSION` names.**
  The alternative was to print `v0.0.0` in the heading, matching the rehearsal's own build
  version. A rehearsal is worth running because it is the same bytes; the generated part below
  says **This is a dry run** in bold and names the test key, which is where that distinction
  belongs.
- **The merge-order lookup is `git log --first-parent --diff-filter=A`, with the file names as
  the fallback.** A file git does not know yet — the one the task running right now is adding —
  comes last by name, which is the only order there is for it. In the container
  `tools/verify.ps1` runs the release step in there is no `git` at all, so the fallback is
  exercised on every commit; the runner that publishes a release has git, and that is the only
  place the order is read for real. (Found by the first local run: `FileNotFoundError: 'git'`
  in `python:3.11-slim`. `gate._git` now answers "no tags" there rather than failing, which is
  right — this machine publishes nothing — and the merge-order test skips itself.)
- **A failed move goes red.** The release stands, the pull request is left open, and the run's
  summary says in bold that the release is out and is not undone, what is waiting, and what to
  do. meshmaster.dk's release does the same for the same reason: red is how a person is told.
- **`main`'s branch protection is not touched.** See *Not verified here*.

## Not verified here (and why)

Nothing on this list is a board: this task touches no firmware source, and no session opens a
port. What is left is one thing only a real release can show, and one setting only Thomas can
change.

1. **The pull request the workflow files after a release will not merge itself, as `main` is
   configured today — and that is a setting, not a bug.**
   `gh api repos/twinoak/twinoak.meshcore.repeater-firmware/branches/main/protection` says
   `required_status_checks.contexts = ["verify"]` and `required_pull_request_reviews` is on with
   `required_approving_review_count: 0`. So:
   - the push straight to `main` that would otherwise do this is refused (*Changes must be made
     through a pull request*), which is why it is a pull request at all;
   - and nothing will ever report `verify` on **that** pull request: GitHub starts no workflow
     from an event raised with the job's own token. `gh pr merge` will answer that the pull
     request is not mergeable, three times, ten seconds apart, and the job will then go red with
     the summary above.

   **The release itself is out and is not undone**, and the next one is refused until the version
   has moved, so nothing is lost and nothing is silently skipped. What Thomas does, once:
   **merge that pull request by hand** (it is `VERSION` and `release-notes/` and nothing else) —
   or, to let the job finish by itself, either take `verify` out of `main`'s required checks, or
   add a repository **ruleset** with a bypass for the `github-actions` app, which is the one kind
   of bypass GitHub offers that the Actions token can use. The task did not change the protection
   of `main`: that is a repository setting and a person's to decide, like the one the first check
   of this task reads.
2. **A real release has not been run**, by design — this task publishes nothing and the phase's
   README says the first real press is the next pile's. What *has* run end to end is the
   rehearsal below: the same three jobs, the same compile of the same lines, the same build,
   sign and verify. What it cannot show is `gh release create --latest` making the tag, and the
   move afterwards.

No line is added to `docs/bench.md`: nothing here can be walked with the rig.
