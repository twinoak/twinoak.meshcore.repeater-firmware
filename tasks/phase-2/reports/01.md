# p2-01 — the-job-and-its-peer

The mesh client has state, and one place where it touches upstream's packet handling. The Walter
can now name a peer and a path (`JOB_BEGIN`, `PATH_SET`), read the path back (`PATH_GET`) and end a
job (`JOB_END`), and `TwinOakMesh` will decrypt that peer's replies to us — and only that peer's,
and only while a reply is awaited — through an extra peer added **in front of** upstream's own
matches (`docs/ARCHITECTURE.md` §2). Nothing is transmitted: arming the wait, the five sends and
taking a reply are task 02. `HELLO`'s `caps` is `0x6f` now (`MESH_CLIENT` joins the five of phase
1), from one more non-null interface and nothing else. Not one file of upstream's is touched. Done
in one session.

## The bound on the number of matches, and that the extra peer stays inside it

Read from the pinned checkout (`d9296435`, `repeater-v1.17.1`).

`Mesh::onRecvPacket` (`src/Mesh.cpp:149–186`) handles a packet addressed to us like this:

```
int num = searchPeersByHash(&src_hash);              // :149
for (int j = 0; j < num; j++) {                      // :152
  uint8_t secret[PUB_KEY_SIZE];
  getPeerSharedSecret(secret, j);                    // :154
  uint8_t data[MAX_PACKET_PAYLOAD];
  int len = Utils::MACThenDecrypt(secret, data, macAndData, pkt->payload_len - i);
  if (len > 0) {                                      // the first MAC that verifies wins
    … onPeerPathRecv(pkt, j, …)  or  onPeerDataRecv(pkt, pkt->getPayloadType(), j, …);  // :173, :181
    found = true; break;
  }
}
```

The count `num` is a **loop bound and nothing else**: the loop keeps one `secret[PUB_KEY_SIZE]` and
one `data[MAX_PACKET_PAYLOAD]` per iteration (`:153`, `:155`) and indexes no array by `j`. Its
comment says "max 4 matches supported ATM" (`:148`) but nothing in the function enforces four;
returning `num + 1` only makes the loop run one more time, with index 0 tried first.

Upstream's own array is `int matching_peer_indexes[MAX_CLIENTS]`
(`examples/simple_repeater/MyMesh.h:116`). It is **written** only by `MyMesh::searchPeersByHash`
(`MyMesh.cpp:623–631`), one entry per ACL client whose hash matches, so it holds `n <=
acl.getNumClients() <= MAX_CLIENTS` entries; and it is **read** only by
`MyMesh::getPeerSharedSecret`, `onPeerDataRecv` and `onPeerPathRecv` (`MyMesh.cpp:634`, `:665`,
`:770`), each with the index it is handed and each range-checked against `acl.getNumClients()`. Our
three overrides only ever pass those functions `peerSlotUpstreamIndex(j, extra_)`, which is `j - 1`
for `j >= 1` while the extra peer is in front — i.e. `0 .. n-1`, never `n`. So upstream's array is
never indexed out of range: the extra peer is index 0, which our code takes before upstream is
asked, and upstream is given only indices into its own count.

`MAX_CLIENTS` is **20** in this build: `MyMesh.h` includes `helpers/ClientACL.h` (whose `:37`
defines `MAX_CLIENTS 20`) before its own `#ifndef MAX_CLIENTS / #define MAX_CLIENTS 32` (`:62–63`),
so the first definition wins, and nothing in `platformio.ini` defines it. `n + 1 <= 21 < ` nothing
there is sized by the count, so no array of upstream's or ours can overrun. The `static_assert`s in
`TwinOakMesh.cpp` hold `kPeerKeyLen`, `kSecretLen` and `kPathBytesMax` against `PUB_KEY_SIZE` and
`MAX_PATH_SIZE`.

## Deviations from the spec or the task

- **`PATH_GET` with no job is answered `ERR_STATE`.** §6.1 spells out `ERR_STATE` for `PATH_SET`
  with no job and says nothing about `PATH_GET` with none — but there is no path to return, and the
  codec cannot encode "no job". `ERR_STATE` is the same answer `PATH_SET` gives and the one a Walter
  can act on; the alternative (a path of mode 0) would be indistinguishable from a real flood job.
  Recorded here as the smallest decision that fits.
- **The 120-second rule counts from `JOB_BEGIN` as the first request.** `Job::begin` stamps
  `last_request_ms_` with the time it was called, so a job that is begun and never touched again
  ends 120 s later — which is what §6.1's "120 seconds pass with no request on the link while a job
  is begun" means with `JOB_BEGIN` being the request that began it.
- **`src/link/session/Interfaces.h`'s `MeshClientAccess` grew five methods.** p1-03 declared it with
  the two `STATUS` bits only; this task adds `beginJob`, `endJob`, `setPath`, `getPath` and
  `noteLinkRequest`, each returning a `Status` so that which refusal a request gets is the client's
  rule and not the session's. A null `mesh` pointer is still `kCapMeshClient` absent and
  `kErrUnsupported` for all four requests, as every other capability of this session behaves.
- **`src/link/BoardLink.cpp`'s `linkBegin` takes a `TwinOakMesh&`, not a `MyMesh&`.** It needs the
  subclass to reach `meshClient()`; the identity and CLI attachments still take the `MyMesh*` base.
  `src/main.cpp` passes `the_mesh`, which is a `TwinOakMesh`, so nothing there changes.
- **No `spec/` disagreement was found.** The fixture's four job cases are reproduced byte for byte.

## Decisions taken without asking

- **The extra peer is decided once per packet, in `searchPeersByHash`, and remembered in a member
  `extra_`** that the other three overrides read — exactly as upstream fills its
  `matching_peer_indexes[]` in its `searchPeersByHash` and reads it in its three. `Mesh::onRecvPacket`
  calls `searchPeersByHash` immediately before the peer loop every time (`src/Mesh.cpp:149`), so
  `extra_` is always fresh for the calls that follow it.
- **The job's peer is matched with `mesh::Identity(peerKey()).isHashMatch(hash)`** (`src/Identity.h:27`,
  `PATH_HASH_SIZE` bytes), the same question upstream's ACL answers (`MyMesh.cpp:626`). The 32-byte
  copy into a temporary `Identity` is paid only while a reply is awaited.
- **The clock keeper is told nothing for a packet the extra peer takes.** The four timestamp hooks
  of p1-04 (`onPeerDataRecv`, `onPeerPathRecv`, `onAnonDataRecv`, `sendSelfAdvertisement`) exist
  because upstream answers those packets with a reply carrying our clock. A packet our peer takes is
  one upstream never sees and never answers, so `noteTimestampEmitted()` is called only on the
  upstream branch of the two peer overrides, not on the ours branch.
- **`onPeerPathRecv` for our peer returns `false`.** No reciprocal path is ever sent for the
  client's peer — one packet per send is the rail (S-12), and `Mesh::onRecvPacket` sends a path
  return only when `onPeerPathRecv` returns true (`src/Mesh.cpp:173–178`).
- **The shared secret lives in the `Job`, calculated by `TwinOakMesh`.** `calcSharedSecret` needs
  the node's private key (`self_id`), which only the board class has; the buffer it writes into is
  the job's, so `Job::end()` is the one place it is wiped — read back to zero by a test, as the
  agent firmware's credential test does.
- **`onPeerDataRecv`/`onPeerPathRecv` count what the peer took** (`peerDataTaken()`,
  `peerPathTaken()`) and do nothing else, as the task asks for now. Task 02 replaces the counters
  with the reply machinery.
- **The loopback (`tools/linkloop/`) gained a real `Job` and a `--job` flag.** A job is per-boot
  RAM and each `linkcli` invocation is a fresh process, so `--job` begins one at startup for `path`
  to read back; `job begin`/`job end` as one-shot requests each answer `OK`. `caps` through the
  pipe is now `0x6f`.
