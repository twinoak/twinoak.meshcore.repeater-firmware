# p2-02 — the five sends

The Walter can now make the five exchanges an exit node makes with a repeater — a login, a
request, a CLI line, a path discovery, a trace — and get the reply. Each send is **one packet**,
built with MeshCore's own primitives exactly as `src/mesh/AgentMesh.cpp` of the agent firmware
builds it, and the reply is taken only from the job's peer and only while it is awaited, delivered
as `EV_MESH_REPLY` and readable with `REPLY_GET`. The mesh loop is never blocked: there is no
`await()`, the wait is a deadline checked from `loop()`. `HELLO`'s `caps` is unchanged at `0x6f`
(the five sends ride the `MESH_CLIENT` bit task 01 already lit). Not one file of upstream's is
touched. Done in one session.

## What is where

- **`src/meshclient/Reply.{h,cpp}`** (portable): the reply record of §6.3 and the matching rules
  of §6.2 as pure functions — what is awaited (a response, a text, a trace), by which tag (0 = the
  next from the peer), until when; a response while a text is awaited is dropped, a response with
  another tag is dropped, a text that is not CLI data is dropped, the first reply wins, the
  timeout. One record is held from arrival until the next send, `JOB_BEGIN` or `JOB_END`.
- **`src/meshclient/MeshPort.h`** (portable): the seam between the client (what goes on the air)
  and the board (how one packet is built and queued) — `uniqueTime`, `randomBytes`, the three
  send primitives, the radio's counters. It is what lets the five sends be tested on a host.
- **`src/meshclient/LinkMeshClient.{h,cpp}`** (portable): the five sends, the reply and the
  counters as the box link's `MeshClientAccess`, over the job of task 01 and the reply above. Each
  send gates (`ERR_STATE`/`ERR_BUSY`), builds the plaintext the agent firmware builds, hands it to
  the port, **wipes the plaintext**, counts it once, answers `send`/`tag`/`sender_ts`, and arms
  the wait in the same step. The replies arrive through `onResponse`/`onText`/`onTrace`/
  `onReturnedPath`, which the board's peer overrides call.
- **`src/app/TwinOakMesh.{h,cpp}`**: the board's half of `MeshPort` (upstream's `createAnonDatagram`
  / `createDatagram` / `createTrace` and `sendDirect` / `sendFlood`, two-byte hashes on every
  flood, the clock keeper told first), and the bodies task 01 left as counters in the peer
  overrides — `onPeerDataRecv` reads a `RESPONSE` or a CLI `TXT_MSG` as the reply, `onPeerPathRecv`
  learns the returned path and takes the response riding in it and **returns false**, `onTraceRecv`
  takes a completed trace with the awaited tag.
- **The session** (`src/link/session/Session.{h,cpp}`): the five send handlers, `REPLY_GET`,
  `MESH_COUNTERS`, and `EV_MESH_REPLY` pumped once a pass before anything else wants the wire. The
  receiver's buffer is wiped after every send, a retry included — the one place a password could
  linger.
- **`src/link/codec/FrameReceiver.{h,cpp}`**: `wipe()`, which zeroes both buffers through a
  `volatile` pointer and keeps the drop counters.
- **`tools/linkcli.py`**: `login [password]` (a prompt, or `-`, printed as stars), `request`,
  `status-of-peer`, `neighbours-of-peer`, `send-cli`, `discover`, `trace`, `reply`, `counters`.
- **`tools/linkloop/`**: a `LoopMeshPort` where the board builds a packet, so the five sends,
  `reply` and `counters` through the pipe are the firmware's own client; `check.sh` drives them.
- **Docs**: `docs/link.md` §2f (the five sends) and the message list to `0x6f`'s full set;
  `docs/bench.md` §6 (the walk with two radios); `docs/upstream.md` place 5 (the new citations).

## The five sends, checked against the pin

Read from the pinned checkout (`d9296435`, `repeater-v1.17.1`); the agent firmware's lines are at
`51faafb4`. Each send is a port of `AgentMesh`'s, and `src/app/TwinOakMesh.cpp` cites the upstream
primitive it is built from.

| Send | Built from (our board) | The receiving repeater reads it at | tag |
|---|---|---|---|
| `SEND_LOGIN` | `Mesh::createAnonDatagram` (`src/Mesh.cpp:512`), flood or direct | `MyMesh::handleLoginReq` (`MyMesh.cpp:90`), via `onAnonDataRecv` (`:571`) | 0 |
| `SEND_REQUEST` | `Mesh::createDatagram` (`src/Mesh.cpp:488`) | `MyMesh::onPeerDataRecv`'s `REQ` branch (`MyMesh.cpp:663`) → `handleRequest` (`:225`) | the timestamp |
| `SEND_CLI` | `Mesh::createDatagram`, `PAYLOAD_TYPE_TXT_MSG` | `MyMesh::onPeerDataRecv`'s `TXT_MSG` branch (`MyMesh.cpp:701`), admin-only | 0 |
| `SEND_DISCOVERY` | `Mesh::createDatagram`, always `sendFlood` | `handleRequest`'s `REQ_TYPE_GET_TELEMETRY_DATA` (`MyMesh.cpp:240`), reply as a returned path | the timestamp |
| `SEND_TRACE` | `Mesh::createTrace` (`src/Mesh.cpp:605`) + `sendDirect`'s TRACE branch (`:698`) | `Mesh::onRecvPacket`'s TRACE branch (`src/Mesh.cpp:42`) | the timestamp |

The things the agent firmware's comments say were learned on the air, each confirmed at the pin:

- **A login's tag is 0.** `handleLoginReq` writes the **repeater's** `getCurrentTimeUnique()` into
  the reply's first four bytes (`MyMesh.cpp:133`), not the sender's timestamp — so the reply cannot
  be matched by a tag of ours, and `Reply` takes the next response from the peer whatever its tag.
  `handleRequest`, by contrast, reflects the sender's timestamp back (`MyMesh.cpp` writes it at
  `reply_data[0..3]` before the body), so `SEND_REQUEST` and `SEND_DISCOVERY` are matched by it.
- **A password is at most fifteen bytes.** `BaseChatMesh::sendLogin` keeps at most fifteen
  (`BaseChatMesh.cpp:581`, `if (len > 15) len = 15`), and the repeater's field is sixteen with its
  NUL (`CommonCLI.h:29`, `char password[16]`), compared with `strcmp` (`MyMesh.cpp:101`). The codec
  holds `SEND_LOGIN`'s password to fifteen; `LinkMeshClient` refuses a sixteenth as `ERR_RANGE`.
- **A CLI line's timestamp is this node's unique second**, and matters: the repeater runs the line
  only when the timestamp is at or above the last it saw from this key (`MyMesh.cpp:704`), answering
  an equal one with an empty reply (a retry) and dropping a lower one. It comes from
  `getRTCClock()->getCurrentTimeUnique()` (`MeshCore.h:108`) at the moment the packet is built, as
  every tag of this client does — one strictly increasing series across requests and CLI lines.
- **Discovery always floods.** `AgentMesh::sendDiscovery` forces a flood whatever path is known,
  because the reply comes back as a returned path; ours ignores the job's path and passes a flood
  route to the port, and the plaintext is the companion's own (the inverse base-permission mask
  `handleRequest` reads at `MyMesh.cpp:240`, three reserved bytes, four random).
- **A trace cannot carry three-byte hashes.** Its flags byte states the hash size as an **exponent**
  in the low two bits (`Mesh::onRecvPacket`, `src/Mesh.cpp:50` reads `flags & 0x03`, `:55` shifts by
  it), so 1, 2, 4 and 8 bytes have an encoding and 3 does not. `hash_size` 3 is `ERR_RANGE`.
- **No reciprocal path is sent.** `onPeerPathRecv` returns **false**, and `Mesh::onRecvPacket` sends
  a path return only when it returns true (`src/Mesh.cpp:173`). One packet per send.

**Where the pin and the agent firmware's comments agree, and where they do not.** They agree on
every point above — the agent firmware runs this same MeshCore family (`repeater-v*`), and its
`sendLogin` comment's citation of `MyMesh.cpp:129-131` for the login reply's timestamp is
`MyMesh.cpp:133` here (a few lines' drift from a different point release, the same code). One place
is worth naming: the agent firmware's `ReplyCodec.h` says a trace's three-byte hashes "cannot be
traced at all" and gives the exponent encoding; the pin's `Mesh.cpp` is exactly that, and this
firmware refuses `hash_size` 3 rather than discovering it on the air. No disagreement was found
that changes a byte.

## The counters, and the reply's RSSI

`MESH_COUNTERS`' `rx` and `tx` are the radio driver's own
(`RadioLibWrapper::getPacketsRecv`/`getPacketsSent`, `RadioLibWrappers.h`), `noise_floor`/
`last_rssi`/`last_snr_q4` likewise (`getNoiseFloor`/`getLastRSSI`/`getLastSNR`), and `client_tx` is
ours — one per send. `adverts`, `adverts_dropped` and `obs_dropped` are the observation ring's
(task 03) and read 0 until it exists; `obs_dropped` is filled from the same count `STATUS` carries
as soon as a ring is wired, which is why the session reads it from `ObservationAccess` when that
interface is present. A reply's **SNR** is the packet's own (`Packet::getSNR() * 4`); its **RSSI**
reads `0x7FFF` (unknown) until task 03 adds the note `logRx` takes, exactly as §6.3 allows and as
the task says.

## Deviations from the spec or the task

- **`EV_MESH_REPLY` is pumped before a waiting request is answered, not only when the link is
  idle.** §6.3 says "when an awaited reply arrives or times out, the RAK sends one `EV_MESH_REPLY`";
  it does not say when relative to a request. The session reports the reply as soon as the wire is
  free, ahead of answering whatever the Walter asked next — which is microseconds away and is as
  often as not a `REPLY_GET` for that very record. This is the smallest reading that sends the event
  "when it arrives" without ever letting it jump an unsent response. Recorded here as the decision.
- **A send with `timeout_ms` 0 lets go of the record held from the previous exchange.** §6.2 says 0
  "means nothing is awaited"; it is silent on what becomes of a held reply. A send is one of the
  three moments §6.3 says the record is kept until (the next send, `JOB_BEGIN`, `JOB_END`), so a
  `timeout_ms` 0 send clears it like any other. Tested
  (`TheReply.TheRecordIsLetGoByTheNextSendJobBeginAndJobEnd`).
- **`src/link/session/Interfaces.h`'s `MeshClientAccess` grew eight methods**, and `FrameReceiver`
  grew `wipe()`. The task's deliverables; a null `mesh` pointer is still `kCapMeshClient` absent and
  `kErrUnsupported` for all eight requests, as every other capability behaves
  (`TheCounters.WithNoMeshClientTheEightAreUnsupported`).
- **No `spec/` disagreement was found.** Every send, reply and counter case of the fixture is
  reproduced byte for byte through the real session.

## Decisions taken without asking

- **The receiver is wiped after every send, a retry included — not only a login or a line flagged
  sensitive.** §6 asks for the password wiped "from every buffer the RAK copied them to". The
  request's bytes sit in the receiver's buffer, and a `SEND_CLI` a Walter forgot to flag still
  carried a password; wiping unconditionally after any of the five sends costs a loop over 492
  bytes and removes the chance of a leak from a missed flag. The retry path (the one-entry memory,
  which does not run the handler) wipes too, because a lost response being retried re-fills the
  receiver. A test searches the whole `Session`, the client, the job and the reply for the
  password's bytes and finds them nowhere (`NoBufferTheSessionOrTheClientOwnsHoldsThePassword`).
- **The plaintext the client builds is wiped whether or not the packet was sent**, through the
  agent firmware's `wipeBytes` (a `volatile` pointer). A login's plaintext holds the password; a
  `SEND_CLI`'s may; both are gone before the send returns, as `AgentMesh::sendLogin`/`sendCli` do it.
- **The reply's RSSI is `0x7FFF` until task 03.** The note `logRx` takes belongs to task 03's ring;
  until then the overrides pass `kReplyRssiUnknown`, and only the SNR — which is the packet's own —
  is known. §6.3 names `0x7FFF` as "not known", so this is the record saying so honestly.
- **`SEND_TRACE`'s `path_bytes` is a byte count, not an encoded `path_len`.** `Mesh::sendDirect`'s
  TRACE branch appends the path to the payload and reads the argument as a raw byte count
  (`src/Mesh.cpp:700`), unlike a datagram's `path_len`. The `MeshPort::sendTrace` seam takes the
  byte count directly, and `TwinOakMesh` passes it straight through.
- **`MeshClientAccess`'s send methods take the decoded message struct, not raw bytes.** The session
  decodes (holding §6.2's length bounds) and hands the struct to the client, which judges what only
  it can — a job, a reply awaited, a value out of range. The views in the struct point into the
  receiver, which is why the session wipes it after the call and not the client.
- **The loopback's `LoopMeshPort` transmits nothing**, so every send through the pipe is answered
  as the firmware answers it and its wait ends in the silence event — which is the send, the event
  path and the deadline watched from a laptop. A real repeater answers before the timeout; that is
  the bench's to confirm.
